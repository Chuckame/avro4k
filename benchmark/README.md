# Kotlin Avro Benchmark

This project contains a benchmark that compares the serialization / deserialization performance of
the following avro libraries and configurations:

- [Avro4k](https://github.com/avro-kotlin/avro4k/) — the library under test
- [Apache Avro](https://avro.apache.org/) `SpecificData`, with generated `SpecificRecord` classes and
  the fast reader — **Apache at full speed, and the comparison that matters**
- [Apache Avro](https://avro.apache.org/) `ReflectData` — Apache's slowest path, kept for continuity
  with older results
- [Apache Avro](https://avro.apache.org/) `GenericData`, fast reader on and off — isolates the effect
  of the fast reader
- [Jackson Avro](https://github.com/FasterXML/jackson-dataformats-binary/tree/master/avro)

Each benchmark is executed with the following configuration:
- Reading from a prepared byte array
- Writing to a hoisted, discarding sink built once in `@Setup` (never inside the measured method)
- Every `read()` returns its value so JMH consumes it — a benchmark that discards its result lets the
  JIT elide the work
- All libraries encode against **the exact same schema, generated by avro4k**, and `@Setup` asserts
  they produce byte-identical output (see *Equivalence is enforced, not assumed* below)
- Each workload is parameterised by size, so scaling behaviour is visible rather than a single point
- Generating a maximum of use cases:
  - nullable fields
  - unions
  - arrays
  - records
  - enums
  - primitives (string, int, float, double, boolean)
  - logical types (date, timestamp-millis, char, uuid)
- not benchmarking uuid as jackson uses a different representation (fixed) than avro4k and apache avro (string)

### What is compared, and why

| Library | Configuration | Note |
|---|---|---|
| **avro4k** | the library under test | |

| Apache `ReflectData` | reflection over the model | Apache's *slowest* path |

| Jackson Avro | `jackson-dataformat-avro` | |

> [!IMPORTANT]
> **Earlier avro4k benchmarks compared only against `ReflectData`, which flattered avro4k.**
> `SpecificData` is a flat 2.0–2.6× faster than `ReflectData` across every workload here. Any
> historical claim of the form "avro4k beats Apache" was measured against Apache's slowest
> configuration. The `SpecificData` column is the one that matters.

> [!NOTE]
> The **fast reader is enabled by default** in Avro 1.12.1
> (`System.getProperty("org.apache.avro.fastread", "true")`) — it was opt-in in 1.11.x. It also
> **cannot ever apply to `ReflectData`**: `FastReaderBuilder.isSupportedData` is an exact-class check
> (`getClass() == GenericData.class || == SpecificData.class`), so every `GenericData` subclass is
> excluded and `setFastReaderEnabled(true)` on one is silently ignored. That is why the reflect rows
> have no fast variant.

> [!NOTE]
> The `GenericData` rows decode into `GenericRecord`s rather than model objects, so their **absolute**
> numbers are not comparable to the other rows. Only the fast-on vs fast-off **ratio** is meaningful
> there.

### Equivalence is enforced, not assumed

Every library has its own model (`internal/apache/`, `internal/jackson/`, and the Kotlin model under
test), and `@Setup` **asserts** that all of them produce a schema equal to avro4k's canonical
`Avro.schema<T>()` and encode byte-identical output. A library that cannot round-trip a workload
fails the build instead of quietly vanishing from the report — which is exactly what used to happen:
before this gate existed, 9 of 87 combinations threw and were silently omitted, and nothing noticed.

Exemptions are explicit, individually justified, and **fail the gate when they become stale**. There
is currently one class of exemption: `jackson/complex`, `apache-generic/complex` and
`apache-specific/complex` (read path only) buffer Avro maps into a `HashMap`, which reorders map
entries on re-encode; those fall back to decoded-data equality. Writes are byte-identical everywhere.

> [!IMPORTANT]
> **Allocation does not explain the read gap, and therefore cannot police it.** On reads avro4k is
> within 1.2–1.4× of `SpecificData` on bytes/op — and actually allocates *less* on `simple` @500 —
> while being ~2× slower. The decode gap is CPU: virtual dispatch through
> `SerializationStrategy`, per-structure coder construction (which escape analysis may elide from
> B/op while still costing time), and per-instance workflow resolution.
>
> This revises the plan's assumption that `gc.alloc.rate.norm` is *the* primary acceptance metric.
> It remains the right metric for the **KMP migration** (no escape analysis on JS/native means
> those elided allocations become real) and for the **write** path. For the decode work it is
> necessary but not sufficient — **throughput must be judged directly**.
>
> The mirror image holds on write: avro4k allocates **4.4× more** than `SpecificData` on `complex`
> @200 yet runs within 1.08×. Neither metric substitutes for the other.

### Micro-benchmarks

The `micro` package isolates individual suspects so a later change can be attributed rather than
just observed. Run with `../gradlew microBenchmark`, or one family via `-Pbench='benchmark\.micro\.<Family>'`.

| Suspect | Measurement | ops/s | B/op |
|---|---|---:|---:|
| Field order ≠ schema order | write, matching | 9,151,542 | 136 |
| | write, swapped | **5,429,873** | **680** |
| | write, reversed | 5,322,122 | 680 |
| Nested records | read, depth 1 / 3 / 8 | 31.4M / 12.6M / 4.5M | 192 / 320 / 640 |
| | write, depth 1 / 3 / 8 | 29.4M / 10.5M / 4.8M | ≈0 / 232 / 392 |
| Polymorphic dispatch | read @1000, concrete → polymorphic | 14,789 → 13,654 | 156,392 → 188,392 |
| | write @1000, concrete → polymorphic | 15,167 → 16,964 | 80,256 → 112,296 |
| Collections | `readLongs` @ 10 / 1k / 100k | 4.2M / 59.0k / 511 | 616 / 28,352 / 2,800,383 |
| | `writeLongs` @ 10 / 1k / 100k | 4.9M / 78.3k / 627 | 168 / 232 / **243** |
| Strings | read, non-null → nullable | 2,626,991 → 1,875,683 | 1,480 → 1,480 |
| | write, non-null → nullable | 3,379,055 → 2,429,518 | 520 → 552 |
| Schema inference | cold (minus instance construction) | — | ~10,616 |
| | warm cache hit | 275,770,631 | ≈0 |

What these say:

- **Field reordering is a cliff, not a gradient.** One swapped field costs the same as a fully
  reversed record: **−41% write throughput** and +544 B/op (68 B per field). It only triggers when
  descriptor order differs from writer-schema order, so it is off the default path — but
  schema-evolution-heavy users pay it in full.
- **Polymorphism costs exactly 32 B per value** — one `Pair` — on both read and write.
- **Each nesting level costs ~64 B on read, ~32 B on write**, independent of payload.
- **`writeLongs` is allocation-flat** (243 B/op at 100,000 elements) while `readLongs` reaches
  2.8 MB, dominated by boxing decoded `Long`s. Decode again.
- **Nullable strings cost ~29% throughput and nothing in allocation** — a pure union-resolution CPU
  cost, invisible to B/op. Another case where allocation is the wrong instrument.
- **The warm schema cache is free.** Cold inference costs ~10.6 kB.

> [!NOTE]
> Two micro-benchmarks are floored by escape analysis and must not be read at their smallest
> parameter: nested `write` at depth 1 reports ≈0 B/op, and polymorphic at 10 shapes under-reports
> the per-value `Pair`. Use depth 3/8 and 1000 shapes. On JS and native these allocations are not
> elided at all — which is why they are tracked.

> [!NOTE]
> **Two suspects are not separable from outside the library.** Per-structure encoder/decoder
> allocation and the per-record-instance `RecordResolver.resolveFields` lookup happen inside the same
> `beginStructure` call with no public seam, so the nested-record family measures their *sum*.
> Attributing a win to one needs async-profiler (`-e alloc`) or a temporary counter inside `core`.

## Results — M1 (C2 + C3 + C9 + the C5 `readBytes()` fix)

2026-09-20, Apple M2 Pro, OpenJDK 21.0.11. Every number below is a **same-machine A/B**: the
pre-M1 commit (`8bc9b40`) and the post-M1 tree were measured back to back, with identical harness
settings, in a separate git worktree. The M0 baseline table above was *not* used as the "before"
side — its rows were produced with different iteration settings and are not comparable at this
resolution.

### Two measurement findings that change how these numbers must be read

**1. Escape analysis makes JVM `gc.alloc.rate.norm` useless as the acceptance metric here.**
Post-M1, `writeRecords` reports 3,200,261 → **250 B/op** at 100,000 elements — a 12,800x collapse.
It is an artifact. Re-run with `-XX:-DoEscapeAnalysis` and the same code allocates a flat
**72 B/element** at *every* size. What changed is not how much the code allocates but whether the
JIT can prove it does not escape: removing the `Key.Lookup` that escaped into `ConcurrentHashMap.get`
unblocked EA on the *remaining* per-structure objects. The `@Param=1000` row, where EA does not fire,
still shows the full 32 B/element and is the honest one.

**This matters beyond benchmarking**: v3 targets JS and native, which have no escape analysis. The
EA-on numbers describe the JVM only. The EA-off table below is what the other platforms will see, and
it is the one to judge a platform-neutral change by. Run it with:

```bash
./gradlew :benchmark:benchmarkAlloc -Pbench='...' -PallocJmhArgs='-jvmArgsAppend -XX:-DoEscapeAnalysis'
```

**2. JMH's within-run error bars understate cross-invocation variance by roughly an order of
magnitude.** `complex` write @200 measured 2,279 ± 41 ops/s in one invocation and 2,538 ± 38 ops/s in
another — **11% apart on identical code**, with both intervals tight and non-overlapping. A
single-invocation A/B at the few-percent level says nothing here, however confident its error bar
looks. Anything below ~10% must be re-measured across separate invocations before it is believed. One
"regression" in this milestone was found this way and withdrawn (see below).

### Allocation, escape analysis disabled — the platform-neutral result

This is the real, code-level win: **72 B per record structure** (per record instance, and per nesting
level) and **88 B per collection**, eliminated.

| Benchmark | param | B/op pre | B/op post | Δ |
|---|---:|---:|---:|---:|
| `readRecords` | 10 / 1k / 100k | 1,904 / 148,440 / 14,800,475 | 1,096 / 76,352 / 7,600,379 | **−42% / −49% / −49%** |
| `writeRecords` | 10 / 1k / 100k | 1,784 / 144,344 / 14,400,378 | 992 / 72,272 / 7,200,298 | **−44% / −50% / −50%** |
| `NestedRecord.read` | depth 1 / 3 / 8 | 264 / 536 / 1,216 | 192 / 320 / 640 | **−27% / −40% / −47%** |
| `NestedRecord.write` | depth 1 / 3 / 8 | 280 / 568 / 1,288 | 208 / 352 / 712 | **−26% / −38% / −45%** |
| `readLongs` | 10 / 1k / 100k | 704 / 28,440 / 2,800,454 | 616 / 28,352 / 2,800,366 | −88 B **flat** |
| `writeLongs` | 10 / 1k / 100k | 344 / 344 / 355 | 272 / 272 / 283 | −72 B **flat** |

The shape of those deltas is the attribution, and it is clean:

- **−72 B scales with the number of record structures** (once per record, once per nesting level) —
  that is C2 removing two `WeakKeyCache.getOrPut` calls, each allocating a `Key.Lookup`, from every
  `RecordDirectDecoder`/`RecordDirectEncoder` construction.
- **−88 B is flat regardless of collection size** — once per collection, not per element. That is C3
  removing the `AvroCollectionSerializer` wrapper allocation, exactly as predicted before measuring.
- `readLongs`/`writeLongs` have no record structures, so they get the flat collection win and nothing
  else. That is the negative control, and it behaves.

### End-to-end — much smaller than the micro-benchmarks suggest

The micro numbers above are attribution instruments, not user-visible speedups. On the end-to-end
suite, only `simple` moves clearly:

| Benchmark | param | pre ops/s | post ops/s | Δ | verdict |
|---|---:|---:|---:|---:|---|
| `simple` write | 1 | 4,722,206 | 5,703,037 | **+20.8%** | real |
| `simple` write | 25 | 286,019 | 307,834 | **+7.6%** | real |
| `simple` write | 500 | 13,564 | 14,673 | **+8.2%** | real |
| `simple` read | 25 | 213,401 | 227,432 | **+6.6%** | real |
| `complex` read/write | 1 / 15 / 200 | — | — | ±0…6% | not established |
| `lists` read/write | 100 / 10000 | — | — | ±0…5% | not established |

`complex` write @200 first measured **−6.5% with non-overlapping error bars** and was reported as a
regression. Re-measured across 5 forks on both trees it is **2,532 ± 57 → 2,539 ± 38 ops/s, i.e.
unchanged**, and its allocation is flat too (350,177 → 344,497 B/op, within error). The regression
was cross-invocation variance. It is written down here rather than deleted, because the failure mode
— a tight, confident, wrong error bar — will recur.

**Why the gap between micro and end-to-end?** The per-structure cost C2 removes is a fixed ~72 B and
a few cache lookups per record. In `simple` (one tiny flat record per op) that is a large share of
the work. In `complex` and `lists` the payload work — string encoding, collection traversal, actual
bytes — dominates, so halving a fixed per-structure overhead moves the total very little. This is
consistent with A8's finding that the read gap to Apache is flat across sizes: the remaining cost is
elsewhere, and C1/C4 in M5 are where it lives.

### Known gap in this measurement

Nothing in C9 is covered by any benchmark — no benchmark touches `AvroSingleObject`, the enum-default
path, or the generic tree — and the `readBytes()` fix in C5 is a correctness change measured only by
its tests. Those two units are justified by inspection, not by the numbers above.

> [!NOTE]
> **`benchmarkAlloc` fails on an empty or partial run.** JMH exits with 0 even when forks die, so the
> task checks its own report: it fails, naming the runs, if JMH printed a failure marker (`<failure>`,
> `<forked VM failed …>`, …) for any benchmark run, and it fails if there are fewer
> `gc.alloc.rate.norm` result rows than runs. A run that measured nothing can no longer end in
> `BUILD SUCCESSFUL`. The pre-M1 baseline hit exactly that: every fork died with
> `ClassNotFoundException` because `mainBenchmarkJar` lacked the benchmark classes (see "Allocation
> flame graphs" below for the cause). The task no longer runs from that jar.

## Results — M2 (KMP foundation: B0, B1, B6)

2026-09-23, same machine and JDK as M0/M1 (Apple M2 Pro, OpenJDK 21.0.11). M2 is a build and model migration with
no intended perf change; the one change on a hot path is B6's `SerializerLocatorMiddleware`, whose two
`IdentityHashMap`s became an `===` scan over ≤5 entries (`apply` runs once per encoded/decoded value). A/B of
`077a1af` (before) vs `ab24319` (after), interleaved before/after/before/after, 3 forks × 5 iterations each:

```bash

  -PallocForks=3 -PallocWarmups=3 -PallocIterations=5 [-PallocJmhArgs='-jvmArgsAppend -XX:-DoEscapeAnalysis']
```

| @100,000 longs | before | after |
|---|---|---|
| `readLongs` ops/s (invocation 1, 2) | 336.4 ± 9.3, 343.9 ± 6.8 | 336.6 ± 8.8, 335.9 ± 4.0 |
| `writeLongs` ops/s (invocation 1, 2) | 429.7 ± 14.5, 442.6 ± 8.4 | 452.7 ± 3.8, 454.5 ± 7.0 |
| EA off: `readLongs` / `writeLongs` ops/s | 339.7 / 452.9 | 337.1 / 449.2 |
| B/op `readLongs` (EA on = EA off) | 2,800,372 | 2,800,372 |
| B/op `writeLongs` EA on / EA off | 248 / 287 | 247 / 287 |

**Neutral.** Read −1.2% and write +3.7% on the means are both inside the ~10% cross-invocation band M1
established, and allocation is byte-identical — as expected, since `IdentityHashMap.get` never allocated either. B6
is accepted as "no regression", not as a win. *But "no measurable end-to-end change" hid a 2× slower lookup — see

### Intercepted-serializer lookup: `when` vs `IdentityHashMap` vs linear scan

`SerializerLocatorMiddleware.apply` runs on every encoded/decoded value and nearly always misses. B6 first replaced its
`IdentityHashMap`s (JVM-only) with a linear `===` scan, expecting a scan over ≤5 entries to be as fast. **It was not**, so
this micro-benchmark (`micro/IdentityLookupMicroBenchmark.kt`) was written to decide, and the middleware now uses
hand-written `when { x === A -> … }` chains. AverageTime, ns/op (lower is better), 3 forks × 5 × 1 s; every variant
allocates 0 B/op:

```bash
./gradlew :benchmark:benchmarkAlloc -Pbench='micro\.(InterceptionLookup|IdentityLookupScaling)MicroBenchmark' \
  -PallocForks=3 -PallocWarmups=5 -PallocIterations=5
```

Production shape — the 4 real entries, each structure reached through a static final as in the middleware `object`:

| | miss (the common case) | mixed (12 misses : 4 hits) |
|---|---|---|
| `when` chain of `===` | **0.753 ± 0.004** | **0.943 ± 0.008** |
| `IdentityHashMap` (pre-B6) | 1.235 ± 0.005 | 1.702 ± 0.091 |
| linear scan (B6's first `IdentityLookup`) | 2.388 ± 0.009 | 2.359 ± 0.003 |

Scaling (keys in a state field, padding entries beyond the 4 real ones), miss / mixed:

| entries | `IdentityHashMap` | linear scan |
|---|---|---|
| 4 | 1.97 ± 0.39 / 1.70 ± 0.07 | 2.45 ± 0.16 / 2.53 ± 0.03 |
| 8 | 1.83 ± 0.46 / 1.78 ± 0.07 | 3.29 ± 0.02 / 3.23 ± 0.07 |
| 16 | 2.05 ± 0.93 / 2.78 ± 0.49 | 4.88 ± 0.07 / 4.41 ± 0.02 |
| 32 | 3.51 ± 1.02 / 2.95 ± 0.76 | 7.82 ± 0.09 / 6.97 ± 0.03 |

- **The scan loses at every size** — there is no small-n crossover on the JVM, contrary to the expectation B6 was written
  under. It costs ~0.17 ns per extra entry.
- **The `when` chain wins by 1.6× over the map and 3× over the scan**, because the JIT compares against the static finals
  as constants. It is also the only candidate that is platform-neutral *and* free of any lookup structure.
- The gaps (1.6–3×) are far outside the ~10% cross-invocation band, so one invocation suffices here.
- End to end this is ~1 ns out of ~30 ns per `Long` element (see the B6 A/B above), which is why the scan's regression
  was invisible there: a micro-benchmark was needed to see it.

### Collection blocks decoded in the decoder: C3's wrapper cache removed

C3 cached the per-collection `AvroCollectionSerializer` wrapper in **one global slot**, which only hits while the same
collection serializer repeats. `readTwoCollections` (new: 1,000 records with two collection fields each) alternates
two serializers, the worst case, which no benchmark covered. The wrapper is gone: the Avro block loop now runs inside
`AbstractAvroDirectDecoder.decodeSerializableValue`. A/B of `5c8a318` (before) vs `131221b` (after), interleaved,
3 forks × 5 iterations each, `-Pparams='size=1000'`:

| | B/op before → after | ops/s before (inv. 1, 2 · EA off) | ops/s after (inv. 1, 2 · EA off) |
|---|---|---|---|
| `readTwoCollections` | 588,394 → **508,354** | 4,028 ± 321, 4,230 ± 62 · 4,245 | 4,451 ± 149, 4,407 ± 151 · 4,339 |
| `readRecords` | 76,352 → 76,352 | 17,489 ± 284, 17,410 ± 512 · 17,370 | 17,948 ± 408, 18,277 ± 184 · 17,743 |
| `readLongs` | 28,352 → 28,352 | 48,215 ± 3,383, 44,274 ± 410 · 46,326 | 46,340 ± 3,317, 43,738 ± 1,161 · 44,350 |

- **−80 B per record** on `readTwoCollections` = 2 collections × (16 B wrapper + 24 B cache holder): the old cache

- **`lists` read @10000 is neutral** (+2.8% EA-on, −1.2% EA-off) although its 10,000-entry block crosses the threshold: the

- `complex` @1 EA-on +9.7% is that row's known bimodality (fast forks: 8 of 9 after vs 3 of 9 before), not a speedup:

#### Verdict

The hardening is affordable on the read path: within ±3% on every end-to-end row except `complex` @15 EA-off, whose −6.9%
(not separated, ~4% per fork plus an occasional slow JIT mode) joins the M3-17 watch list. Allocation goes down by 16 B
per collection, except blocks above 1,024 items, which pay for list growth (+31% on one block of 100,000 longs, −0.1% net
on `lists` @10000). The 1,024 threshold stays as it is.

others). The investigation below covers `simple` write @25 only.

**Why `simple` write @25 is bimodal.** Three extra runs on head, with the JIT's log written to one file per fork:

- Full `-XX:+PrintCompilation -XX:+PrintInlining` (6 forks) made **every** fork fast (354–362k). The logging shifts the
  compiler's timing, and that alone removes the slow mode.
- `-XX:+PrintCompilation` only: 3 slow forks of 9. Then `PrintInlining` limited to kotlinx's shared
  `CollectionLikeSerializer.serialize` (the loop over the 25 records): 4 slow forks of 9.
- In **all 7 slow forks**, the JVM's optimizing compiler started compiling `CollectionLikeSerializer.serialize`
  53–72 ms *before* the element serializer `SimpleDataClass$$serializer.serialize`. In all 11 fast forks, the element
  serializer came first or at most ~20 ms later.
- When the loop is compiled first, the element serializer is not compiled yet, so the compiler inlines the whole
  record encode into the list loop. That runs out of the compiler's inlining budget (`NodeCountInliningCutoff`,
  `size > DesiredMethodLimit`): the record's `endStructure`, the bytes field and the array's `endStructure` become real
  calls. The loop's prologue is also compiled from a cold profile (`low call site frequency`, a `virtual call` to
  `SerialDescriptor.getKind`).
- In the 5 fast forks of the targeted run, the element serializer was "already compiled into a big method". The loop
  then calls one compiled record encoder, which has its own full budget.
- **Not a megamorphic `AvroSchema` call site.** Every type profile on the path is monomorphic in both modes
  (`AvroSchema$RecordSchema` 100%).
- What makes the budget run out is structural: the per-value encode methods are too big to inline anywhere.
  `AbstractAvroEncoder.encodeString` is 437 bytes of bytecode ("hot method too big") and `encodeInt` 190 (compiled "big"),
  because every call re-checks unions and re-dispatches on the writer schema's type.
- **Verdict:** which order you get is JIT timing, a lottery. What that order costs is structural. It is fixable in a
  platform-neutral way by shrinking the per-value encode path: resolve the writer type and union branch once per field,
  not on every call (union branch tables and the frame-stack encoder). It needs no JIT-shape trick. Re-measure this row
  after those changes.

### Verdict, in plain words

- **Nothing is worse than M0.** 6 of 16 rows are better (+15% to +37%: all of `lists`, `simple` write @500, `complex`
  write @200), 4 slightly better, 6 the same. Allocation is down on every row (writes −13% to −58%). On battery,

- **Writes are at or above Apache from medium sizes up** (`simple` 1.31×/1.50×, `complex` 0.97×/1.05×, `lists`
  0.93×/0.94×). The gap left is the smallest payloads (`simple` @1 0.79×, `complex` @1 0.92×): a fixed cost per call and
  per structure, targeted by the frame-stack encoder. Union branch tables target `complex`'s unions and the oversized
  per-value encode methods behind the bimodal `simple` writes.
- **Reads are the main gap, still about half Apache's speed:** `simple` 0.52–0.68×, `complex` 0.53–0.55×, `lists`
  0.55–0.57× (M0 0.45–0.64×). Read allocation moved by only 3–5% on `complex` and `lists`, because a decoder is still
  built for each record, array block and map block. That is the job of the frame-stack decoder, fewer allocations in
  polymorphic decode (a `Pair` per value on `complex`'s sealed field), and the string/bytes decode fast paths. The
  reordering encoder without closures cannot show here, because no workload reorders fields.
- **Compared with the battery run:** ops/s are 40–60% higher, and the noise floor is half as wide (±3.3%). The M0
  ratios to Apache are back within ~0.07× of the M0 tables (`complex` read @1: 0.54×, battery 0.73×). `lists` write

## Allocation profiling

Throughput alone is **not** a sufficient acceptance metric for avro4k performance work. On the JVM the
JIT and escape analysis hide a lot of allocation; on Kotlin/JS and Kotlin/Native they do not exist.
Bytes allocated per operation is therefore the portable proxy for "will this also be slow off the JVM",
and **`gc.alloc.rate.norm` (B/op) is the primary acceptance metric**: it must go down for a performance
change to count, and must not regress during the multiplatform migration. Report throughput next to it,
never instead of it.

### Running it

```shell
../gradlew :benchmark:benchmarkAlloc -Pbench=Avro4kSimpleBenchmark.write -Pparams='recordCount=1'
```

The task compiles the JMH stubs and runs JMH with its GC profiler (`-prof gc`), on the same classpath as
the plugin's own `benchmark` task. Output is streamed to the console *and* captured in
`build/reports/benchmarks/alloc/main-alloc.txt`; the `gc.alloc.rate.norm` result rows are echoed again
at the end of the run. The task fails if any benchmark run failed or measured nothing.

| Gradle property   | Default   | Meaning                                                                                      |
|-------------------|-----------|----------------------------------------------------------------------------------------------|
| `-Pbench`         | `Avro4k`  | JMH benchmark-name regex, e.g. `Avro4kSimpleBenchmark.write` or `complex.Avro4kBenchmark`.     |
| `-Pparams`        | *(none)*  | `@Param` selection, `;`-separated, e.g. `-Pparams='recordCount=1;other=a,b'`. Empty = full matrix. |
| `-PallocForks`    | `1`       | JMH `-f`.                                                                                     |
| `-PallocWarmups`  | `2`       | JMH `-wi`.                                                                                    |
| `-PallocIterations` | `3`     | JMH `-i`.                                                                                     |
| `-PallocTime`     | `1s`      | JMH `-w` and `-r`.                                                                            |
| `-PallocJmhArgs`  | *(none)*  | Extra raw JMH arguments, space-separated (e.g. `-PallocJmhArgs='-bm avgt'`).                   |

The defaults are deliberately much shorter than the `@Warmup`/`@Measurement` annotations on the
benchmark classes: allocation per operation converges almost immediately, unlike throughput. Always
pin `-Pbench` (and usually `-Pparams`) to a small subset — the full matrix is ~25 minutes, whereas a
single benchmark class at one `@Param` value takes ~10 seconds.

### Reading the output

```
Benchmark                                       (recordCount)   Mode  Cnt        Score        Error   Units
Avro4kSimpleBenchmark.write                                 1  thrpt    3  4879798.474 ± 604470.633   ops/s
Avro4kSimpleBenchmark.write:gc.alloc.rate.norm              1  thrpt    3      280.001 ±      0.001    B/op
```

`gc.alloc.rate.norm` is the number of bytes the benchmark method allocates per invocation — here 280
bytes to encode one record. The error is normally near zero: unlike throughput, this number is stable,
so a change of even a few bytes per op is real and worth explaining. `gc.alloc.rate` (MB/sec) is just
that figure multiplied by throughput, and `gc.count` / `gc.time` tell you what the allocations cost in
collection pauses.

### Allocation flame graphs with async-profiler

The GC profiler says *how much* is allocated, not *what*. For that, use
[async-profiler](https://github.com/async-profiler/async-profiler) in allocation mode (`-e alloc`)
against `ManualProfilingRead` / `ManualProfilingWrite` in
`src/main/kotlin/com/github/avrokotlin/benchmark/ManualProfiling.kt`. Those `main()`s run the complex
`Avro4kBenchmark` read/write path 1,000,000 times in a plain loop, which is exactly the shape a
sampling profiler wants — no JMH harness frames in the way.

They are launched from the plugin's self-contained JMH uber-jar (its `Main-Class` is JMH's, so pass the
class explicitly):

```shell
../gradlew --no-configuration-cache :benchmark:mainBenchmarkJar
JMH_JAR=$(ls build/benchmarks/main/jars/*-JMH.jar)
java -cp "$JMH_JAR" com.github.avrokotlin.benchmark.ManualProfilingRead
```

> [!WARNING]
> Build the jar with `--no-configuration-cache`. The plugin fills it from a provider that keeps only
> the classpath directories that already exist when the provider is evaluated. With the configuration
> cache on, that happens before `compileKotlin` runs, so on a fresh or cleaned `build/` the jar silently
> lacks every benchmark class, and a reused cache entry keeps producing it that way.
> Do not hardcode the jar name either: it embeds the project version (`local-SNAPSHOT` for local
> builds). Glob for `*-JMH.jar`.

**async-profiler is not installed on the current dev machine** (`java -jar "$JMH_JAR" -lprof` lists
`async` as unsupported, and `perf`/`dtrace` need `sudo`). Install it first — on macOS, download the
`macos` release archive from the project's releases page or `brew install async-profiler`, then point
the JVM at the native agent:

```shell
AP_HOME=/path/to/async-profiler        # directory containing lib/libasyncProfiler.dylib
java -agentpath:"$AP_HOME/lib/libasyncProfiler.dylib"=start,event=alloc,flamegraph,file=build/reports/benchmarks/alloc/read-alloc.html \
     -XX:+UnlockDiagnosticVMOptions -XX:+DebugNonSafepoints \
     -cp "$JMH_JAR" com.github.avrokotlin.benchmark.ManualProfilingRead
```

On macOS the dynamic loader must be able to find the library, so either pass the absolute path to
`-agentpath:` as above or export `DYLD_LIBRARY_PATH="$AP_HOME/lib"` first. Opening the resulting
`read-alloc.html` gives the allocation flame graph: frame width is bytes allocated, so the widest
frames are the ones to attack. Replace `ManualProfilingRead` with `ManualProfilingWrite` for the
encoding path.

Once async-profiler is installed, the same agent can be attached to the JMH run instead
(`-PallocJmhArgs='-prof async:event=alloc;output=flamegraph'`), but the manual `main()`s stay the
faster loop to iterate on.
