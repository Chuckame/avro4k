# A1 — benchmark methodology fixes

**Outcome:** done
**Commit:** `0c14e9b5d21a22932f8f3afc201784b461e1a48e` (code + this note), plus this one-line sha backfill on top.

## What changed

All changes are confined to `benchmark/src/main/kotlin/com/github/avrokotlin/benchmark/`.
No `core/` source was touched, `benchmark/build.gradle.kts` needed no change, and neither
`benchmark/README.md` nor `ManualProfiling.kt` were modified.

### Defect 1 — dead-code elimination on `read()`

All 9 `read()` methods now return the decoded value instead of `Unit`:

| class | new signature |
| --- | --- |
| `complex/Avro4kBenchmark` | `fun read(): Clients` |
| `complex/ApacheAvroReflectBenchmark` | `fun read(): Clients` |
| `complex/JacksonAvroBenchmark` | `fun read(): Clients` |
| `simple/Avro4kSimpleBenchmark` | `fun read(): SimpleDatasClass` |
| `simple/ApacheAvroReflectSimpleBenchmark` | `fun read(): SimpleDatasClass` |
| `simple/JacksonAvroSimpleBenchmark` | `fun read(): SimpleDatasClass` |
| `lists/Avro4kListsBenchmark` | `fun read(): ListWrapperDatasClass` |
| `lists/ApacheAvroReflectListsBenchmark` | `fun read(): ListWrapperDatasClass` |
| `lists/JacksonAvroListsBenchmark` | `fun read(): ListWrapperDatasClass` |

**The 9 `write()` methods intentionally stay `Unit`.** Every one of them writes into a sink
(`kotlinx.io.Sink` for avro4k, an `org.apache.avro.io.Encoder` for Apache, an `OutputStream`
for Jackson) and produces no value. Returning the sink would be meaningless and returning the
input value would be a no-op for the JIT. The sink is a `@State` field, so it is reachable from
outside the benchmark method and the encoding work cannot be eliminated. This is the correct
JMH shape for a void-returning workload; it was already what the code did and it is left alone.

### Defect 2 — `write()` measured sink construction

Before, the three avro4k `write()` methods each allocated
`OutputStream.nullOutputStream().asSink().buffered()` *inside* the measured method, while
Apache built its `Encoder` once in `setup()`. The avro4k number therefore carried a per-op
allocation of a `RealSink` + a `Buffer` + an anonymous `OutputStream` that Apache never paid.

Fix — **option "single discarding sink built in `@Setup`"**, applied to all three harnesses:

- **avro4k**: a `lateinit var sink: Sink` field built once in `setup()` as
  `OutputStream.nullOutputStream().asSink().buffered()`. `write()` does
  `Avro.encodeToSink(...)` followed by `sink.flush()`.
  The `flush()` is **required for boundedness**: `Avro.encodeToSink` explicitly does *not*
  flush (see the KDoc on `core/.../AvroKotlinxIoExtensions.kt`), so a hoisted buffered sink
  that is never flushed would accumulate every encoded byte of every op for the whole
  iteration and OOM on the `lists` workload. `flush()` drains the buffer into
  `nullOutputStream` (a no-op `write`) and recycles the segments, so memory is flat.
- **Apache**: already hoisted; only an `encoder.flush()` was added so all three harnesses
  terminate an op the same way. `DirectBinaryEncoder.flush()` only flushes the underlying
  stream, which is a no-op here.
- **Jackson**: `OutputStream.nullOutputStream()` was allocated per op inside `write()`; it is
  now a `lateinit var out: OutputStream` field built in `setup()`.
  **Gotcha:** Jackson's `ObjectWriter.writeValue(OutputStream, …)` closes the target by
  default, and `OutputStream.nullOutputStream()` throws `IOException` on any `write` after
  `close()`. Hoisting the stream therefore *requires* disabling `AUTO_CLOSE_TARGET`, which is
  now done on the `AvroMapper` (`.disable(JsonGenerator.Feature.AUTO_CLOSE_TARGET)`).
  Flushing is unaffected (`FLUSH_PASSED_TO_STREAM` stays on and the generator still flushes
  its own buffer on close).

Why a discarding sink rather than the `kotlinx.io.Buffer` + `clear()` variant that was also
suggested: a `Buffer` retains the encoded bytes, so avro4k would pay a real memcpy into
segments while Apache and Jackson write to a no-op stream — that reintroduces a bias in the
opposite direction. Keeping all three on `nullOutputStream` is the minimal, symmetric change
and keeps the Apache/Jackson numbers comparable to the pre-existing baseline.

### Defect 3 — one data shape per workload

`@Param` added on the three abstract `@State` base classes.

| workload | field | values | previous fixed value | data shape driven |
| --- | --- | --- | --- | --- |
| `complex` | `clientCount` | `1 / 15 / 200` | 15 | `ClientsGenerator.generate(clientCount, RandomUtils())` |
| `simple` | `recordCount` | `1 / 25 / 500` | 25 | `SimpleDatasClass.create(recordCount, RandomUtils())` |
| `lists` | `entryCount` | `100 / 10000` | 10000 | `ListWrapperDatasClass.create(WRAPPER_COUNT = 1, entryCount, VALUES_PER_ENTRY = 100)` |

Reasoning for the sets:

- `complex` / `simple`: `1` isolates per-call fixed overhead (schema walk, encoder setup,
  polymorphic dispatch) from per-element cost; the old value is kept as the midpoint so the
  new runs stay comparable with any previously recorded numbers; the top value is ~13x/20x
  the midpoint, enough to show whether the curve is linear.
- `lists`: **the outer list was deliberately shrunk from 10 to 1.** The old shape was
  `10 wrappers × 10 000 StatsEntry × 100 longs = 10 000 000 longs`, which is what produced the
  ~6 ops/s figure — far too few ops per iteration for a usable error bar. Driving the size
  from the `entries` dimension alone with the outer list pinned at 1 gives
  `1 × 10 000 × 100 = 1 000 000 longs` at the top point, measured at ~57–63 ops/s (see below),
  a 10x improvement in sample count for the same *shape* of workload. The outer list was pure
  repetition and added no information. `WRAPPER_COUNT` and `VALUES_PER_ENTRY` are named
  `private companion object` constants in `SerializationListsBenchmark` so the pinned
  dimensions are explicit rather than magic numbers at the call site.

No change was needed in `internal/` — `ClientsGenerator.generate`, `SimpleDatasClass.create`
and `ListWrapperDatasClass.create` already took the sizes as parameters.

### `@Param` on Kotlin `internal` classes — the non-obvious part

JMH's generated harness assigns the parameter via
`SerializationBenchmark.class.getDeclaredField("clientCount")` + `Field.set`, so it needs a
**backing field**, not the Kotlin accessors. Two Kotlin-specific traps:

1. A plain `var x: Int = 15` has a *private* backing field. `@JvmField` is required so the
   field is emitted with the property's visibility. (`lateinit var` is the special case that
   already exposes its backing field — which is why the pre-existing `lateinit var clients`
   worked.)
2. `@JvmField` is rejected on an *open* property, and this module applies
   `kotlin("plugin.allopen")` with `annotation("org.openjdk.jmh.annotations.State")`, which
   makes every member of the `@State` classes open. The fix is an explicit `final` modifier:
   `@Param(...) @JvmField final var clientCount: Int = 15`. Without the `final` the build
   fails with `JvmField can only be applied to final property`.

Each `@Param` field also keeps a **default value** equal to the old hard-coded size. This is
required because `ManualProfiling.kt` (out of scope for this unit) instantiates
`Avro4kBenchmark()` directly and calls `initTestData()` outside the JMH harness; without a
default it would read an uninitialised size of 0.

## What was measured

Everything below was run from the JMH uber-jar directly
(`benchmark/build/benchmarks/main/jars/benchmark-main-jmh-local-SNAPSHOT-JMH.jar`), **never**
through the Gradle `benchmark` tasks, which are owned by the orchestrator.

Build verification:

```
./gradlew :benchmark:compileKotlin :benchmark:mainBenchmarkGenerate   # BUILD SUCCESSFUL
./gradlew :benchmark:mainBenchmarkJar                                 # BUILD SUCCESSFUL
./gradlew spotlessApply                                               # BUILD SUCCESSFUL, no reformat of the touched files
```

(The generate task in this plugin version — kotlinx-benchmark 0.4.17 — is
`:benchmark:mainBenchmarkGenerate`, not `benchmarkGenerate`.)

Generated-source verification (grepped, not assumed), under
`benchmark/build/benchmarks/main/`:

- All 9 `*_read_jmhTest.java` contain `blackhole.consume(<state>.read())` — the return value is
  now consumed, dead-code elimination is no longer possible.
- The 9 `*_write_jmhTest.java` contain a bare `<state>.write()` and zero `blackhole.consume`,
  as expected for a `Unit` method.
- All 18 `*_jmhTest.java` contain
  `…SerializationBenchmark.class.getDeclaredField("clientCount")` (resp. `recordCount`,
  `entryCount`) + `f.set(val, Integer.valueOf(control.getParam(...)))`.
- `resources/META-INF/BenchmarkList` records the value sets:
  `M 1 11 clientCount 3 …` (3 values), `M 1 11 recordCount 3 …` (3 values),
  `M 1 10 entryCount 2 …` (2 values).

### Matrix growth

| workload | before | after |
| --- | --- | --- |
| complex (3 libs × 2 methods) | 6 | 18 |
| simple (3 libs × 2 methods) | 6 | 18 |
| lists (3 libs × 2 methods) | 6 | 12 |
| **total** | **18** | **48** |

At the configured 5×1 s warmup + 5×3 s measurement plus fork/JIT overhead, a full run is
roughly 48 × ~30 s ≈ **25 minutes**, up from ~10 minutes. The `lists` `@Param` was kept at 2
values (and the outer list at 1) specifically to avoid a multi-hour matrix.

The `benchmark { configurations { … } }` filters in `benchmark/build.gradle.kts` are regexes
over the benchmark FQN (e.g. `^com.github.avrokotlin.benchmark.simple.+.read$`). Parameters do
not appear in the FQN, so every existing named configuration still matches and now simply runs
each selected benchmark once per parameter value. No build-script change was needed. If a
future unit wants a fast smoke configuration, JMH's `-p name=value` (or a `param(...)` entry in
a kotlinx-benchmark configuration block) can pin a single size.

## What was rejected, and why

- **`kotlinx.io.Buffer` + `clear()` for the avro4k `write()`.** Rejected: a `Buffer` retains
  the encoded bytes, so avro4k would pay a segment memcpy that Apache (`directBinaryEncoder`
  straight to `nullOutputStream`) and Jackson do not. That swaps one bias for another. The
  hoisted discarding sink keeps all three symmetric.
- **Hoisting the `Decoder`/parser out of `read()`.** Apache builds
  `DecoderFactory.get().binaryDecoder(data, null)` inside `read()` and could reuse it via the
  second argument. It was deliberately left alone: avro4k's `decodeFromByteArray` and Jackson's
  `ObjectReader.readValue(ByteArray)` both construct their per-call reader internally and
  expose no reuse hook, so making Apache reuse its decoder would bias the read comparison *in
  Apache's favour*. All three currently pay a per-call decoder setup, which is both symmetric
  and what a real caller pays.
- **Reusing a growable in-memory `ByteArrayOutputStream` for Apache/Jackson** so all three
  write into memory. Rejected: `ByteArrayOutputStream.write` is `synchronized`, which adds a
  monitor op to the Apache/Jackson side only, and it would need a new helper class outside this
  unit's file scope.
- **Changing the fork / warmup / measurement counts.** Out of scope; the orchestrator owns run
  configuration.
- **Touching `ManualProfiling.kt`** (explicitly out of scope) — accommodated instead by giving
  every `@Param` field a default value.

## Follow-ups

1. **Residual asymmetry found beyond the three defects (fixed in passing):**
   `JacksonAvroSimpleBenchmark.data` was `var data: ByteArray? = null` while every other
   benchmark used `lateinit var data: ByteArray`, so `reader.readValue<SimpleDatasClass>(data)`
   was resolving against a nullable and carrying an extra null check that the avro4k and Apache
   `simple` harnesses did not. Normalised to `lateinit var` so all nine classes are identical
   in this respect. Almost certainly noise-level, but it was a free asymmetry to remove.
2. **`ReflectData.get()` is a JVM-wide singleton and `ApacheAvroReflect*Benchmark.setup()`
   mutates it** (`addLogicalTypeConversion`) on every `@Setup`, i.e. once per parameter value
   per fork. Conversions accumulate in a list that is scanned on every conversion lookup, so
   the Apache numbers can drift slightly across parameter values within a fork. With
   `@Param` this now happens 3x instead of 1x per fork. Worth guarding with a
   `@JvmStatic` one-shot init, or forcing `forks = 1` per param (JMH already forks per
   benchmark, so the blast radius is one class).
3. **`complex` at `clientCount = 200`** allocates ~540 KB of `picture` byte arrays per
   `Clients` instance (`randomBytes(4048)` for 2/3 of the clients). That is fine for a single
   `@State`, but if a future unit raises the top value it should check the read benchmark is
   not turning into a GC benchmark — `-prof gc` would settle it.
4. **Neither `read()` nor `write()` asserts correctness.** Nothing in the harness verifies that
   the three libraries actually produce/consume equivalent data at each parameter value. A
   cheap `@Setup(Level.Trial)` round-trip assertion would catch a silent divergence (e.g. a
   schema mismatch at `clientCount = 1` where some union branches may not be exercised).
5. **The `main` benchmark configuration reports `text`.** For size-scaling curves a
   machine-readable `json` or `csv` report would be far easier to chart. Deferred to whichever
   unit owns reporting.
6. The `@Param` value sets are the natural knob for a future "quick" profile — e.g. a
   `register("smoke") { param("clientCount", "1") ... }` configuration — if 25 minutes per full
   run becomes painful.
