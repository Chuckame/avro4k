**Outcome:** done

## What changed

Two files, both inside the unit's scope. Nothing under `benchmark/src/main/kotlin/**`,
`core/` or any other module was touched.

### `benchmark/build.gradle.kts` — the `benchmarkAlloc` task

A `JavaExec` task that runs the kotlinx-benchmark uber-jar through JMH's GC profiler.

```
./gradlew :benchmark:benchmarkAlloc -Pbench=<regex> -Pparams='<name>=<values>;<name>=<values>'
```

| property            | default  | maps to                                       |
| ------------------- | -------- | --------------------------------------------- |
| `-Pbench`           | `Avro4k` | JMH trailing positional benchmark-name regex   |
| `-Pparams`          | *(none)* | one `-p` per `;`-separated entry               |
| `-PallocForks`      | `1`      | `-f`                                           |
| `-PallocWarmups`    | `2`      | `-wi`                                          |
| `-PallocIterations` | `3`      | `-i`                                           |
| `-PallocTime`       | `1s`     | `-w` and `-r`                                  |
| `-PallocJmhArgs`    | *(none)* | extra raw JMH args, space-separated            |

Key implementation points, in the order they bit:

1. **The jar task is `:benchmark:mainBenchmarkJar`** (type `org.gradle.jvm.tasks.Jar`,
   registered by `kotlinx/benchmark/gradle/JvmTasksKt` as `"$target" + "BenchmarkJar"`).
   Its `archiveFile` provider is used directly as the `classpath`, which is both the task
   dependency and the exact jar path — strictly better than globbing `*-JMH.jar`, since the
   filename embeds the project version (`benchmark-main-jmh-local-SNAPSHOT-JMH.jar` here).
   The README still tells humans to glob, because they do not have the provider.
2. **The registration must live inside `afterEvaluate { }`.** The kotlinx-benchmark plugin
   creates `mainBenchmarkJar` from *its own* `afterEvaluate` hook, so a top-level
   `tasks.named("mainBenchmarkJar")` fails configuration with
   `Task with name 'mainBenchmarkJar' not found in project ':benchmark'`. Because the plugin
   is applied in the `plugins { }` block its hook is registered first, so ours runs after it.
   This is the single thing most likely to be rediscovered the hard way.
3. `mainClass = "org.openjdk.jmh.Main"` rather than `-jar`: the uber-jar's manifest already
   points there, but `JavaExec` + explicit main class keeps the classpath declarative and lets
   the same jar launch the `ManualProfiling*` mains.
4. **Configuration cache**: the repo has `org.gradle.configuration-cache=true`. All the
   `-P` values are read through `providers.gradleProperty(...)` inside a
   `CommandLineArgumentProvider`, i.e. at *execution* time. Verified: the CC entry is stored on
   the first run and **reused** on subsequent runs even when `-Pbench`/`-Pparams` change, so
   changing the selection costs no reconfiguration.
5. **Output is teed**, not redirected. `standardOutput` is replaced inside `doFirst` with a
   stream that writes to both `System.out` and
   `build/reports/benchmarks/alloc/main-alloc.txt` (mirrors the existing
   `build/reports/benchmarks/main` convention). A `doLast` then re-echoes every
   `gc.alloc.rate.norm` line so the metric is the last thing on screen.
6. `outputs.upToDateWhen { false }` — a benchmark must never be skipped as up-to-date.

## What was measured

Real output, captured from `build/reports/benchmarks/alloc/main-alloc.txt`.

`./gradlew :benchmark:benchmarkAlloc -Pbench='Avro4kSimpleBenchmark.write' -Pparams='recordCount=1'`
— **7 s wall clock** end to end (1 benchmark × 1 param):

```
Benchmark                                       (recordCount)   Mode  Cnt        Score        Error   Units
Avro4kSimpleBenchmark.write                                 1  thrpt    3  4879798.474 ± 604470.633   ops/s
Avro4kSimpleBenchmark.write:gc.alloc.rate                   1  thrpt    3     1302.765 ±    160.631  MB/sec
Avro4kSimpleBenchmark.write:gc.alloc.rate.norm              1  thrpt    3      280.001 ±      0.001    B/op
Avro4kSimpleBenchmark.write:gc.count                        1  thrpt    3       26.000               counts
Avro4kSimpleBenchmark.write:gc.time                         1  thrpt    3       12.000                   ms
```

`./gradlew :benchmark:benchmarkAlloc -Pbench='complex.Avro4kBenchmark' -Pparams='clientCount=1'`
— **11 s wall clock** (2 benchmarks × 1 param):

```
Avro4kBenchmark.read:gc.alloc.rate.norm               1  thrpt    3    5896.023 ±     0.001    B/op
Avro4kBenchmark.write:gc.alloc.rate.norm              1  thrpt    3    1632.011 ±     0.001    B/op
```

Notes on the numbers themselves (these are *tooling-proving* runs on a busy laptop, **not** a
baseline — A4 owns the baseline):

- the `± 0.001` error on `gc.alloc.rate.norm` is the whole point: bytes/op is essentially
  noise-free at 2 warmup + 3 measurement iterations of 1 s, whereas throughput on the same run
  carries ±12 %. Short settings are legitimate for this metric and only for this metric.
- rule of thumb from these runs: **~5 s of JVM+harness overhead per benchmark method**, so
  cost ≈ `5s × (#benchmarks × #params)`. The full 48-benchmark matrix would be ~25 min, hence
  the mandatory `-Pbench`.
- `ManualProfilingRead` was smoke-tested from the uber-jar
  (`java -cp "$JMH_JAR" com.github.avrokotlin.benchmark.ManualProfilingRead`) and runs; it was
  killed after a few thousand iterations rather than run to completion.

## What was rejected, and why

- **A plain-JMH source set / hand-rolled JMH dependency.** Not needed: `java -jar <uber-jar>
  -lprof` lists `gc: GC profiling via standard MBeans` as *supported*, and `-prof gc` works
  against the plugin's jar as-is (proven above). The fallback would have duplicated the whole
  benchmark source set for nothing.
- **JMH's `-o <file>`.** It *redirects* human-readable output to the file, leaving the console
  silent for the whole run. Teeing `standardOutput` gives both a live run and a captured file.
- **Globbing `build/benchmarks/main/jars/*-JMH.jar` from the build script.** Works, but
  `mainBenchmarkJar.archiveFile` is exact, lazy, and carries the task dependency for free.
  Globbing survives only in the README, for humans invoking `java` directly.
- **`-rf text -rff <file>` for a machine-readable table.** The teed log already ends with the
  full result table including the `gc.alloc.rate.norm` rows; a second file would just be
  another thing to keep in sync. Reconsider if A4 wants to diff runs programmatically.
- **Defaulting `-Pparams` to a single value.** Tempting for speed, but silently measuring one
  `@Param` while the header says otherwise is how wrong baselines happen. Default is the full
  `@Param` matrix of whatever `-Pbench` selects; the README tells you to narrow it.
- **An `application`-plugin `run` task for the `ManualProfiling*` mains.** `benchmark/` does
  not apply the `application` plugin, and the uber-jar already contains both classes
  (`com/github/avrokotlin/benchmark/ManualProfilingRead.class` is in it), so a documented
  `java -cp` line was cheaper than a new plugin + task.

## Follow-ups

- **async-profiler is not installed on this machine** and `async` is listed as unsupported by
  `-lprof`; `perf`/`dtrace` need `sudo`. The README documents the `-agentpath:` /
  `DYLD_LIBRARY_PATH` install-and-run recipe but it is **unverified end to end** — nobody has
  produced an actual flame graph yet. First person to `brew install async-profiler` should
  confirm the command line and fix the README if the macOS release layout differs.
- `-PallocJmhArgs='-prof async:...'` is documented as the "once installed" path; also
  unverified.
- `benchmark/` does not apply spotless (only `core`, `kotlin-generator`, `gradle-plugin` and
  the `library-module-conventions` plugin do), so `./gradlew spotlessApply` does not format
  `benchmark/build.gradle.kts`. Formatting there is by hand; keep it consistent manually.
- A4 should capture the baseline with a longer `-PallocIterations`/`-PallocTime` only if it
  also wants trustworthy throughput from the same run; for bytes/op the defaults suffice.
