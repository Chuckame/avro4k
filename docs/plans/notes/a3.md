### `@Param` sets, and why those values

- **`depth` = 1/3/8.** Each level is a record with exactly one field, so the payload stays ~1 byte
  at every depth and the slope over `depth` *is* the per-record overhead, with the data cost
  removed by construction. 1 is the floor (a single structure), 3 is the shallow-but-not-trivial
  case, 8 is deep enough that the slope is unambiguous. Four values would have bought nothing: the
  curve turned out to be exactly linear, so two points already determine it and the third
  cross-checks it.
- **`size` = 10/1000/100000** — as specified. 100k is the one that could have blown up; it did not:
  `readRecords` at 100k still runs at ~199 ops/s, i.e. ~600 measured operations per 3s iteration,
  which is plenty of samples. `writeRecords` at 100k is ~253 ops/s. For comparison the existing
  `lists` workload runs at ~57 ops/s at its heaviest point, so this family is *lighter* than the
  slowest thing already in the suite. Setup allocates ~100k small records once per trial, which is
  a few MB — not a concern.
- **`shapeCount` = 10/1000** (not 100k). Two points are enough to separate the fixed cost from the
  per-value cost, and this family is duplicated (polymorphic + monomorphic control), so a third
  size would have cost 4 more combinations for no new information.
- **`fieldOrder` = matching/swapped/reversed.** Deliberately a 3-value ladder rather than a
  2-value on/off: `swapped` moves only the last two of eight fields, `reversed` moves all eight.
  The hypothesis under test is that they cost *the same*, because `ReorderingCompositeEncoder`
  buffers every field as soon as it is used at all. Confirmed below.
- **No parameter on the string and schema families.** The string field count is baked into the
  descriptor and cannot be parameterised without code generation; the schema family has a single
  fixed descriptor (the depth-8 record, so inference visits 8 record types).

### Runtime budget

`MICRO_WARMUP_ITERATIONS = 5`, `MICRO_MEASUREMENT_ITERATIONS = 5`, both at 1s, vs the end-to-end
suite's 5x1s + 5x**3s**. Measurement time is cut to a third; **warmup was deliberately not cut**.
The first draft used 3 warmup iterations and the cheapest families' throughput swung by an order of
magnitude between iterations (`FieldOrderMicroBenchmark.write` reported 281k ops/s for `matching`
and 1.74M ops/s for `reversed`, with error bars larger than the scores), while their bytes/op stayed
stable to the milli-byte. Five warmup iterations fixed it (see the figures below).

Measured overhead, from the run below: 39 combinations in 4m10s at 2+3 iterations of 1s
=> ~6.4s of JVM/harness overhead per combination. So:

- `./gradlew :benchmark:microBenchmark` (1 fork, the annotated 5+5 iterations):
  39 x (10s + 6.4s) ~ **10-11 minutes**.
- `./gradlew :benchmark:benchmarkAlloc -Pbench='benchmark\.micro'` (2+3 iterations):
  **4m10s, measured**.
- Narrowed to one family, e.g. `-Pbench='micro\.FieldOrder'`: ~40s.

Running the uber-jar directly uses JMH's own default of 5 forks, so the same family costs 5x more
there; that is the right setting when a *throughput* number has to be trusted.

## What was measured

One `./gradlew :benchmark:benchmarkAlloc -Pbench='benchmark\.micro'` run (1 fork, 2 warmup +
3 measurement iterations of 1s, 4m10s wall) covering all 39 combinations, plus one 5-fork jar run
of the `FieldOrder` family. **These are instrument-proving figures on a laptop, not a baseline**
(A4 owns the baseline). The `± 0.001`-class error on every bytes/op figure is the point: that
metric is essentially noise-free even at these settings.

### Nested records — per-structure cost

| depth | read B/op | write B/op | read ops/s | write ops/s |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 192 | ~0 | 29.8M | 30.7M |
| 3 | 320 | 232 | 12.7M | 10.0M |
| 8 | 640 | 392 | 4.93M | 4.56M |

Exactly linear: **+64 B/op per record on decode** ((320-192)/2 = (640-320)/5 = 64) and
**+32 B/op per record on encode** ((392-232)/5 = 32). Extrapolating decode to depth 0 gives a
~128 B fixed cost, which is `decodeFromByteArray`'s `Buffer` + source.

**Caveat on `write` at depth 1: it reports ~0 B/op.** Escape analysis eliminates the whole
encoder for a single-record encode. That point is therefore *not* a usable baseline - it measures
what the JIT can delete, not what avro4k allocates. Use depth 3 and 8 for the slope.

### Collections

| size | readLongs | writeLongs | readRecords | writeRecords |
| ---: | ---: | ---: | ---: | ---: |
| 10 | 616 B | 168 B | 1096 B | 520 B |
| 1000 | 28352 B | 232 B | 76368 B | 32232 B |
| 100000 | 2800382 B | 243 B | 7600403 B | 3200259 B |

- **`writeLongs` is flat** (168 -> 243 B/op over a 10000x size range): encoding an array of longs
  allocates essentially nothing per element, so the collection-serializer wrapper plus the array
  block handling is a **fixed ~170-240 B per collection** and is not the problem on the write side.
- `readLongs` is 28 B/element (boxed `Long` + list slot + growth).
- The record-vs-long delta is the per-element structure cost, and it matches the nested family
  exactly: `readRecords - readLongs` = 48 B/element (48016/1000, 4800021/100000);
  `writeRecords - writeLongs` = **32 B/element**, the same 32 B/record as the nested `write` slope.
- Throughput at 100k: readLongs 486, writeLongs 630, readRecords 199, writeRecords 253 ops/s.

### String field storms (12 fields x 16 chars)

| | B/op | ops/s |
| --- | ---: | ---: |
| `readNonNull` | 1480 | 2.84M |
| `readNullable` | 1480 | 1.81M |
| `writeNonNull` | 520 | 3.52M |
| `writeNullable` | 552 | 2.43M |

**The union branch resolution is a CPU cost, not an allocation cost.** Nullability costs
+32 B/op *in total* across 12 fields on write (2.7 B/field) and **0 B/op** on read, but -31% on
write throughput and -36% on read throughput. This is the one family that `gc.alloc.rate.norm`
alone would *not* police - it has to be read on throughput.

### Sealed-interface storms

| shapeCount | readPoly | readConcrete | writePoly | writeConcrete |
| ---: | ---: | ---: | ---: | ---: |
| 10 | 1752 B | 1656 B | 1120 B | 1080 B |
| 1000 | 188392 B | 156392 B | 112296 B | 80256 B |

At 1000 elements the polymorphic overhead is **exactly 32 B per polymorphic value** on both sides
(188392-156392 = 32000; 112296-80256 = 32040). That is one `Pair` per value, precisely the suspect
described in the brief. Throughput cost is small (~4% read, ~0 write at 1000), so this one is
allocation-visible and throughput-invisible - the mirror image of the string family.

At `shapeCount = 10` the delta collapses to ~4-10 B/value: escape analysis removes most of the
`Pair`s when the loop is short enough to inline. **Read this family at 1000, not at 10.**

### Field order mismatch — `ReorderingCompositeEncoder`

| fieldOrder | write B/op | write ops/s (5 forks) | read B/op | read ops/s (5 forks) |
| --- | ---: | ---: | ---: | ---: |
| matching | 136 | 9.09M ± 0.08M | 248 | 6.81M ± 0.09M |
| swapped | 680 | 5.35M ± 0.15M | 248 | 6.80M ± 0.09M |
| reversed | 680 | 5.29M ± 0.08M | 248 | 8.22M ± 0.07M |

**+544 B/op and -41% throughput** for an 8-field record, and `swapped` (two fields moved) costs the
*same* as `reversed` (all eight moved) - the predicted cliff. 544/8 = **68 B per field**, i.e. a
`BufferedCall` holder plus a capturing lambda per field plus the 8-slot array.

Read is unaffected (248 B/op at every order), as expected: decoding is driven by `DecodingStep`s
already ordered by the writer schema, so no buffering layer exists on that side. The `reversed`
read throughput being 20% *higher* than `matching` is cross-fork JIT/layout noise, not a real
effect - there is no code path that could make it faster.

#### How the reordering path was confirmed (not assumed)

Two independent ways, because `RecordResolver` is `internal` to `core` and therefore invisible to
the benchmark module:

1. **Direct reflection**, from a throwaway Java program compiled against the JMH uber-jar
   (kept out of the repo, in the session scratchpad). It reads the private `Avro.recordResolver`
   field, calls `RecordResolver.resolveFields(writerSchema, descriptor)` and prints the
   `SerializationWorkflow.encoding` implementation class for each of the three schemas this
   benchmark builds:
   ```
   matching (abcdefgh) -> EncodingWorkflow = ExactMatch    ; decodingSteps[0] = DeserializeWriterField
   swapped  (abcdefhg) -> EncodingWorkflow = NonContiguous ; decodingSteps[0] = DeserializeWriterField
   reversed (hgfedcba) -> EncodingWorkflow = NonContiguous ; decodingSteps[0] = DeserializeWriterField
   ```
   `EncodingWorkflow.NonContiguous` is the *only* branch of `RecordDirectEncoder` that constructs a
   `ReorderingCompositeEncoder`, so this is conclusive.
   Gotcha if this has to be redone: `RecordResolver` has several methods whose JVM name starts with
   `resolveFields` (Kotlin emits `resolveFields$lambda$1`), so select on `getParameterCount() == 2`.
2. **The allocation signature itself**: 544 extra bytes appearing on `swapped` and `reversed` and
   on neither `matching` nor any read, scaling as 68 B x 8 fields, is the buffering allocation and
   nothing else looks like that.

### Schema inference

| | B/op | ops/s |
| --- | ---: | ---: |
| `warmCacheHit` | ~0 (1e-5) | 268M |
| `coldInference` | 13344 | 519k |
| `newAvroInstance` | 2728 | 2.68M |

A warm cache hit is **allocation-free** and costs ~4ns - the weak-keyed map lookup is not worth
optimising. Cold inference of a depth-8 record costs ~13.3 kB and ~1.93 us.

## How the cold-schema case was handled

The schema cache is per-`Avro`-instance, so on the shared `Avro.Default` the second invocation is
already a hit and "cold" is unmeasurable. Of the two honest options:

- **Chosen: a fresh `Avro { }` per invocation, in `Mode.Throughput`, with an explicit control
  benchmark (`newAvroInstance`) that constructs the instance and does nothing else.** The
  construction is *not* negligible - it is **2728 of the 13344 B/op (20%)** and
  1/2.68M = 0.37 us of the 1.93 us (19%). So `coldInference` on its own is **not** the inference
  cost and must never be quoted as one; `coldInference - newAvroInstance` is:
  **~10.6 kB/op and ~1.55 us** of actual inference. The KDoc on the class says this, and the two
  methods are adjacent in the output so the subtraction is hard to forget.
- **Rejected: `Mode.SingleShotTime` with `@Setup(Level.Invocation)`.** It would have measured a
  single cold call honestly, but at ~2 us per op JMH's own invocation-level timing overhead is of
  the same order as the measurement, and `Level.Invocation` carries a standing JMH warning for
  exactly this range. It also gives no bytes/op worth trusting, which is the primary metric here.

So: cold inference *is* isolated, but only as a difference of two numbers, and that is stated in
the code rather than hidden.

## What was rejected, and why

- **Parameterising the string-field count.** `@Param` cannot change a `SerialDescriptor`; varying
  the field count needs either N hand-written records or code generation. Fixed at 12 fields, with
  the nullable/non-nullable pair carrying the attribution instead.
- **A `List<String?>` instead of a field storm** to make the count parameterisable. Rejected: a
  list element goes through the array encoder, not the record field encoder, so it would no longer
  isolate *field* union resolution and would add the collection cost the brief wants kept separate.
- **Null values in `NullableStringStorm`.** A null short-circuits on the first
  `trySelectTypeNameFromUnion(NULL)` and would measure the null branch instead of the string one.
  All 12 values are non-null on purpose. (A null-heavy variant is a reasonable follow-up.)
- **A `when (depth)` inside the measured nested methods.** The serializer is resolved once in
  `@Setup` and stored erased as `KSerializer<Any>`, so the measured method has a single call site.
  JMH forks per parameter combination, so that call site stays monomorphic within a fork.
- **Sharing the `internal/` models** (`SimpleDataClass` etc.). They model realistic payloads, which
  is the opposite of what an attribution instrument needs, and `internal/` is out of scope for
  edits anyway. The micro models are self-contained and seeded from a constant so two runs encode
  byte-identical payloads.
- **An abstract `@State` base class per family**, mirroring the end-to-end suite. There is only one
  implementation per family, so the indirection would buy nothing (and the brief says so).
- **`kotlinx.io.Buffer` + `clear()` for the write sinks.** Same reasoning as A1: a hoisted
  `nullOutputStream().asSink().buffered()` flushed once per op, so the measured method contains
  encoding only and the buffer cannot grow. `Avro.encodeToSink` does not flush.
- **Touching `benchmark/README.md`** to document the `micro` configuration - A4 owns that file.
  Someone should add a paragraph there.

## Follow-ups

1. **The suspect that could not be isolated from the outside: `RecordResolver.resolveFields`
   being re-run per record instance, separately from the encoder/decoder object allocated per
   structure.** Both happen inside the same call (`AbstractAvroDirectDecoder.beginStructure` ->
   `RecordDirectDecoder(...)`, and `RecordDirectEncoder(...)` -> `resolveFields`), and the public
   API offers no seam between them. `NestedRecordMicroBenchmark` measures their **sum**:
   64 B/record decode, 32 B/record encode. Splitting the two needs an allocation profile
   (async-profiler `-e alloc`, still not installed on this machine per a2.md) or a temporary
   counter in `core/`. **If the perf program changes either one, this benchmark will move, but it
   will not say which one moved.** That is the single most important thing for the next session.
2. Same limitation, smaller stakes, for the collection family: the per-collection
   *collection-serializer wrapper* cannot be separated from the rest of the fixed per-collection
   cost. What the benchmark gives is the total fixed cost (~170-240 B/op on write) and the
   per-element cost, which is enough to police a regression but not to attribute one inside the
   fixed part.
3. **The union chain is only measured at its best case.** `encodeString` tries `STRING` first, so a
   `["null","string"]` field resolves on attempt 1 - the "up to 9 attempts" worst case needs a
   writer schema whose union has no STRING at all (e.g. encoding a `String` into `["null","double"]`),
   which is pathological. The realistic cost is measured; the pathological one is not.
4. Two escape-analysis floors to be aware of when reading results, both documented above:
   `NestedRecordMicroBenchmark.write` at `depth = 1` reports ~0 B/op, and
   `PolymorphicMicroBenchmark` at `shapeCount = 10` under-reports the per-value `Pair` by ~3x.
   If a future change makes these objects escape, those two points will jump for a reason that has
   nothing to do with the change's real cost.
5. `FieldOrderMicroBenchmark.read` shows a 20% throughput spread across `fieldOrder` values that
   cannot be real (the read path has no reordering layer). It is cross-fork noise; if it persists
   after the perf work, it is worth 5 minutes to confirm it is still noise.
6. No round-trip assertion anywhere in the micro suite (same gap as the end-to-end one, see a1.md
   follow-up 4). A `@Setup`-time `decode(encode(x)) == x` check per family would be cheap insurance
   against a model that silently stops exercising the path it names - particularly for
   `FieldOrderMicroBenchmark`, whose whole point is a schema built by hand.
7. `benchmark/` is not covered by spotless; these files were formatted by hand to match the
   existing ones.
