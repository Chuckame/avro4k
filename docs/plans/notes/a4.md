## Findings that change how later milestones are verified

1. **Apache `ReflectData` reads fail on `complex` and `simple`** with `Can not set final <T> field …`.
   **Confirmed pre-existing**: pristine `main` fails identically, so M0 did not cause it.
   > **Correction (A5).** The cause recorded here — Kotlin `val`s compiling to final fields — was
   > **wrong**. `Field.set` prints the field's modifiers in its message; a finality violation would
   > be `IllegalAccessException`, not `IllegalArgumentException`. The real cause is a type mismatch:
   > `ReflectData` needs the `java-class` schema hints to map a decoded value back to its field
   > (`GenericData$Array` → `Array<String>`, `Integer` → `Byte`). The counter-evidence was already in
   > this file: `lists` Apache read worked against an all-`val` model. A5 fixed all three failures. Consequence: no avro4k-vs-Apache *read* comparison exists for those two workloads. The write
   side and both sides of `lists` are unaffected. The plan's context table ("+15% read on `simple`,
   −7% on `complex`") is **not reproducible on this machine** — do not treat those as targets.
2. **Fixing DCE cost 8.9% of avro4k's apparent read throughput** (`simple` @ 25: 206,652 → 188,278
   ops/s, error bars ±1.7k/±1.2k). The old number was inflated by work the JIT could elide. Every
   pre-M0 avro4k read figure is overstated by roughly this much.
3. `complex.JacksonAvroBenchmark.read` still fails on the abstract `Partner` type — long-standing,
   documented before M0.
4. The previously published numbers were taken on a MacBook Air M2; this machine is an M2 Pro.

## Headline baseline

- avro4k **write** leads Apache by +71…79% on `complex` at every size, and leads on `simple` and
  `lists` too. The write path is in good shape.
- avro4k **read** allocates 5.7× what its write path does (`complex` @ 200: 1.74 MB vs 305 kB per
  op, ~8.6 kB per decoded client). Decode is where the allocation work is.
- avro4k's collection **write** path is already allocation-flat: 243 B/op at 100,000 longs, vs
  Apache 167 kB and Jackson 397 kB on the `lists` workload. The `lists` write throughput gap to
  Jackson is therefore **not** an allocation problem — look elsewhere (C3, block framing).
- Reordering is a cliff: +544 B/op and −41% write throughput, identical for one swapped field and a
  fully reversed record.

## What was rejected, and why

- Re-running the pre-M0 numbers for a like-for-like comparison: impossible in general, because the
  Apache read side does not run at all. The control run was narrowed to the one avro4k benchmark
  needed to quantify the DCE effect.

## Follow-ups

- The Apache-read failure is arguably worth fixing in the benchmark model (e.g. `@JvmField`, or
  mutable fields for the Apache variant only) so a read comparison exists again — but that changes
  the model all four libraries share, so it needs care to stay fair. Not in M0's scope.
- async-profiler is still not installed, so C1-vs-C2 attribution (see `a3.md`) remains unavailable.
