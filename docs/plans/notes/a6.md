# A6 — Apache fast-reader variants

**Outcome:** done
**Commit:** `36e5346`

## Headline

Apache's fast reader **does not apply to `ReflectData`, and cannot be made to.** It exists for
`GenericData` and `SpecificData` only, where — contrary to the unit brief's premise — it is **on by
default**. So the three `ApacheAvroReflect*` benchmarks get no fast variant, and the unit instead
measures the one Apache data model that does have the switch: plain `GenericData`, read-only, fast on
vs fast off, across all three workloads.

## Which data models support the fast reader, and the evidence

`org.apache.avro.io.FastReaderBuilder`, Avro 1.12.1, verbatim:

```java
public static boolean isSupportedData(GenericData data) {
  return data.getClass() == GenericData.class || data.getClass() == SpecificData.class;
}
```

and `org.apache.avro.generic.GenericData`:

```java
public static final String FAST_READER_PROP = "org.apache.avro.fastread";
private boolean fastReaderEnabled = "true".equalsIgnoreCase(System.getProperty(FAST_READER_PROP, "true"));

public boolean isFastReaderEnabled() {
  return fastReaderEnabled && FastReaderBuilder.isSupportedData(this);
}
```

Two consequences, both confirmed by running them against the jar this repo resolves
(`avro-1.12.1.jar`):

| Data model | `isSupportedData` | `isFastReaderEnabled()` | after `setFastReaderEnabled(true)` |
|---|---|---|---|
| `GenericData.get()` / `new GenericData()` | `true` | **`true`** | `true` |
| `SpecificData.get()` | `true` | **`true`** | `true` |
| `ReflectData.get()` | **`false`** | `false` | **still `false`** |
| any subclass of `GenericData` (incl. `DeclarationOrderReflectData`) | **`false`** | `false` | still `false` |

1. **It is an exact-class check, not `instanceof`.** `ReflectData extends SpecificData extends
   GenericData`, so it inherits the setter and the getter but can never satisfy the predicate.
   Calling `reflectData.setFastReaderEnabled(true)` writes a field that is then ignored:
   `isFastReaderEnabled()` still answers `false`, and `GenericDatumReader.read` keeps taking the
   `ResolvingDecoder` path. **This is exactly the silent-lie failure mode the unit brief warned
   about**, and it is why a `fastReader` `@Param` on the existing Apache benchmark classes was
   rejected (see below).
2. **The default is `true`, not `false`.** The brief's premise that Apache "leaves it disabled by
   default" is wrong for 1.12.1: the system property defaults to `"true"`, so for `GenericData` and
   `SpecificData` the fast reader is what a real user already gets. `fastReader=false` is the
   **opt-out** row, not the default one. That also means avro4k has been compared against
   `ReflectData`, which is both the slowest Apache data model *and* the one Apache excludes from its
   own fast path — the flattering comparison this unit set out to broaden is worse than it looked.

`SpecificData` is the other supported model, but it needs generated specific classes; that is A7's
unit, not this one.

## What changed

Three new read-only benchmark classes, one per workload:

- `benchmark/.../complex/ApacheAvroGenericFastReaderBenchmark.kt`
- `benchmark/.../simple/ApacheAvroGenericFastReaderSimpleBenchmark.kt`
- `benchmark/.../lists/ApacheAvroGenericFastReaderListsBenchmark.kt`

each with `@Param("false", "true") @JvmField final var fastReader: Boolean` (a `Boolean` `@Param`
works: JMH's generated setter does `Boolean.valueOf(control.getParam("fastReader"))`), and a single
`@Benchmark fun read(): GenericRecord`. No write variants — the fast reader is a read-path feature.

`internal/apache/ApacheAvro.kt` grew the fast-reader section:

- `GENERIC_DATA_FAST` / `GENERIC_DATA_SLOW`, two *plain* `GenericData` instances built once.
- `genericDatumReader(schema, fastReader)` — builds the reader through
  `GenericData.createDatumReader`, the call a real user makes, after asserting both
  `FastReaderBuilder.isSupportedData(data)` and `data.isFastReaderEnabled() == fastReader`.
- `assertFastReaderInEffect(reader, bytes, fastReader)` — the real proof (below).
- an `init` block asserting `!isSupportedData(REFLECT_DATA)`, so an Avro upgrade that lifts the
  restriction fails loudly instead of leaving this note quietly stale.

`internal/WorkloadEquivalence.kt` gained `apacheGenericLibrary(...)`, wiring a fourth
`ComparedLibrary` (`apache-generic`) into all three workloads' gates.

`benchmark/build.gradle.kts` gained a `fastreader` benchmark configuration
(`include("ApacheAvroGenericFastReader")`) so the 16 new rows are runnable without the full matrix.

### How the flag is proven to have taken effect

Three layers, because `isFastReaderEnabled()` alone is not proof that the *reader* uses it:

1. `FastReaderBuilder.isSupportedData(data)` — catches the subclass trap at its source.
2. `data.isFastReaderEnabled() == fastReader` — catches a flag that silently refused to be set.
3. **The decisive one.** `GenericDatumReader` builds its fast reader lazily inside `read` and caches
   it in a private `fastDatumReader` field. `assertFastReaderInEffect` performs one throwaway read
   in `@Setup`, then reflects on that field:
   - `fastReader=true` → must be non-null and an `org.apache.avro.io.FastReaderBuilder$…` instance;
   - `fastReader=false` → must be `null`.

   Anything else throws in `@Setup`. Both branches are exercised on every trial, and they are
   mutually exclusive, so neither can pass vacuously.

Two instances rather than one mutated per `@Param` value, deliberately: `GenericDatumReader` caches
the fast reader it built on first use, so flipping a flag on a shared instance between trials would
leave already-built readers on the path they were born with. One instance per setting means the
setting cannot drift from what the reader does. (The A5 "one shared `ReflectData`" rule is not
violated: that rule exists because of the *static* `ReflectData.ACCESSOR_CACHE`; `GenericData` has no
field accessors and therefore no such cache, and nothing writes through these instances.)

### The equivalence gate (A5) still holds

`apache-generic` goes through the same `EquivalenceGate` as the other three libraries, with both
readers proven in one entry:

- **schema**: avro4k's canonical schema, *unchanged and unexempted* — generic reading derives nothing
  from a class, so there is nothing to diverge. Zero schema exemptions.
- **write**: the record the **slow** reader decoded, re-encoded with `GenericDatumWriter`.
- **read/re-encode**: the record the **fast** reader decoded, re-encoded the same way.
- plus an explicit assertion that the fast and slow readers decode avro4k's bytes to the **same
  datum**. A fast reader that is merely fast at producing the wrong answer is the failure this unit
  had to rule out, and byte identity alone would not catch a difference the writer happens to
  normalise away.

One new `ByteExemption`, on `apache-generic/complex` only: `GenericData.newMap` returns a
`java.util.HashMap`, so a generically decoded map comes back in hash order. Verified to be real, not
precautionary — removing the exemption fails the gate at byte 282 of the 48,771-byte `complex`
encoding. The `ReflectData` side fixes this by overriding `newMap`, which is *not* available here:
any subclass of `GenericData` loses the fast reader, which is the whole point of the variant. The
exemption downgrades to decoded-datum equality exactly as the existing `jackson/complex` one does,
and `simple`/`lists` have no map and stay under strict byte identity.

## What was measured

Machine: the A4/A5 machine (Apple M2 Pro, macOS 26.6.2, OpenJDK 21.0.11 JBR, Apache Avro 1.12.1).
Run: `./gradlew :benchmark:fastreaderBenchmark`, the classes' own 5×1s warmup / 5×3s measurement,
`-f 1`. Indicative, not a baseline — A8 re-captures that.

| Workload | Parameter | `fastReader=false` (ops/s) | `fastReader=true` (ops/s) | Speed-up |
|---|---|---:|---:|---:|
| `complex` | `clientCount=1`   | 333,244 ± 279,523 | 748,731 ± 92,326 | **2.25x** |
| `complex` | `clientCount=15`  | 29,071 ± 2,441 | 56,454 ± 4,209 | **1.94x** |
| `complex` | `clientCount=200` | 2,155 ± 67 | 4,406 ± 380 | **2.04x** |
| `simple` | `recordCount=1`   | 4,602,548 ± 402,218 | 8,370,627 ± 204,792 | **1.82x** |
| `simple` | `recordCount=25`  | 232,321 ± 3,090 | 300,165 ± 84,872 | **1.29x** |
| `simple` | `recordCount=500` | 12,180 ± 531 | 13,670 ± 533 | **1.12x** |
| `lists` | `entryCount=100`   | 4,915 ± 145 | 12,404 ± 377 | **2.52x** |
| `lists` | `entryCount=10000` | 49.7 ± 1.4 | 130.2 ± 6.0 | **2.62x** |

The like-for-like headline, `complex` @ `clientCount=15` (the class default, and the row with the
tightest error bars of the three): **29,071 -> 56,454 ops/s, a 1.94x speed-up from one boolean.**

Two things worth carrying forward:

- **The effect is largest where the record structure dominates and smallest where raw bytes do.**
  `lists` (2.5-2.6x) is nothing but nested records and longs, which is exactly the per-datum schema
  walking the fast reader compiles away. `simple` at `recordCount=500` (1.12x) is dominated by
  copying a 50-byte `bytes` field and a 25-char string per record, which the fast reader does not
  change. So "about 2x" is a fair summary for record-shaped payloads, and an overstatement for
  byte-heavy ones.
- The `complex` @ `clientCount=1` `false` row has a very wide interval (± 279,523 on 333,244): one
  of its five iterations came in at 228k against a 371-397k spread. Its 2.25x should be read as
  "consistent with the other two rows", not as a precise figure.

All 16 rows produced numbers, `BUILD SUCCESSFUL in 5m 36s`. `<failure>` occurrences in the run
output: **0**. Exceptions / `AssertionError` / kotlinx-benchmark `Failure:` lines: **0**.
`Success:` lines: **16** — i.e. every combination, none dropped. (Note: `<failure>` is emitted only by
kotlinx-benchmark's IntelliJ XML log format, which a plain Gradle run does not use; the marker that
actually appears per row is `Success:` / `Failure:`, so both were grepped.)

### Reading these numbers

They are **not** comparable to the `ApacheAvroReflect*` or avro4k rows, and the class KDoc says so:
generic decoding produces `GenericRecord`s and `Utf8`s, not model objects, so it does strictly less
work than any of the mapped readers. The number this unit exists for is the fast-on / fast-off ratio
*within* each class, which is a clean like-for-like: same data model, same schema, same bytes, same
reader construction path, one boolean apart.

### Matrix size

| Suite | Before A6 | After A6 |
|---|---:|---:|
| End-to-end combinations | 48 | **64** |
| Micro-benchmark combinations | 39 | 39 |

The 16 new rows are 3 classes × 1 method (`read`) × 2 `fastReader` values × the workload's own
parameter count (3 `complex`, 3 `simple`, 2 `lists`). At the suites' fixed 20 s of warmup +
measurement per combination plus fork startup, the end-to-end suite goes from roughly 25 min to
**roughly 33 min** (+~8 min). The gate itself also got marginally heavier — two extra decodes and two
extra encodes per trial — which is noise against 20 s.

The `fastreader` Gradle configuration runs just these 16 rows in **5 min 36 s** (measured).

## What was rejected, and why

- **A `fastReader` `@Param` on the existing `ApacheAvroReflect*` classes** — the brief's preferred
  design. It cannot be made honest: `setFastReaderEnabled(true)` on a `ReflectData` is a no-op, so
  the `true` rows would be byte-for-byte the same slow path under a different label. Layer 3 of the
  proof above would fail them in `@Setup` every single time. Separate classes for the data model that
  actually has the switch is the only shape where the label matches the work.
- **Subclassing `GenericData` to override `newMap`** (the fix the `ReflectData` side uses for map
  ordering). `isSupportedData` is an exact-class check, so the subclass silently loses the fast
  reader — turning the whole variant into the thing this unit was written to prevent. A declared
  byte exemption is the honest trade.
- **Registering `TimeConversions` on the generic data models.** A stock `new GenericData()` has no
  conversions, so `date` and `timestamp-millis` come back as the `int` and `long` they are on the
  wire. Registering them would be a configuration a default generic user does not have, and would
  move the measured work; A5's rule about not rigging the comparison applies in both directions.
- **Adding a generic *write* row.** The fast reader is read-only, as the brief says, and a generic
  write row would be a different unit's comparison (`GenericDatumWriter` from a hand-built
  `GenericRecord` is not what any of the other rows do).
- **Setting `-Dorg.apache.avro.fastread` as a JVM arg** instead of per-instance. It is read once into
  a field at `GenericData` construction, so it is a process-wide default, not a per-row switch — and
  it would silently change every other Apache row in the suite.
- **A `SpecificData` fast-reader row.** Supported, but it needs generated specific classes. That is
  A7.

## Follow-ups

- **A7 (`SpecificData`) gets the fast reader for free** — `isSupportedData` accepts
  `SpecificData.class` exactly, and the flag is on by default. But the same exact-class trap applies:
  a `SpecificData` *subclass* (which is the usual way to configure one) loses it silently.
  `ApacheAvro.assertFastReaderInEffect` is reusable as-is for that unit.
- **A8 must re-capture the baseline** with 64 combinations, not 48.
- **`benchmark/README.md`** (orchestrator-owned) should say that the Apache reflect rows are measured
  *without* the fast reader because Apache excludes `ReflectData` from it — otherwise the obvious
  reader question ("why isn't Apache using its fast reader?") has no answer in the repo.
- The `init` check in `ApacheAvro` will fail the build if a future Avro relaxes `isSupportedData`.
  That is intentional; the fix at that point is to add the `fastReader` `@Param` to the reflect
  classes and delete the check.
