# A7 — Apache SpecificData variant

**Outcome:** done
**Commit:** `4182c4f`

## Headline

Against `SpecificData` with generated `SpecificRecord` classes — the fastest thing Apache offers —
**avro4k is behind on read in every workload, and behind on write in two of three.** The suite had
been comparing avro4k against `ReflectData`, the slowest Apache data model, and (since A6) against
`GenericData`, which decodes to `GenericRecord`/`Utf8` and so is not directly comparable to anything.
`apache-specific` is the first Apache row that is a true like-for-like: it decodes into real model
objects with real field types, from avro4k's own canonical schema, byte-identical on the wire.

`complex` @ `clientCount=15`: avro4k reads **24,715 ops/s** where `SpecificData` reads **47,699** —
1.93x. On write avro4k is 36,757 against 42,992, 1.17x behind. The `ReflectData` row that used to
stand in for "Apache" is 20,389 / 21,093, i.e. roughly half of what an Apache user who cares about
performance actually runs.

## What changed

### The generated classes, and how they are produced

```
Avro.schema<T>()  --(:benchmark:regenerateAvroSchemas)-->  benchmark/src/main/avro/*.avsc
                  --(:benchmark:generateSpecificRecords)-->  build/generated/sources/avro/main/java
```

- **`benchmark/src/main/avro/{Clients,SimpleDatasClass,ListWrapperDatasClass}.avsc`** — checked in,
  **derived, never hand-edited**. Each one is `Avro.schema<T>().toString(true)` with exactly one
  mechanical edit: the namespace `com.github.avrokotlin.benchmark.internal` is rewritten to
  `…internal.specific`, because the generated class names are avro4k's own (`Clients`, `Client`,
  `GoodPartner`, …) and would otherwise collide with the model under test.
- **`internal/specific/CanonicalSchemas.kt`** — the `main` behind `regenerateAvroSchemas`, and the
  file that states the "derived, not source" rule.
- **`:benchmark:generateSpecificRecords`** — calls `SpecificCompiler` directly, from the build
  script's own classpath, with `StringType.String`. Its output directory is wiped first, so a
  removed or renamed record cannot keep compiling.
- **`internal/specific/SpecificModels.kt`** — `toSpecific()` converters, called once from `@Setup`.

They are checked in rather than generated from avro4k on every build because generating them
requires compiling the Kotlin model, which lives in the **same source set** as the generated Java —
wiring that into the compile chain is a cycle. A clean `git clone` therefore needs no bootstrap step.

### How drift is caught

Not by discipline, and not by the regeneration task. `apache-specific` is registered as a
`ComparedLibrary` in all three workloads, and the schema it presents to the A5 gate is the generated
class' **`SCHEMA$`** — a string literal baked into the generated Java at codegen time. So if an
`.avsc` (or the generated code) falls behind what avro4k now produces, every `apache-specific` trial
throws in `@Setup` naming the exact differing path.

Verified, not assumed. Swapping two fields in `SimpleDatasClass.avsc` and rebuilding:

```
java.lang.AssertionError: [simple/apache-specific] schema is not equivalent to the canonical avro4k schema.
1 undeclared difference(s):
  - SimpleDatasClass.data[]: field names/order [bool, byte, short, int, long, float, double, string, bytes]
    != [bool, short, byte, int, long, float, double, string, bytes] (same fields, different order)
```

A type change is caught even earlier — changing `short` from `int` to `long` fails
`:benchmark:compileKotlin`, because the converter no longer type-checks against the generated
constructor. Both layers were exercised.

### What codegen could not express: nothing

The whole canonical schema round-trips through `.avsc` + `SpecificCompiler`, including the three
things the brief flagged as likely friction:

| Feared friction point | What actually happens |
|---|---|
| avro4k's `char` logical type on `int` | Unknown to Avro, so the field is generated as `Integer` — but `logicalType: char` survives in `SCHEMA$` as a plain JSON property, so the gate compares it and it matches |
| `date` / `timestamp-millis` | Generated as `java.time.LocalDate` / `java.time.Instant`; the compiler puts the two `TimeConversions` into each class' `MODEL$` |
| the sealed `Partner` hierarchy | `["null", BadPartner, GoodPartner, Stranger]` generates as an `Object` field — the compiler's normal shape for a multi-branch union. Branch order comes from the schema, so it is avro4k's |

**Nothing in avro4k's model was weakened.** `Byte`/`Short`, `BigDecimal`-as-string, `ByteArray`,
`Array<String>`, `LongArray`, `List<String?>`, the map — all intact.

Four avro4k types land as different Java types in the generated classes, none of them a choice this
unit made: `ByteArray`→`ByteBuffer`, `Char?`→`Integer`, `BigDecimal?`→`String`, `Partner?`→`Object`.

### Proving the configuration is what is claimed

`ApacheAvro.specificDatumWriter/specificDatumReader` build the **one-argument constructors a real
user calls** (`new SpecificDatumWriter<>(Clients.class)` / `new SpecificDatumReader<>(Clients.class)`).
Both resolve `SpecificData.getForClass(c)`, which is the generated class' own `MODEL$` — a plain
`new SpecificData()` carrying the conversions the compiler saw. Nothing is tuned, cached or shared
beyond that.

Three layers of proof, the same shape A6 used:

1. `FastReaderBuilder.isSupportedData(MODEL$)` — the exact-class trap. If a future Avro generates a
   `SpecificData` *subclass* into `MODEL$`, the fast reader is silently lost and this fails loudly.
2. `MODEL$.isFastReaderEnabled()` — the flag is on by default in 1.12.1; if something turned it off
   this is no longer the configuration a real user gets.
3. **The decisive one**: `ApacheAvro.assertFastReaderInEffect(reader, data, fastReader = true)`,
   reused unchanged from A6. It performs one throwaway read in `@Setup` and then reflects on
   `GenericDatumReader.fastDatumReader`, requiring it to be non-null and an
   `org.apache.avro.io.FastReaderBuilder$…`. `SpecificDatumReader` extends `GenericDatumReader`, and
   `GenericDatumReader.read` is where the fast reader is built and cached, so this is a check on the
   reader that is actually measured. All 16 rows pass it, so the fast reader is provably in effect.

There is deliberately **no `fastReader` `@Param`** here: turning it off would mean mutating the
generated class' JVM-wide `MODEL$`, which is exactly the global-state mutation A5 removed. A6 already
owns the fast-on/fast-off ratio.

### Gate result for `apache-specific`

| Workload | Schema | Write bytes | Read/re-encode bytes |
|---|---|---|---|
| `complex` | ✅ equivalent, **zero schema exemptions** | ✅ byte-identical | ⚠️ one `ByteExemption` (map order) |
| `simple` | ✅ zero exemptions | ✅ byte-identical | ✅ byte-identical |
| `lists` | ✅ zero exemptions | ✅ byte-identical | ✅ byte-identical |

**The one exemption**, `apache-specific/complex`: a generated record decodes its map field through
`GenericData.newMap`, which returns a `java.util.HashMap`, so `Client.map`'s ten entries come back in
hash order. The `ReflectData` side fixes this by overriding `newMap`; that is not available here for
the same reason as in A6 — the generated classes carry their own `MODEL$`, and
`FastReaderBuilder.isSupportedData` is an exact-class check, so a `SpecificData` subclass would
silently lose the fast reader that is most of the point of this variant.

Proven load-bearing, not precautionary. Removing it fails the gate:

```
[complex/apache-specific read/re-encode] encoding differs from avro4k's for the same logical data.
  first difference at byte 282: 0x4e != 0x30
```

Worth noting precisely how narrow it is: the **write** half is byte-identical even with the exemption
declared (the gate short-circuits on `contentEquals`), because `toSpecific()` hands the record a
`LinkedHashMap`. Only the *decode* side loses the order. `simple` and `lists` have no map and stay
under strict byte identity.

`avro.java.string` is the only other schema property the generated classes add, and it is one of the
four object-mapping hints the A5 comparison already ignores by design — it does not reach the wire.

## What was measured

Machine: the A4/A5/A6 machine (Apple M2 Pro, macOS 26.6.2, OpenJDK 21.0.11 JBR, Apache Avro 1.12.1).
`-f 1`, the classes' own 5×1s warmup / 5×3s measurement. Indicative, not a baseline — A8 re-captures
that.

- **avro4k's write path is competitive**, and on `simple` it is the fastest thing in the suite.

## What was rejected, and why

- **Handing `SpecificData` anything a normal user would not have.** No shared/tuned data model, no
  identity cache, no pre-warmed reader: the writer and reader are the one-argument constructors, and
  the data model is the generated `MODEL$`. Same rule that made A5 reject the +69% Apache-write
  `getCustomEncoding` cache. It is not needed — `SpecificData` wins on its own.
- **An Avro Gradle plugin** (e.g. `davidmc24/gradle-avro-plugin`). A whole plugin, with its own
  conventions and its own version to track, for a single `SpecificCompiler` invocation. Calling the
  compiler API from a 20-line task is less machinery and leaves nothing implicit.
- **`avro-tools` as a `JavaExec` main class.** It is the documented CLI, but the published artifact
  is a ~70 MB shaded uber-jar, and `SpecificCompiler.main` in 1.12.1 compiles **protocols only**
  (verified by disassembly: it is two `new File(...)` and a `compileProtocol`) — the usage string
  mentioning `schema` belongs to `avro-tools`' `SpecificCompilerTool`, not to `avro-compiler`.
- **Checking in the generated Java.** Zero build machinery, but in review it is indistinguishable
  from hand-written code, and nothing stops someone editing it. The brief's "must not drift into
  being maintained by hand" rules it out.
- **Generating the `.avsc` on every build.** It would need avro4k's compiled Kotlin model, which is
  in the same source set as the generated Java it feeds — a dependency cycle. Checked in + a gate
  that fails loudly is the honest version.
- **A `fastReader` `@Param` on the specific classes.** Turning it off means mutating the generated
  class' JVM-wide `MODEL$` from `@Setup`, which is the global-state mutation A5 removed. A6 already
  measures that ratio on `GenericData`.
- **`StringType.CharSequence`** (the `SpecificCompiler` default). It would let Apache keep `Utf8`
  instead of building `String`s, which is *faster* — and would make the decoded model incomparable to
  avro4k's, which decodes into `String`. `-string` is the choice that costs Apache and buys
  like-for-like. Disclosed here so the number is not read as Apache's ceiling: a `CharSequence` user
  would read faster still.
- **Pinning `java-class: java.math.BigDecimal` into the `.avsc`** so the specific model would hold a
  `BigDecimal` like avro4k's does. It would have made the `balance` field like-for-like, but it means
  hand-editing a derived file, which is the thing this unit is not allowed to do. Disclosed instead
  (below).

## Known, disclosed asymmetries

- **`balance`.** avro4k stores a `BigDecimal` and `toString()`s it on every write; the generated
  class stores the already-stringified value, so `SpecificData`'s `complex` write does not pay that
  per record. One field out of twenty, `complex` only. It flatters Apache slightly on `complex`
  write, which is Apache's *weakest* margin (1.17x), so the headline is not the thing it affects.
- **`gender` decodes to `Integer`, not `Char`.** avro4k's `char` logical type is avro4k's own; Avro
  has no conversion for it, so the specific model keeps the code point. Same amount of wire work,
  one less object.
- Both are visible in `SpecificModels.kt`'s table rather than buried.

## Things a future session would otherwise rediscover the hard way

- **`SpecificCompiler.main` in avro-compiler 1.12.1 only compiles protocols.** The schema CLI lives
  in `avro-tools`. Use the API.
- **`new SpecificDatumWriter<>(Class)` and `new SpecificDatumReader<>(Class)` both go through
  `SpecificData.getForClass(c)`**, which reads the generated `MODEL$` reflectively. That is what
  carries the logical-type conversions: the generated classes here have **no** `getConversion(int)`
  override and no `customEncode`/`customDecode`, so conversions come from the data model alone.
  Building a reader from a hand-made `new SpecificData()` would decode `LocalDate`/`Instant` fields
  into `int`/`long` and fail on the union.
- **`MODEL$` is `new SpecificData()`** — exactly the class, so the fast reader applies. Any future
  compiler change that subclasses it would silently cost the fast reader;
  `assertSpecificFastReaderAvailable` fails loudly if that happens.
- **An unknown `logicalType` survives `Schema.parse` as a plain property.** That is why avro4k's
  `char` is still compared by the gate on the generated side.

## Follow-ups

- **A8 must re-capture the baseline** with **80** combinations, not 64, and the README's
  Apache-vs-avro4k narrative needs rewriting around `SpecificData`, not `ReflectData`: the honest
  summary is now "avro4k reads ~1.6-2.4x slower than Apache's fastest path, and writes between 1.35x
  slower and 1.2x faster depending on workload".
- **avro4k's read path is the target.** Against the fairest fast Apache comparator it loses in all
  three workloads, worst on `lists` (2.39x). That is the number for the optimisation units to move.
- `benchmark/README.md` (orchestrator-owned) should explain the four Apache rows and what each is
  for: `ReflectData` (POJOs, no fast reader, Apache's slowest), `GenericData` (fast-reader ratio,
  not comparable to the model rows), `SpecificData` (Apache's fastest, the real comparator).
- `:benchmark:regenerateAvroSchemas` must be run after any change to `Clients`, `SimpleDatasClass` or
  `ListWrapperDatasClass`. Forgetting fails every `apache-specific` row with the differing path, so
  it cannot be missed — but it is worth a line in the README.
