# B0 — multiplatform build conventions

**Outcome:** done, with three deviations from the plan text, all flagged below (one is a temporary
publication guard that B1 must delete, one moves kotest assertions out of `commonTest`)
**Commit:** the commit that adds this file (`git log -1 -- docs/plans/notes/b0.md`)

## What changed

- `buildSrc/build.gradle.kts`: adds the `org.jetbrains.kotlin.multiplatform` Gradle plugin at the
  existing `kotlinVersion` (2.3.21). No other version changed.
- New `buildSrc/src/main/kotlin/library-multiplatform-module-conventions.gradle.kts`, started from
  the `kmp` branch's version:
  - `kotlin("multiplatform")`, `org.jetbrains.dokka` (HTML), BCV, spotless. **No `dokka-javadoc`**,
    which is JVM-only and stays in `library-module-conventions`.
  - `explicitApi()`, the same two opt-ins, `-Xcontext-parameters` plus `-Xexpect-actual-classes` (for
    B6), `jvmToolchain(11)` at the `kotlin {}` level, so it applies to the JVM target. Checked: the
    JVM tests run on "Eclipse Temurin JDK 11".
  - Dropped the `kmp` branch's `java { withSourcesJar() }`. KMP and vanniktech publish per-target
    sources jars themselves.
  - Spotless `kotlin { target("src/**/*.kt") }`. **This was a real gap:** spotless infers the Kotlin
    sources only from JVM source sets, so under MPP its default Kotlin target is empty and
    `spotlessKotlinCheck` passed on a deliberately misformatted file in `jvmMain` and `jvmTest`. With
    the explicit target it flags both. The `kmp` branch has this bug too.
- `buildSrc/.../library-publish-conventions.gradle.kts`: the POM `description` is now a lazy
  `provider { … }`. Needed: under KMP the publications already exist when the plugin is applied,
  so vanniktech's `pom {}` ran before `core/build.gradle.kts` had set `description`. That failed with
  "Missing core project description", confirmed by stack trace
  (`MavenPublishBaseExtension.pom` → `mavenPublications` → our block). The `kmp` branch wrapped the
  whole `mavenPublishing {}` in `afterEvaluate`. One lazy property is smaller and leaves the JVM
  modules' ordering untouched. POM descriptions were checked in the published `.pom` files.
- `core/build.gradle.kts`: `library-multiplatform-module-conventions`, the `kmp` target list (jvm;
  js(IR) browser + nodejs; iosArm64/iosSimulatorArm64/iosX64, macosArm64,
  watchos{SimulatorArm64,Arm32,Arm64,DeviceArm64}, tvos{SimulatorArm64,Arm64},
  androidNative{Arm32,Arm64,X86,X64}, mingwX64, linux{Arm64,X64}; wasmJs commented out). The source
  set dependencies are listed below. The Apple-simulator guard was carried over as-is.
- `git mv core/src/main core/src/jvmMain` and `core/src/test core/src/jvmTest`. No code edits.
  `commonMain` is empty.
- Root `build.gradle.kts` `actionsBeforeCommit`: added `jvmMainClasses`/`jvmTestClasses`. A KMP
  module has no `classes`/`testClasses` tasks, so without this the pre-commit aggregate would have
  stopped compiling core's tests. `jvmMainClasses` only compiled before because `apiDump` needed it.
- `kotlin-js-store/yarn.lock` (new, committed): the KGP JS lockfile, as on the `kmp` branch. KGP
  fails on a lockfile mismatch by default, so it belongs in git.

**The `.api` file stays at `core/api/core.api`.** The plan predicted per-target files, but BCV
0.18.1 only splits the dump into `api/<target>/` when there is more than one JVM target, and klib
validation (B8) is off. `apiDump` does now also schedule the per-native-target `*ApiBuild` tasks,
which are no-ops.

**Test tasks present** (`:core:tasks --all`): `jvmTest`, `jsTest`/`jsNodeTest`/`jsBrowserTest`,
`iosSimulatorArm64Test`, `iosX64Test`, `macosArm64Test`, `tvosSimulatorArm64Test`,
`watchosSimulatorArm64Test`, `linuxX64Test`, `mingwX64Test`, `allTests`. `linuxX64Test` and
`mingwX64Test` are disabled by KGP on this macOS host ("Task is enabled" is false). The rest skip
through KGP's own "test binary exists" `onlyIf`, because there is no test source yet. The Kotlin/Native
2.3.21 distribution was already in `~/.konan`, and nothing native was compiled (every native compile
is NO-SOURCE).

## Deviations, and why

1. **Temporary native-publication guard in `core/build.gradle.kts` (B1 must delete it).** Because
   `commonMain` is empty, every native `compileKotlin<Target>` is NO-SOURCE and writes no `.klib`.
   `generateMetadataFileFor<Native>Publication` then fails with `FileNotFoundException …/core-<target>Main-local-SNAPSHOT.klib`,
   which breaks `:core:publishToMavenLocal` and so `:gradle-plugin:test`. JS is unaffected: its klib
   is packaged by a jar task and exists even when empty. The guard disables
   `generateMetadataFileFor<Native>Publication` and `publish<Native>PublicationTo*` while
   `core/src/commonMain` does not exist, so it switches itself off once B1 creates that directory.
   Configuration cache tracks the `exists()` check. Rejected alternatives:
   - A placeholder source in `commonMain` or `nativeMain`. The orchestrator forbade it.
   - Pointing `gradle-plugin`'s test at `publishJvmPublicationToMavenLocal` only. That leaves
     `:core:publishToMavenLocal` and CI's `publishToMavenCentral` broken.
2. **`kotest-assertions-core` is in `jvmTest`, not `commonTest`. The plan's premise is wrong.**
   `kotest-assertions-core` 6.2.0 publishes no `androidNativeArm32` variant; it has every other
   target in our matrix. With it in `commonTest`, `:core:check` fails configuring
   `compileTestKotlinAndroidNativeArm32` ("No matching variant of io.kotest:kotest-assertions-core:6.2.0").
   `allTests` does not catch this, because androidNative test binaries are not runnable. Since
   locked decision 2 is the full native matrix, I did not drop the target. **B1 must choose one of:**
   - `commonTest` uses `kotlin.test` assertions only.
   - A custom test source-set hierarchy that excludes `androidNativeArm32` from kotest.
   - Drop `androidNativeArm32`. This reopens locked decision 2, so it is the user's call.
   - Wait for, or pin, a kotest that ships the target.
3. Root `actionsBeforeCommit` gained `jvmMainClasses`/`jvmTestClasses`. This is outside `core/` and
   `buildSrc/`, but without it the repo's own pre-commit gate silently stopped compiling core's
   tests.

## Other things that surprised me

- `kotlin("test")` in `commonTest` makes KGP add `kotlin-test-junit5` to `jvmTest`, because
  `useJUnitPlatform()` is set. That drags `junit-jupiter-engine` 5.13.4 onto the classpath next to the
  kotest engine. It is harmless: the test count is unchanged at 709 and nothing uses `@Test`. It
  does mean JUnit Jupiter will also discover any `kotlin.test.@Test` put in `commonTest`, which is
  the runner B1 wants anyway.
- The javadoc jar of `avro4k-core-jvm` is now Dokka **HTML**, where it used to be Dokka-javadoc
  format. Maven Central only requires the jar to exist. This follows from keeping `dokka-javadoc`
  JVM-only.
- Apple-simulator guard on this host: `xcrun simctl list runtimes` reports only `iOS 26.5`. So the
  guard lets `ios*SimulatorArm64Test`/`iosX64Test` run, and skips tvOS/watchOS simulator tests. This
  cannot be observed yet, because KGP's own "no test binary" `onlyIf` fires first on empty test
  sources. Re-check in B1 once `commonTest` has content: `--info` should show
  "No TVOS simulator runtime installed".
- Existing warnings are unchanged: the toolchain auto-provisioning deprecation and the
  `AvroDecoder.kt:301` / `AvroSerializer.kt:159` compiler warnings.

## Follow-ups

- **B1:** delete the native-publication guard block in `core/build.gradle.kts`, and settle the
  kotest-in-`commonTest` question (deviation 2). Once `commonTest` has tests:
  - `jsBrowserTest` needs a headless browser (Karma + ChromeHeadless by default). CI (ubuntu) must
    provide one, or restrict JS tests to `nodejs()`.
  - `iosSimulatorArm64Test` will boot the iOS 26.5 simulator locally.
- **B1:** consider adding a non-JVM compile (e.g. `compileKotlinMetadata`, or one native/JS
  `compileTestKotlin*`) to `actionsBeforeCommit`. Right now the pre-commit gate compiles only the
  JVM target.
- **B8 / CI:** CI runs on ubuntu, where the Apple targets are disabled. A release that publishes the
  full native matrix needs a macOS runner (or a split publish). Maven-only consumers must now depend
  on `avro4k-core-jvm`, since the root `avro4k-core` POM only carries the common dependencies (no
  apache-avro). The migration guide should say so, and the BOM may want to constrain
  `avro4k-core-jvm` explicitly.
- **B8:** enabling klib validation will move the dump to per-target files. Until then it stays in
  `core/api/core.api`.
