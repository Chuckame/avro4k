# B6 — caches → `expect`/`actual`

**Outcome:** done
**Commit:** see `PROGRESS.md` (implemented inline by the orchestrator after three agent runs died: a rate limit, then two runs interrupted when the host went to sleep — the second one came back, found the inline work, and correctly stopped)

## What changed

- **`Cache<K, V>` moved to `commonMain`** (same FQN; `core.api` unchanged). The JVM, equality-keyed `WeakKeyCache`
  stays in `jvmMain` (file renamed `Cache.kt` → `WeakKeyCache.kt`) and is **used by exactly the same call sites as
  before** — no key semantics changed anywhere.
- **New `expect class WeakIdentityKeyCache<K, V>() : Cache<K, V>`** (`@InternalAvro4kApi`, invisible in the dump):
  - **JVM + native share one implementation** in a new `jvmAndNative` intermediate source set (custom group added to
    the default hierarchy template in `core/build.gradle.kts`): a copy-on-write, power-of-two hash table of immutable
    chained entries, published through stdlib `kotlin.concurrent.atomics.AtomicReference`. Only `WeakRef` and
    `identityHashCode` are per-platform (`java.lang.ref.WeakReference` subclass / `System.identityHashCode`;
    `kotlin.native.ref.WeakReference` / `Any.identityHashCode()`).
  - **JS**: `WeakMap` with plain `get`/`set`, plus a strong `Map` for JS-primitive keys (a Kotlin `String`,
    `Boolean`, `Double` is a JS primitive and a `WeakMap` throws on it).
- **`SerializerLocatorMiddleware`**: the two `IdentityHashMap`s were first replaced by a linear `===` scan
  (`IdentityLookup`), on the *unmeasured* expectation that a scan over ≤5 entries matches a hash lookup. A follow-up
  micro-benchmark (`micro/IdentityLookupMicroBenchmark.kt`, numbers in `benchmark/README.md` → "Results — M2")
  refuted it: the scan was the slowest option at every size (2.39 ns vs 1.24 ns for the map on a miss). The
  middleware now uses two hand-written `when { x === A -> … }` chains (0.75 ns) over static finals, and
  `IdentityLookup` was deleted. The two chains (serializers, descriptors) must list the same types;
  `SerializerLocatorMiddlewareTest` lists each intercepted type once and checks both — mutation-verified by dropping
  one descriptor branch. The `runCatching` around `Instant` became a nullable static (`null` never `===` a key).
  The C3 inline collection cache is untouched.
- **`apache-interop`**: `toAvro4k()` / `toApacheSchema()` now each go through a `WeakIdentityKeyCache`. Neither
  result references its source, so the weak keys stay collectable. Callers must not mutate a returned Apache
  `Schema` (`addProp`…) — already true of the schemas `Avro.schema()` caches.

## Concurrency argument, per platform

- **JVM and native (shared code).** A `Table`, its bucket array and its entries are fully built before the
  `compareAndSet` that publishes them, and never mutated afterwards. The atomic gives a happens-before edge from a
  successful CAS to every `load()` that observes it: on the JVM via `java.util.concurrent.atomic.AtomicReference`'s
  volatile semantics; on Kotlin/Native because atomic operations are sequentially consistent and order the plain
  writes made before them. **No reliance on the JVM final-field freeze** (which native lacks — the M1-review lesson).
  *Source, checked after the M2 review asked for one:* the stdlib 2.3.21 KDoc of `kotlin.concurrent.atomics.AtomicReference`
  says that on Native it "stores a volatile variable" and defers to `kotlin.concurrent.Volatile`, whose KDoc states a
  reader "sees not only that value, but all side effects that led to writing that value" — i.e. the happens-before
  edge for the plain writes that built the table.
  Lost races only cost a discarded computation: after computing, the writer re-reads the table and returns the
  winner's value if the key appeared meanwhile, so every thread observes one value per key.
- **JS.** Single-threaded; no synchronization.

## Reclamation

No `ReferenceQueue`. A put copies the bucket array anyway (O(capacity)), so stale entries are dropped for free when
the table fills: the rebuild keeps live entries only and grows only if they still need the room. Stale entries (and
their values) are therefore retained until the next rebuild — bounded by capacity, never swept on the read path.
Same trade as C2's put-path-only purge, documented in the KDoc.

## Fresh-descriptor probe (JVM, kotlinx-serialization as pinned on `v3/m2-foundation`)

Raw output of the throwaway `FreshDescriptorProbeTest` (deleted before commit):

| Expression, called twice | serializer `===` | descriptor `===` | descriptor `==` / same hash |
|---|---|---|---|
| `serializer<Foo>()` (plain `@Serializable` class) | yes | yes | yes |
| `serializer<List<Foo>>()` | **no** | **no** | yes |
| `ListSerializer(Foo.serializer())` | **no** | **no** | yes |
| `serializer<Map<String, Foo>>()` | **no** | **no** | yes |
| `MapSerializer(String.serializer(), Foo.serializer())` | **no** | **no** | yes |
| `serializer<Foo?>()` | **no** | **no** | yes |
| `Foo.serializer().nullable` | **no** | **no** | yes |
| `serializer<Box<Int>>()` (generic class) | **no** | **no** | yes |
| `Box.serializer(Int.serializer())` | **no** | **no** | yes |
| `serializer<ByteArray>()` | yes | yes | yes |
| `serializer<String>()` | yes | yes | yes |

- Element descriptors of a *non-generic* class are stable: `Holder.serializer().descriptor.getElementDescriptor(i)`
  is `===` across calls for a `List<Foo>`, a `Box<Int>` and a `Foo?` element (the generated serializer is an
  `object` whose `childSerializers` are built once).
- But that element descriptor is **not** `===` to `serializer<List<Foo>>().descriptor` (only `==`).
- `Avro.schema<List<Foo>>()` twice returns the **same** `Schema` instance (the equality-keyed `schemaCache` hits
  even though the descriptor is fresh).
- The element type of `Avro.schema<List<Foo>>()` is **not** `===` to `Avro.schema<Foo>()`: a record schema is
  rebuilt per top-level descriptor, so schemas that are equal are routinely distinct instances.
- Apache `Schema.Parser().parse(json)` twice: distinct instances, `==` true.
- `PrimitiveSerialDescriptor("kotlin.String", STRING)`, `"kotlin.uuid.Uuid"` and `"kotlin.time.Duration"` all
  **throw** `IllegalArgumentException: The name of serial descriptor should uniquely identify associated
  serializer.` A user cannot build an equal-but-distinct *primitive* descriptor for a built-in name.

### Consequence: per-call-site identity analysis for M3

| Call site | Key | Identity safe? | If switched to identity |
|---|---|---|---|
| `Avro.schemaCache` | `SerialDescriptor` | **No** | Every `serializer<List<Foo>>()` / nullable / generic descriptor is fresh per call → a miss and a full schema inference **per top-level call**, *and* a fresh `Schema` instance each time, which then also misses every schema-keyed identity cache downstream. Must stay equality-keyed, or identity-first with an equality fallback (the C2 pattern). |
| `RecordResolver.fieldCache` (outer) | writer `Schema` → `AvroSchema` in M3 | Yes, if callers reuse schema instances (they do: `Avro.schema` is cached; Confluent caches by schema id) | A caller that re-parses the writer schema per message would recompute workflows per message. **Must** be identity in M3 (structural `AvroSchema.equals` on the per-record path is the thing to avoid). |
| `RecordResolver.fieldCache` (inner) | record `SerialDescriptor` | Mostly | Non-generic record descriptors are singletons, and element descriptors of a non-generic class are stable. A *generic* record (`Box<T>`) obtained fresh per top-level call would miss once per call (not per element — the C2 memo is per decode). Identity-first + equality fallback is the safe choice. |
| `EnumResolver.defaultIndexCache` | enum `SerialDescriptor` | Yes | Generated enum serializers are singletons. |
| `PolymorphicResolver.cache` | sealed/polymorphic `SerialDescriptor` | Yes for non-generic sealed types | A generic sealed hierarchy would miss per call. |
| `AnySerializer.decodingCache` | writer `Schema` | Yes | Same reasoning as the `fieldCache` outer key. |
| `AvroSingleObject.fingerprintCache` | `Schema` | Yes | Per format instance; a miss is one CRC-64, not a hot-path cost. |
| Confluent `Serializers.cache` | registry `Schema` | Yes | The registry client caches schemas by id, so instances are stable. |

**Rule for M3:** schema keys → identity (as B1 already required). Descriptor keys → identity only for
enum / non-generic sealed descriptors; `Avro.schemaCache` and the inner `fieldCache` level need an identity fast path
*backed by* an equality lookup, never identity alone.

## What was rejected, and why

- **The `kmp` branch's actuals.** Native: a plain `mutableMapOf` mutated from `getOrPut` (not thread-safe; native has
  shared-memory threads) that also scanned every key on every miss. JS: `Map.prototype.getOrInsertComputed`, too new
  for many runtimes.
- **Two copies of the table (one in `jvmMain`, one in `nativeMain`).** Subtle concurrent code reviewed twice and
  drifting apart; the `jvmAndNative` source set costs six lines of build script.
- **A `ReferenceQueue` sweep on the JVM.** Puts are O(capacity) anyway, so sweeping during the rebuild is free, and it
  keeps one implementation for both platforms.
- **atomicfu.** Stdlib `kotlin.concurrent.atomics` works on every target at Kotlin 2.3.21; no new dependency.
- **Moving any existing call site to identity keys.** See the table above: it is M3's decision, and for descriptor
  keys it would be a hit-rate regression.
- **A test of an equal-but-distinct built-in descriptor in the middleware.** Unconstructible — the probe shows
  kotlinx-serialization rejects a user `PrimitiveSerialDescriptor` with a built-in serial name — so identity versus
  equality is unobservable there.

## Follow-ups

- M3: apply the per-call-site rule above; the identity-first + equality-fallback cache for descriptor keys does not
  exist yet (C2's inline memo in `RecordResolver` is the only instance of the pattern).
- JS: `WeakMap` values are held strongly while the key lives — the same "value must not reference its key" caveat
  as every weak-keyed map; nothing in core violates it today.
