# c2 — Don't re-resolve the record workflow per instance

**Outcome:** done
**Commit:** `perf(core): memoize the resolved record workflow per (schema, descriptor)`

## What changed

Two changes, both confined to `core/src/main/kotlin/com/github/avrokotlin/avro4k/internal/`.

### 1. An inline identity cache in front of `RecordResolver.fieldCache`

`resolveFields(writerSchema, classDescriptor)` is called from every `RecordDirectDecoder` /
`RecordDirectEncoder` / `RecordGenericDecoder` / `RecordGenericEncoder` construction — i.e. once per
record *instance*. Each call was two nested `WeakKeyCache.getOrPut`s, so decoding a 100k-element
array of records did 200k `ReferenceQueue.poll()` + `Key.Lookup` allocations + `ConcurrentHashMap`
lookups for a workflow that was already resolved for element 1.

`RecordResolver` now keeps a copy-on-write array of up to `INLINE_CACHE_CAPACITY = 16` `Memo`
entries, scanned linearly and matched by **identity** on both the schema and the descriptor:

```kotlin
@Volatile private var inlineCache: Array<Memo> = emptyArray()
private class Memo(val writerSchema: Schema, val classDescriptor: SerialDescriptor, val workflow: SerializationWorkflow)
```

A hit is a volatile reference read plus a few `===` comparisons and **zero allocation**. A miss falls
through to the existing `fieldCache` unchanged and then prepends a new `Memo` (copy-on-write,
dropping the oldest once full).

Design points worth keeping:

- **One immutable holder, never three fields.** Schema, descriptor and workflow are published
  together or not at all; three separate fields could tear and hand back the workflow of another
  type, which would silently corrupt data rather than fail loudly.
- **Identity, not equality.** Same instances ⇒ same resolved workflow, and it avoids
  `Schema.equals`, which is a deep structural comparison. Structurally-equal-but-distinct schema
  instances simply miss the inline cache and are still deduplicated by `fieldCache` (there is a test
  for that: the two calls return the same `SerializationWorkflow` instance).
- **`@Volatile`, deviating from the briefed "plain field".** The brief's plain-field argument rests
  on JMM final-field semantics, which cover `val`s of a `Memo` but **not array elements**. With a
  plain field, a racing reader could observe an array slot holding a not-yet-initialized `Memo`
  (or `null`). A volatile *read* is a plain load on x86 and a cheap `ldar` on ARM; the volatile
  write only happens on a miss. No locking anywhere on the hot path; a lost concurrent update just
  costs the loser a future miss.

**Why 16 and not 1 (the briefed shape).** A one-entry cache is perfect for a homogeneous collection
but *thrashes to a 100% miss rate on nested records*: decoding `List<Client>` where `Client` has a
nested `Address` alternates `(ClientSchema, ClientDesc)` and `(AddressSchema, AddressDesc)` on every
element, so a single slot never hits. Since the acceptance criteria explicitly expect
`NestedRecordMicroBenchmark` at `depth` 8 to improve, one entry would have shown ~zero win there.
16 covers the whole working set of the benchmark payloads (8 distinct record types at `depth=8`,
2 for `CollectionMicroBenchmark.readRecords`/`writeRecords`) with headroom, and is small enough that
the worst case — a full miss — is 16 iterations of two reference comparisons (≤32 compares) before
falling through, which is still far cheaper than the two `getOrPut`s it replaces. Entries are
inserted MRU-first and never reordered on a hit, so the hot path performs **no writes at all** and
there is no cache-line ping-pong between threads.

**Bounded strong retention (known trade-off).** Unlike `fieldCache`, the inline cache holds its
schemas, descriptors and workflows *strongly*. That pins at most 16 triples per `Avro` instance —
including the `Avro.Default` singleton, where they are effectively pinned for the process lifetime.
Bounded and small; documented in the field's KDoc.

### 2. `WeakKeyCache.removeStaleEntries()` moved off the read path

It ran on *every* `getOrPut`, i.e. a synchronized `ReferenceQueue.poll()` per lookup. It now runs
only in the put path (after a get miss). This is not observable for lookups: a `Key.Stored` whose
referent has been collected compares unequal to every `Key.Lookup` and to every other `Key.Stored`,
so a stale entry could never have been returned by the get phase anyway.

**Known, bounded retention (behaviour change).** Because the map can only grow in the put path,
purging there keeps growth bounded by the number of distinct keys ever inserted. The flip side,
stated explicitly in the class KDoc: a cache that reaches a steady state and stops putting will
**never** reclaim entries that go stale afterwards — the dead `Key.Stored` wrapper *and* its value
(a `SerializationWorkflow` is not tiny) are retained until the next put, possibly forever. Accepted
here because the keys are schemas and serial descriptors, a small and effectively fixed set per
application, so the ceiling is "one entry per distinct schema/descriptor the process ever used".
The keys themselves remain weakly referenced, so they stay collectable; only the derived entry
lingers. If a future unit makes `WeakKeyCache` public-facing or uses it with unbounded key churn in
a read-mostly loop, revisit with a counter-based "purge every N misses" instead.

### Tests

New, both under `core/src/test/kotlin/com/github/avrokotlin/avro4k/internal/`:

- `RecordResolverTest` (6 tests): repeated same-pair resolution returns the identical instance;
  alternating two *descriptors* against one schema in a 1000-iteration loop; alternating two
  *schemas* against one descriptor (field-reordered writer schema → `EncodingWorkflow.NonContiguous`,
  asserting `descriptorToWriterFieldIndex` and the decoding element order); structurally-equal but
  distinct schema instances still share one workflow; 64 distinct pairs (4× the capacity) each
  asserting a per-schema-distinct workflow shape, looped 5×; and 8 threads × 20 000 iterations over
  33 pairs on one shared resolver, asserting reference equality against a pre-warmed expected map.
- `WeakKeyCacheTest` (3 tests): compute-once-per-key with hits; live entries survive a churn of 2000
  throw-away keys with periodic `System.gc()`; compute-once-per-key under 8 concurrent threads.

**Mutation-checked**, so these are not vacuous. Weakening the guard to `memo.writerSchema === writerSchema`
fails "alternating two descriptors…" and the concurrency test; weakening it to
`memo.classDescriptor === classDescriptor` fails "alternating two schemas…" and the over-capacity test.

## What was measured

**Nothing — benchmarks are the orchestrator's job on this machine** (strictly serialized; running
one from this worktree would corrupt another unit's numbers). No `:benchmark:benchmark`,
`:benchmark:benchmarkAlloc` or JMH jar was run. What the orchestrator should expect:

| Benchmark | `@Param` | Throughput | `gc.alloc.rate.norm` |
|---|---|---|---|
| `CollectionMicroBenchmark.readRecords` | `size=100000` | **up, largest win** | **down, largest win** |
| `CollectionMicroBenchmark.writeRecords` | `size=100000` | up | down |
| `CollectionMicroBenchmark.readRecords` / `writeRecords` | `size=1000` | up, ~same relative % | down, ~same relative % |
| `NestedRecordMicroBenchmark.read` / `write` | `depth=8` | up | down |
| `NestedRecordMicroBenchmark.read` / `write` | `depth=3` | up, smaller than depth 8 | down, smaller than depth 8 |

Rationale for the shape: the saving is exactly *one* `Key.Lookup` allocation and one
`ConcurrentHashMap.get` + `ReferenceQueue.poll` **per record instance**, so it scales with the number
of records in the payload. In `CollectionMicroBenchmark` that is `size`, so the win should be roughly
constant *per element* and therefore a near-constant percentage across `size=1000` and `size=100000`
(with `size=100000` the cleanest signal, being least polluted by fixed per-call costs). In
`NestedRecordMicroBenchmark` it is `depth`, so `depth=8` should improve more than `depth=3`, and
`depth=1` should show little or nothing (a single record per op — one saved lookup against all the
fixed per-call cost).

`gc.alloc.rate.norm` is the sharper instrument here: the removed allocation is exact and
deterministic (one `Key.Lookup` per `resolveFields` call → two per record instance, since the
resolver does two nested `getOrPut`s), so the drop in bytes/op should be a clean, reproducible
`≈ 2 × sizeof(Key.Lookup) × records-per-op`. If `gc.alloc.rate.norm` does **not** drop on
`readRecords@100000`, the change is not taking effect and something is wrong. Throughput should
never regress on any benchmark, including `readLongs`/`writeLongs` and `depth=1`, which do not
exercise the new path meaningfully — a regression there would point at the added volatile read.

## What was rejected, and why

- **The briefed one-entry memo in a plain field.** Rejected for nested records: the working set of a
  nested payload is `depth` pairs cycled in order, so a single slot has a 100% miss rate at any depth
  > 1, i.e. it would deliver nothing for `NestedRecordMicroBenchmark`, which the acceptance criteria
  name explicitly. See "Why 16 and not 1" above.
- **A plain (non-`@Volatile`) field for the array.** Unsafe: array elements are not final fields, so
  the JMM final-field freeze that makes the briefed single-`Memo` plain field safe does not extend to
  an array of `Memo`. Correctness over a load that is free on x86.
- **An immutable linked chain of `Memo`s** (which *would* be safely publishable through a plain field
  via final-field semantics, avoiding `@Volatile`). Rejected: pointer-chasing is less cache-friendly
  than a small contiguous array, and the `@Volatile` read it saves costs nothing on x86.
- **Reordering entries MRU-on-hit.** Rejected: it turns every hit into a write to a field shared by
  all threads using the `Avro` instance, trading a lookup win for cache-line contention. FIFO
  insertion with no reordering is optimal whenever the working set fits, which is the case that
  matters.
- **The deeper "memoize on `DecodingStep.DeserializeWriterField`" variant** from the plan. Not done,
  **and M5 should revisit it.** It is strictly better in principle — the child workflow of a given
  parent field is a genuine 1:1 memo with no scan and no capacity limit, so it would be O(1) and
  correct at any nesting depth or record-type count. But it cannot be done without touching the four
  callers: the parent decoder/encoder holds the `DecodingStep`, while the child
  `RecordDirectDecoder`/`RecordDirectEncoder` resolves its own workflow from its constructor with no
  reference to the step that produced it, so the step would have to be plumbed through
  `beginStructure`. Those callers (and `AbstractAvroDirectDecoder`) are owned by other units right
  now, and the inline cache captures the same win for every realistic working set. Revisit if
  profiling after M1 still shows `resolveFields` on the hot path, or if a workload with > 16 live
  record types in one decode loop shows up.
- **Amortising the purge with a "every N misses" counter** rather than "every put". Rejected as
  strictly worse here: the put path is *already* the rare path (misses only), so a counter would add
  state and a mutable shared write for no further saving.
- **Modifying any caller.** Not needed; `RecordResolver.kt` and `Cache.kt` are the only production
  files touched.

## Follow-ups

- **M5:** reconsider the `DecodingStep.DeserializeWriterField` memo once the caller files are free,
  per the bullet above. It would let `INLINE_CACHE_CAPACITY` and its linear scan disappear entirely.
- **KMP:** both files are JVM-only today. `WeakKeyCache` depends on `java.lang.ref` and
  `ConcurrentHashMap`; the inline cache depends on `@Volatile` (which is `expect`-able / maps to
  `kotlin.concurrent.Volatile` in common code). When `RecordResolver` moves to `commonMain`, the
  inline cache is the part that ports trivially — the weak cache underneath is the hard part, and on
  JS it would likely have to become a plain map or a `WeakRef`-based one.
- **Sizing:** `INLINE_CACHE_CAPACITY = 16` is a judgement call, not a measurement. If a later unit
  gets a profile of a real deeply-polymorphic workload, re-derive it. The relevant trade-off is
  documented in the constant's KDoc and in "Why 16 and not 1" above.
- The retention caveat on `WeakKeyCache` (stale entries held until the next put) is currently only
  argued, not tested — it is not directly observable from outside the class, since `map` is private.
  If it ever matters, expose a test-only size accessor rather than loosening the design.
