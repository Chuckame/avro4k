# c3 — stop wrapping collection serializers per collection

**Outcome:** done
**Commit:** `perf(core): reuse the collection serializer wrapper across decodes`

## What changed

`SerializerLocatorMiddleware.apply(deserializer)` runs on **every** `decodeSerializableValue`
(`AbstractAvroDirectDecoder.kt:44`, and the same call exists in `AbstractAvroGenericDecoder.kt:44`).
It used to allocate a fresh `AvroCollectionSerializer` for every collection it saw. It now memoizes
the wrapper in a **one-entry inline cache** held by the middleware object:

```kotlin
private class CachedCollectionDeserializer(
    @JvmField val original: AbstractCollectionSerializer<*, *, *>,
    @JvmField val wrapped: AvroCollectionSerializer<*>,
)

private var cachedCollectionDeserializer: CachedCollectionDeserializer? = null
```

A hit is an identity compare (`cached.original === deserializer`) and a cast — no allocation, no
hashing, no lock. A miss allocates the wrapper *and* the holder and overwrites the single field.

Two properties make this safe:

- **The wrapper is stateless.** Verified by reading `AvroCollectionSerializer` (bottom of
  `SerializerLocatorMiddleware.kt`): it holds only `original`, its `descriptor` delegates to
  `original.descriptor`, and the decode loop keeps its cursor in a local `result` plus
  `decoder.decodedCollectionSize` — i.e. on the *decoder*, not on the serializer. The claim in the
  brief held; one wrapper instance is safely shared across calls and across threads.
- **Key and value are published together.** They live in one immutable holder behind one
  non-`@Volatile` reference. A single reference read/write is atomic on every supported platform, so
  a racing thread sees either a fully consistent holder or a stale/null one and simply falls through
  to allocating. Splitting key and value into two fields would permit a torn read that returns a
  wrapper around the *wrong* serializer — silent data corruption — so the code and its KDoc state
  explicitly that they must never be separated.

Why one entry is enough in practice: decoding is overwhelmingly repetitive. In
`ListWrapperDatasClass` (the `lists` workload) the sequence is outer-list → `entries` list →
`values` list repeated per entry, so the innermost serializer hits on every iteration but the first
of each group. Alternation between two collection types thrashes the cache but stays *correct*, and
degrades to exactly the old behaviour (one allocation per collection) — never worse.

New tests in `core/src/test/kotlin/com/github/avrokotlin/avro4k/internal/CollectionSerializerWrapperCacheTest.kt`
(6 cases, all green):

- same serializer twice returns the *same* wrapper instance (this is the case that fails without the change);
- 1000 iterations alternating `ListSerializer` / `MapSerializer`, asserting each returned wrapper's
  `descriptor` is identically the input's — proves the cache can never hand back the wrong wrapper;
- 1000 iterations with a **brand new** `ListSerializer(...)` instance each time (the leak case);
- nested-collection round trip (`List<List<Int>>`, `Map<String, List<Long>>`, `List<Record>`);
- 200 round trips of a record alternating four different collection serializers;
- 8 threads × 500 decodes of two different nested-collection types concurrently.

## What was measured

Nothing here — **benchmarks are the orchestrator's job** and are strictly serialized; no benchmark
task was run from this worktree.

What should move, and in which direction:

| Benchmark | `@Param` | Expected |
|---|---|---|
| `lists.Avro4kListsBenchmark.read` | `entryCount = 10000` (and `100`) | throughput **up**, `gc.alloc.rate.norm` **down** |
| `lists.Avro4kListsBenchmark.write` | `entryCount = 10000` | **unchanged** — see caveat below |
| `micro.CollectionMicroBenchmark.readRecords` | `size = 10`, `1000`, `100000` | throughput **up** and B/op **down**, effect largest at `size = 10` |
| `micro.CollectionMicroBenchmark.readLongs` | `size = 10` | small improvement; negligible at `100000` |
| `micro.CollectionMicroBenchmark.writeRecords` / `writeLongs` | any | **unchanged** |

Two caveats worth stating plainly rather than overselling:

1. **This is a read-path change only.** The plan's section motivates C3 with "the `lists` workload,
   where avro4k currently loses 15% on write", but the encode path
   (`AbstractAvroEncoder.encodeSerializableValue` → `SerializerLocatorMiddleware.apply(serializer:
   SerializationStrategy)`) has **no** collection branch and never allocated a wrapper. The write
   regression on `lists` has a different cause and is **not** addressed by this unit. Whoever owns
   the write gap should be told.
2. **The wrapper is allocated once per *collection*, not once per element.** A single large list
   sees almost nothing — at `CollectionMicroBenchmark size = 100000` the saving is one object out of
   a 100k-element decode. `lists` is the target precisely because it encodes *many separate*
   collections (one `values` list per `StatsEntry`, `entryCount` of them), so the per-collection
   constant is multiplied by the collection count. Expect a modest, measurable win concentrated in
   collection-dense workloads, not a headline number.

## What was rejected, and why

- **A plain identity map (`IdentityHashMap` / `ConcurrentHashMap` keyed by the serializer
  instance).** This is the obvious fix and it **leaks**. `SerializerLocatorMiddleware` is a global
  `object` shared by every `Avro` instance and every thread, with no lifecycle and no eviction.
  Compiler-generated serializers are per-type singletons, so the map would look bounded in tests —
  but user code calling `ListSerializer(elementSerializer)` or `MapSerializer(k, v)` gets a *fresh*
  `AbstractCollectionSerializer` on **every** call, and nothing stops a service from doing that per
  request. The map would then grow without limit and keep every one of those serializers (and their
  element serializers and descriptors) strongly reachable forever: a genuine memory leak in a
  long-running process. Do not re-propose this. The third new test
  ("keeps working when every call hands over a brand new collection serializer instance") is the
  executable form of this argument.
- **A weak-keyed cache** (e.g. the repo's `WeakKeyCache`). Leak-free, but it re-introduces a
  per-call map lookup that itself allocates — exactly the cost this unit exists to remove — so it is
  plausibly not a net win at all. It is also off-limits right now: `internal/Cache.kt` is owned by
  another unit.
- **A small N-entry (e.g. 4-slot) cache.** Would survive alternation better than one entry, but it
  needs a slot-selection counter and turns a hit into a short scan, and the `lists` access pattern
  is already near-ideal for a single entry. Rejected as unjustified complexity for this unit; it is
  a cheap follow-up if a profile ever shows thrashing.
- **`@Volatile` on the cache field.** Unnecessary: a stale read is harmless (fall through and
  allocate) and the holder is immutable, so there is nothing to publish unsafely beyond a final
  field write. Adding it would put a memory barrier on the hot path for no correctness gain.
- **Caching inside the decoder instead of the middleware.** Would give per-decode isolation and
  remove all sharing concerns, but the decoder is `AbstractAvroDirectDecoder.kt`, owned by another
  unit right now, and a per-decode cache would be re-created for every top-level decode — losing the
  win for the small-record case.

## Follow-ups

- **The `lists` write regression is still unexplained** and C3 does not touch it (see caveat 1). It
  needs its own investigation on the encode path.
- If a profile ever shows the one-entry cache thrashing on a record with many sibling collection
  fields of different types, promote it to a 2- or 4-slot array of the same immutable holder — the
  holder type and the identity-compare discipline carry over unchanged.
- The same `apply(deserializer)` call also does an `IdentityHashMap` lookup in `serializers` on
  **every** decoded value, before the collection branch. That map is tiny and never mutated after
  init, but it is still a hash lookup per value on the hottest path in the library. Worth measuring
  whether a cheaper pre-filter (or hoisting the lookup to schema-resolution time) pays off — out of
  scope here, but it is the same line of code.
- This change is v2.x-shippable: no public API change, no KMP dependency, no platform-specific
  construct (a plain reference field, no `Unsafe`, no `ClassValue`), so it carries over to
  js/native unchanged.
