# c9 — smaller, independent wins

**Outcome:** done (3 of the 4 bullets changed; the 4th investigated and deliberately skipped)
**Commit:** `perf(core): memoize schema fingerprints and drop avoidable allocations`

This unit is v2.x-shippable: no public API change, no KMP dependency, no behaviour change.

## What changed

### 1. `AvroSingleObject` recomputed the parsing fingerprint on every encode — memoized

`AvroSingleObject.crc64avro()` called `SchemaNormalization.parsingFingerprint("CRC-64-AVRO", this)`
on **every** `encodeToSink`. That call canonicalizes the whole schema to its parsing form
(`toParsingForm` — a full recursive walk producing a JSON string) and then hashes it. For the small
records that single-object encoding exists for, this dominated the encode: the payload is tens of
bytes, the fingerprint is a whole schema traversal plus a string build.

It is now memoized in a per-instance `WeakKeyCache<Schema, ByteArray>`.

Two things the brief asked to get right:

- **Cache scope: per-`AvroSingleObject` instance, weak-keyed.** Per-instance rather than global
  because the natural lifetime of the memo is the lifetime of the format object (one per app, or one
  per Kafka serde), and a per-instance map avoids one global `ConcurrentHashMap` becoming a
  contention point shared by unrelated formats. Weak-keyed because an `AvroSingleObject` typically
  lives for the whole process, and a strong-keyed cache would then pin every `Schema` ever encoded —
  including the per-request schemas a registry-backed application generates. `WeakKeyCache` keys on
  `Schema.equals`/`hashCode` (structural for Apache `Schema`), so two structurally equal `Schema`
  instances share one entry, which is exactly right: their fingerprints are equal by definition.
- **The cached value is a mutable `ByteArray`, and it must not escape.** It does not.
  `Schema.crc64avro()` is `private`, it has exactly one caller (`encodeToSink`), and that caller
  passes the array to `Sink.write(ByteArray)`, which copies the bytes into the sink's segments and
  neither retains nor mutates the argument. No public or internal API hands the array to a caller,
  so there is no path by which a caller can mutate the memo. This is stated in a KDoc on the cache
  field so a future change that returns the array has to confront it. If the fingerprint bytes ever
  become reachable from a public API, the cache must hand out a copy (or store the `Long` and
  re-serialize it, which is 8 bytes of work).

Regression test: `core/src/test/kotlin/com/github/avrokotlin/avro4k/AvroSingleObjectFingerprintCacheTest.kt`.
Every assertion either interleaves two schemas on one format instance or warms the cache with the
*other* schema first, so a one-entry or miskeyed cache fails. It also checks that a distinct but
structurally equal `Schema` instance (re-parsed from the same JSON) resolves to the same fingerprint,
which pins the equals/hashCode-based keying.

### 2. `EnumResolver` cached a boxed `Int?` — replaced with a primitive plus a sentinel

`private data class EnumDefault(val index: Int?)` stored a boxed `java.lang.Integer` for the whole
lifetime of the cache entry. It is now `private class EnumDefault(@JvmField val index: Int)` with
`-1` (`NO_DEFAULT`) meaning "this enum has no `@AvroEnumDefault` element"; element indexes are always
`>= 0`, so the sentinel cannot collide.

`getDefaultValueIndex` still returns `Int?`, because one of its three callers is
`internal/decoder/direct/AbstractAvroDirectDecoder.kt`, which another unit owns and which this unit
must not touch. The `?:`-based call sites are therefore unchanged.

The "multiple default values" `UnsupportedOperationException` is byte-for-byte the same message and
is thrown from the same place; the sentinel only changes the "already found one" test from
`foundIndex != null` to `foundIndex != NO_DEFAULT`.

Regression test: `core/src/test/kotlin/com/github/avrokotlin/avro4k/internal/EnumResolverTest.kt`,
covering an annotated element at index 0 (the case a badly chosen sentinel would break), an annotated
element at a later index, no annotation at all (`null` on every call, not just the first), several
descriptors in one resolver, and the multiple-defaults failure asserted on repeated calls with its
exact message. The pre-existing end-to-end coverage in `encoding/EnumTest.kt`
("Only allow 1 @AvroEnumDefault at max") is untouched and still passes.

### 3. Generic map encoder/decoder allocated `Pair`s per entry — removed

`MapGenericEncoder` accumulated into an `ArrayList<Pair<String, Any?>>` and then called
`entries.associate { it.first to it.second }`, i.e. **two** `Pair` allocations per entry (one on
insert, one rebuilt by `associate`) plus a throwaway list. It now writes straight into a
`LinkedHashMap<String, Any?>(mapSize)` that is handed to `onEncoded` as-is.

Behaviour is identical: `associate` also produced a `LinkedHashMap`, and re-putting an already
present key keeps its original position while overwriting the value, exactly like the
insert-then-`associate` sequence did. Encounter order, null values and the
`SerializationException("Map key cannot be null")` guard are unchanged.

`MapGenericDecoder` flattened the map through
`map.asSequence().flatMap { sequenceOf(true to it.key, true to it.value) }` — two `Pair`s per entry
plus a `Sequence` pipeline plus the `flatMap` iterator. It now walks `map.entries.iterator()`
directly with a `nextIsKey` flag, holding the current entry between the key read and the value read.
No allocation per entry.

Regression test: `core/src/test/kotlin/com/github/avrokotlin/avro4k/encoding/GenericDataMapEncodingTest.kt`
— generic-data encode preserving insertion order, a nullable-value map round-tripped through
`encodeToGenericData`/`decodeFromGenericData` with a `null` in the middle, an empty map, a map nested
in a record, and the null-key failure. Note the generic *decoder* had essentially no coverage before:
`AvroAssertions.isEncodedAs` exercises `encodeToGenericData` but decodes through the direct/binary
path, so `MapGenericDecoder` was only reachable from the (deprecated) `decodeFromGenericData` entry
point that nothing tested.

### 4. `Avro.encodeToByteArray`'s `Buffer()` + `readByteArray()` copy — **investigated, not changed**

Verdict: **skip.** Reasons, in order of weight:

- `kotlinx.io` has no API that transfers ownership of a `Buffer`'s backing storage to the caller.
  `UnsafeBufferOperations` only *lends* segment memory for the duration of a callback
  (`readFromHead` / `writeToTail`) or *donates* a caller-owned array into a buffer
  (`moveToTail`, which is what `internal/helpers.kt:Buffer(bytes)` uses on the decode side). The
  decode path is zero-copy precisely because the array flows *into* the buffer; there is no inverse
  operation, so the symmetry the plan hoped for does not exist in the library.
- `encodeToByteArray` must return a `ByteArray` of the exact encoded size, which is not known before
  encoding. So an allocation of exactly `size` bytes is required no matter what; the only thing a
  smarter path could remove is the `memcpy` from pooled 8 KiB segments into that array — which is
  cheap relative to the allocation that remains mandatory, and for the small-record case is a single
  sub-8 KiB copy.
- The one real alternative is a bespoke `Sink` backed by a growable `ByteArray`, trading the single
  final copy for amortized growth copies and the loss of `kotlinx-io`'s segment pooling. That is a
  plausible win only for a size distribution we have not measured, it touches the public
  `Avro.encodeToByteArray` path, and it is the kind of change that needs its own before/after
  numbers. It does not belong in a "smaller, independent wins" unit.
- Locked decision 6 (platform-neutral, no `Unsafe`) rules out the JVM-only escape hatches that would
  make a true zero-copy handoff possible.

Recorded as a follow-up below rather than done badly here.

## What was measured

**Nothing, by design: running benchmarks is the orchestrator's job.** Benchmarks on this machine are
strictly serialized and a run from this worktree would corrupt another unit's numbers. No
`:benchmark:*` task and no `apiDump` was run here.

What the orchestrator should know before trying to measure this unit:

- **No benchmark in the current suite exercises `AvroSingleObject` at all.** `AvroSingleObject` does
  not appear anywhere under `benchmark/`. The whole suite goes through `Avro.encodeToByteArray` /
  `Avro.decodeFromByteArray` (the `simple`, `complex`, `lists` and `micro` packages), none of which
  writes the single-object header or computes a fingerprint. **The fingerprint win is therefore
  invisible to the suite as it stands and will show as "no change".**
  To make it visible, a micro-benchmark would have to be added along the lines of
  `benchmark/src/main/kotlin/com/github/avrokotlin/benchmark/micro/SingleObjectMicroBenchmark.kt`:
  one `AvroSingleObject` instance built in `@Setup` over a registry of one schema, then a
  `@Benchmark fun writeSingleObject()` doing `encodeToSink` of a *small* record (the
  `micro/MicroModels.kt` small record is the right shape) into a reused `Buffer`. The effect size
  scales with schema size and inversely with payload size, so a second variant over a wide/nested
  schema would show the memoization best. Pair it with an allocation-mode run: before the change,
  each encode allocated the canonical-form `String` plus a fresh 8-byte fingerprint array.
  A decode-side benchmark is not needed — `decodeFromSource` never computed a fingerprint.
- **The enum path is only indirectly covered.** `benchmark/internal/Clients.kt` has an `EyeColor`
  enum in the complex workload, but `EnumResolver.getDefaultValueIndex` is consulted *only* when a
  written symbol is unknown to the reader descriptor, which never happens in the suite. The boxing
  removed here is one `Integer` per cached descriptor, not per call, so it is a footprint win rather
  than a throughput win and should not be expected to move any number.
- **The generic map path has no coverage either.** `benchmark/internal/Clients.kt` does contain a
  `Map<String, String>` field, but the avro4k benchmarks all use the direct (binary) encoder;
  `ApacheAvroGenericFastReaderBenchmark` benchmarks *Apache's* generic path, not avro4k's tree
  encoder. `MapGenericEncoder`/`MapGenericDecoder` are unbenchmarked. This was expected — the plan
  already flagged the generic tree as "lower priority — but cheap to fix" — and the change is
  justified on allocation counting (4 `Pair`s per entry across encode+decode, now 0), not on a
  measurement.

So: expect this unit to move **no** number in the existing suite. That is not a reason to revert it,
it is a reason to add the single-object micro-benchmark above.

## What was rejected, and why

- **A global (`object`-level) fingerprint cache** instead of a per-instance one. Rejected: it makes
  the memo outlive every `AvroSingleObject`, turns one `ConcurrentHashMap` into a shared contention
  point across unrelated formats, and buys nothing — the fingerprint is cheap to recompute once per
  format instance, and applications hold one instance.
- **Caching the `Long` fingerprint and re-encoding it to 8 bytes per call**, to sidestep the mutable
  `ByteArray` question entirely. Rejected: it would re-introduce a per-call allocation (or force a
  `writeLongLe`-shaped rewrite of the header write), and the escape analysis above shows the array
  genuinely cannot be reached by a caller. Noted as the fix to apply *if* the bytes ever become
  reachable.
- **Changing `getDefaultValueIndex` to return the sentinel `Int` directly** (the brief allowed it).
  Rejected: one of its three call sites lives in `AbstractAvroDirectDecoder.kt`, which another unit
  owns for the duration of this milestone. Keeping the `Int?` signature keeps this unit's diff
  confined to files it owns. The remaining boxing is one `Integer` per *cached descriptor*, not per
  call, so the residual cost is negligible.
- **Fixing the `MapGenericDecoder.currentWriterSchema` bug found on the way** (see follow-ups).
  Rejected here: it is a behaviour change, and this unit is explicitly no-behaviour-change.
- **A growable-`ByteArray` `Sink` for `Avro.encodeToByteArray`** — see bullet 4 above.

## Follow-ups

1. **`MapGenericDecoder.currentWriterSchema` is (and was) wrong.** The old pipeline was
   `flatMap { sequenceOf(true to it.key, true to it.value) }` — note that **both** the key and the
   value were tagged `true`, i.e. "this is a key". So `currentWriterSchema` always reported
   `STRING_SCHEMA` and the `writerSchema.valueType` branch was dead code. Anything that decodes a map
   whose values need their writer schema — a nested map, a nested array, a polymorphic value, or any
   custom serializer reading `AvroDecoder.currentWriterSchema` — gets the wrong schema (or fails,
   since `Schema.valueType` on a `string` schema throws). This unit **preserved the behaviour
   verbatim** and documented it in place: the rewritten class returns `STRING_SCHEMA` unconditionally
   with a comment pointing here, and the now-unused `writerSchema` constructor property is kept and
   `@Suppress("unused")`-annotated so the fix is a one-line change.
   The fix is to track the key/value position properly (`nextIsKey` is already there — the `advance()`
   function just needs to expose it) and return `writerSchema.valueType` in the value position.
   It needs its own commit with tests for nested maps and polymorphic map values, because it changes
   behaviour and may surface as a new exception in code that currently silently mis-decodes.
   Low blast radius: the generic tree decoder is only reachable via the **deprecated**
   `Avro.decodeFromGenericData`.
2. **Add `micro/SingleObjectMicroBenchmark.kt`** as described under "What was measured", so the
   fingerprint memoization is visible and a future regression in it is bisectable.
3. **Add an avro4k generic-data (tree) benchmark**, or accept that `internal/encoder/generic/**` and
   `internal/decoder/generic/**` are optimized blind. Given that the generic-data API is deprecated,
   "accept" is the reasonable answer — but then future units should stop spending effort there.
4. **Revisit the `encodeToByteArray` copy** only with a size distribution in hand and a
   growable-`ByteArray` `Sink` prototype to compare against, as its own benchmarked unit.
