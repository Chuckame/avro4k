# M3-01 — Test bridge

**Outcome:** done
**Commit:** `test(core): route schema-typed test calls through an Apache test bridge`

Tests and `core/build.gradle.kts` only: no file under `core/src/*Main`, no other module, no `.api` change.
Perf-neutral (tests only).

## What changed

- **New `core/src/jvmTest/.../ApacheTestBridge.kt`**: the only file of the `jvmTest` suite that calls core's schema-typed
  API. Every helper is an identity today.
- **New `core/src/jvmTest/.../ApacheSchemaTestHelpers.kt`**: test-local copies of core's Apache-typed internals (below).
- **37 existing test files changed**, mechanically (a regex rewrite, then the imports cleaned up), to go through the
  bridge and the local copies: every
  `Avro.schema…`, every `encodeToByteArray`/`decodeFromByteArray`/`encodeToGenericData`/`decodeFromGenericData` given a
  writer schema, every `currentWriterSchema` read or mockk stub, every override of a schema-typed core hook. Includes
  `AvroAssertions.kt` (`testEncodeDecode`, `basicScalarEncodeDecodeTests`, the assertion classes), the generic-data tests
  (kept and bridged, per the user's Q1 answer: they move to `apache-interop` in M3-19) and the internal-API tests.
- **Not touched:** M3-02's `KotlinxIoEncoderTest`, `ReadBytesBufferBoundsTest`, `DecodeFromByteBufferTest`.
  `RecordBuilderForTest.kt` needed no change: it never calls core, it only builds Apache generic data.
- **`core/build.gradle.kts`:** `jvmTest` gets `implementation(project(":apache-interop"))`, excluding core itself (see
  "The circular dependency").

### The bridge's API surface

All public, in package `com.github.avrokotlin.avro4k` (test source set, so no `.api` impact; public because the public
inline `testEncodeDecode` calls them).

| Helper | Today | Used for |
|---|---|---|
| `typealias CoreSchema = Schema` | core's public schema type | return type of `getSchema` overrides, parameter of the `AnySerializer.*DeserializationStrategy(writerSchema)` hooks |
| `Schema.toCoreSchema(): CoreSchema` | `this` | returning an Apache schema from a `getSchema` override |
| `Avro.apacheSchema<T>()`, `Avro.apacheSchema(serializer)`, `Avro.apacheSchema(descriptor)` | `schema(descriptor)` | schema generation, compared against Apache-built expectations |
| `Avro.encodeWith(writerSchema, serializer, value)`, reified `Avro.encodeWith(writerSchema, value)` | `encodeToByteArray(writerSchema, …)` | encoding with an explicit writer schema |
| `Avro.decodeWith(writerSchema, deserializer, bytes)`, reified `Avro.decodeWith<T>(writerSchema, bytes)` | `decodeFromByteArray(writerSchema, …)` | decoding with an explicit writer schema |
| `AvroSingleObject.encodeWith(writerSchema, serializer, value)` | `encodeToByteArray(writerSchema, …)` | `AvroSingleObjectFingerprintCacheTest` |
| `Avro.encodeToGenericDataWith(…)`, `Avro.decodeFromGenericDataWith(…)` | the deprecated GenericData calls (the `@Suppress("DEPRECATION")` lives here now) | `AvroAssertions.isEncodedAs`, `GenericDataMapEncodingTest` |
| `AvroDecoder.apacheWriterSchema` | `currentWriterSchema` | test serializers that read the writer schema (`GenericDataMapEncodingTest`) |
| `AvroDecoder.stubWriterSchema(schema)` | `every { currentWriterSchema } returns schema` | mockk-mocked decoders (`AnySerializerTest`) |

`CoreSchema` is the one addition to the brief's sketch. Without it, the 11 test overrides of `getSchema` and of the
`AnySerializer` hooks would have to change at M3-12 anyway, since an override cannot take its signature from a bridge
function. With it, `CustomAvroSerializerTest` and `AvroCustomSchemaTest` drop off M3-12's list of test files to change.

**Stubbing needs its own helper.** `every { decoder.apacheWriterSchema } returns x` would not work after M3-12: mockk
records the innermost call (`currentWriterSchema`, typed `AvroSchema`) and would hand back an Apache `Schema`, failing
with a `ClassCastException`. So the stub is a bridge function that converts the value, not the getter.

**Not added:** a `decodeFixed` accessor. No test outside M3-02's codec tests calls `decodeFixed()`, so the helper would
have no caller. The structural grep below still checks that no test calls it directly; add the helper when a test needs it.

### Test-local copies of core's internals

`ApacheSchemaTestHelpers.kt` holds verbatim copies of `internal/helpers.kt`'s `Schema.nullable`, `Schema.copy` and the
private `Schema.Field.copy` it needs. They replace the tests' imports of `com.github.avrokotlin.avro4k.internal.nullable`
(15 files) and `…internal.copy` (3 files: `PrimitiveEncodingTest`, `AnySerializerTest`, `BigDecimalSchemaTest`); 17
distinct files. The tests use these to *build expected* schemas, so they must not follow core when M3-11 retypes those
internals to `AvroSchema`. They are pure Apache code and never call core.

**Internal imports left in place, on purpose:** `AvroSchemaGenerationException` (`MapEncodingTest`, `UnionSchemaTest`)
and `AvroGenerated` (`AvroGeneratedTest`), which are not Apache-typed. Also `AbstractAvroDirectDecoder`
(`AnySerializerTest`'s mocks) and `RecordResolver.resolveFields(Schema, …)` (`RecordResolverTest`), which M3-11 owns
(§3 names both as its internal-API tests). Their `Avro.schema` calls do go through the bridge.

## The circular dependency

`apache-interop` depends on `core` (`api(project(":core"))`), so `core`'s `jvmTest` depending on `apache-interop` pulls
`project :core` back in through that edge.

**What happens without a fix:** Gradle resolves the edge to core's own JVM **jar**, next to the `jvmMain` class
directories the test compilation already has. The resolved `jvmTest` runtime classpath, printed from the test task:

```
core/build/classes/kotlin/jvm/test
core/build/classes/java/jvmTest
core/build/processedResources/jvm/test
apache-interop/build/libs/apache-interop-local-SNAPSHOT.jar
core/build/classes/kotlin/jvm/main
core/build/classes/java/jvmMain
core/build/processedResources/jvm/main
core/build/libs/core-jvm-local-SNAPSHOT.jar      <-- every core class a second time
…
```

The class directories come first, so the in-tree classes would win, and the jar is built from the same compilation. But
every core class is on the classpath twice, and the brief asks for none.

**Resolution: exclude the self-edge.** The dependency is declared with
`exclude(group = project.group.toString(), module = project.name)`. That drops `project :core` from under
`apache-interop` in `jvmTestCompileClasspath` and `jvmTestRuntimeClasspath` (checked with `:core:dependencies`), and the
jar line above disappears from the runtime classpath. `apache-interop`'s own classes then link against core's `jvmMain`
class directories: one copy of core, the in-tree one. The documented fallback (no dependency, self-contained bridge) was
not needed.

**Proof that the tests exercise the in-tree code:** with the exclusion in place, I temporarily changed `AvroSingleObject`'s
`MAGIC_BYTE` from `0xC3` to `0xC4` in `core/src/jvmMain` and ran `:core:jvmTest --tests '*AvroSingleObject*'`:
`AvroSingleObjectTest` failed on both of its tests (2 of 7 failed). Then I reverted the change. The fingerprint-cache tests
stay green under that mutation, as expected: they encode and decode with the same format.

**Today the dependency has no caller in the tests.** It exists so that M3-12 changes only the bridge bodies (below).
Adding it now also proves the classpath while nothing depends on it.

How to re-check it (the init script is not committed):

```kotlin
// print-cp.init.gradle.kts, run with: ./gradlew -q -I print-cp.init.gradle.kts :core:printJvmTestClasspath --no-configuration-cache
allprojects {
    if (path == ":core") {
        tasks.register("printJvmTestClasspath") {
            val cp = tasks.named<Test>("jvmTest").map { it.classpath }
            doLast { cp.get().files.forEach { println("CP $it") } }
        }
    }
}
```

Pass: exactly one `core` entry set (`core/build/classes/kotlin/jvm/main` …) and no `core-jvm-*.jar`.

## The structural grep (for M3-12 to rerun)

From the repository root; **no output** (grep exit code 1) means that no test outside the bridge calls a schema-typed core
entry point directly:

```bash
grep -rnE --include='*.kt' \
  '[aA]vro\w*\.schema[<(]|\.currentWriterSchema\b|decodeFixed\(|\.(encodeToByteArray|decodeFromByteArray|encodeToStream|decodeFromStream|encodeToSink|decodeFromSource|encodeToGenericData|decodeFromGenericData|openWriter)(<[^()]*>)?\((writerSchema *= *)?(\w*[sS]chema\w*\b|Schema\.|\w+\.\w*[sS]chema\b)' \
  core/src/jvmTest \
  | grep -vE '/(ApacheTestBridge|KotlinxIoEncoderTest|ReadBytesBufferBoundsTest|DecodeFromByteBufferTest)\.kt:'
```

It catches: `Avro.schema<T>()` / `avro.schema(…)` on any `…Avro…`/`…avro…` receiver; any `.currentWriterSchema`;
`decodeFixed(`; and any encode/decode/generic-data/stream/sink/source/`openWriter` entry point, with or without explicit
type arguments or a named `writerSchema =`, whose first argument looks like a schema (an identifier containing
`schema`/`Schema`, a `Schema.` factory call, or `x.…schema…`). At `86e4215` it prints **298** lines; after this unit, **0**.

It is lexical. A schema bound to a name without "schema" in it (`val record = SchemaBuilder…; Avro.encodeToByteArray(record, …)`)
would slip through, so I also listed every remaining entry-point call by its first argument. All are serializer-first or
schema-less `BinaryFormat` calls (`encodeToByteArray(value)`, `decodeFromByteArray(Serializer, bytes)`,
`openWriter<T>(stream)`, …). Overrides are not covered by the grep: `getSchema(…): CoreSchema` and the `AnySerializer`
hooks take `CoreSchema`, so a new override that spells `Schema` would compile today and be caught only at M3-12.

## What M3-12 must change in the bridge bodies

Replace each identity with the conversion to or from `AvroSchema`, using `apache-interop`'s `toAvro4k()` /
`toApacheSchema()`. The call sites stay as they are.

| Helper | M3-12 body |
|---|---|
| `typealias CoreSchema` | `= AvroSchema` |
| `Schema.toCoreSchema()` | `toAvro4k()` |
| `Avro.apacheSchema(descriptor)` | `schema(descriptor).toApacheSchema()` (the other two overloads delegate to it) |
| `Avro.encodeWith(writerSchema, serializer, value)` | `encodeToByteArray(writerSchema.toAvro4k(), serializer, value)` |
| `Avro.decodeWith(writerSchema, deserializer, bytes)` | `decodeFromByteArray(writerSchema.toAvro4k(), deserializer, bytes)` |
| `AvroSingleObject.encodeWith(…)` | `encodeToByteArray(writerSchema.toAvro4k(), …)` |
| `encodeToGenericDataWith` / `decodeFromGenericDataWith` | unchanged if M3-19's moved API stays Apache-typed in `apache-interop`; otherwise `toAvro4k()` |
| `AvroDecoder.apacheWriterSchema` | `currentWriterSchema.toApacheSchema()` |
| `AvroDecoder.stubWriterSchema(schema)` | `every { currentWriterSchema } returns schema.toAvro4k()` |

Reified overloads delegate to these and need no change.

Things to watch at M3-12:

- **Identity-sensitive tests.** `AvroSingleObjectFingerprintCacheTest` checks that a structurally equal but *distinct*
  schema gets the same fingerprint, and `RecordResolverTest` has identity and equality cases. An uncached `toAvro4k()` in
  `encodeWith` hands core a fresh `AvroSchema` per call, which is harmless for the fingerprint test (it asserts equality
  of bytes) but changes which cache layer a call hits. `RecordResolverTest` calls `resolveFields` directly with Apache
  schemas, so M3-11 rewrites it anyway.
- **Round-trip fidelity.** `apacheSchema()` compares the core-generated schema *converted back* to Apache against an
  Apache-built expectation, so any `toApacheSchema()` lossiness becomes a test failure in `schema/*`. That is the oracle
  doing its job. The known artefacts are recorded in the ledger's B1 row: integer-literal defaults for float fields, and
  big-integer int defaults.
- **M3-12's list of tests to change shrinks.** `CustomAvroSerializerTest` and `AvroCustomSchemaTest` (via `CoreSchema`),
  `AvroFixedEncodingTest`, `AvroSingleObject*Test` and `RecordBuilderForTest` should need no edit. `AvroObjectContainerTest`
  uses only schema-less `openWriter<T>`/`decodeFromStream<T>` plus the bridge, and moves to `apache-interop` in M3-14.
