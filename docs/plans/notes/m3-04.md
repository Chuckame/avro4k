# M3-04 — Model readiness: a hot-path-ready `AvroSchema`

**Outcome:** done. No locked decision touched. One design point differs from the brief's wording, explained below:
`EnumSchema`'s index is built at construction, not lazily. Enum symbols can never be recursive, so the index is complete
there.
**Commit:** the one that adds this file (`git log -1 -- docs/plans/notes/m3-04.md`).

**Why `logicalTypeName` is computed at init rather than lazily.** It is a single map lookup on a map the constructor
already holds, and every schema is built on a cold path. A lazy version would need either `lazy {}` (a lock and an extra
object per instance, which the brief rules out) or a sentinel plus a volatile field. Both cost as much memory as the
stored field, and both add a branch on every read. The only memory cost is one reference per instance.

**Why the record index is lazy, but the enum index is not.** A recursive record's `LockableList` is empty when the
constructor runs, so an index built there would be empty. The second mutation below shows this breaks 15 tests. An
enum's `symbols` is complete at construction, and the uniqueness check has to build the same hash structure anyway, so
keeping it costs nothing extra in CPU.

**Equality untouched (B1).**
- `type` and `logicalTypeName` live in the sealed base's constructor, not in any data class's primary constructor. So
  they take no part in the generated `equals`, `hashCode`, `toString`, `copy` or `componentN`. Both are derived from the
  primary-constructor arguments anyway.
- `symbolIndex` and `fieldIndexByName` are body properties. Data classes ignore them, and so do the hand-written
  `RecordSchema.equals`, `hashCode` and `toString`.
- `RecordSchema.hashCode` is still `name.hashCode()`, and `SeenPair` and the co-inductive `equals` are unchanged.
- All recursive-schema tests pass. `warmCachesDoNotAffectEqualsHashCodeAndToString` compares a warmed record with a cold
  one (`==` both ways, same hash, same `toString`, a warmed `copy()` starts cold), does the same for an enum, and pins
  the exact `toString` of `EnumSchema`, `BytesSchema` and `FixedSchema`.

## Visibility of the lazy record index, on every platform

The KDoc on `fieldIndexByName` states the argument. It is the B6 pattern (`WeakIdentityKeyCache`):
- The `HashMap` is fully built before the single write that publishes it, and it is never mutated afterwards.
- The field is `kotlin.concurrent.Volatile`:
  - **JVM:** a volatile write happens-before every read that observes it (JLS 17.4.5).
  - **Kotlin/Native:** `@Volatile`'s contract is that a reader "sees not only that value, but all side effects that led to
    writing that value".
  - **JS:** single-threaded.

So a reader that sees the map sees all of its entries. The argument does not rely on the JVM final-field freeze.
Kotlin/Native lacks that freeze, and it would not apply anyway to a field written after construction.

The old `lateinit var fieldsByName` was the case this fixes. For recursive records it was written at `lock()`, after
construction. It was not volatile, so a racing reader on another thread could see it unset
(`UninitializedPropertyAccessException`).

Two threads may both build the map on a first-lookup race. The two builds are equal and either one wins, so the race is
benign and no lock is needed.

**Scope of the guarantee.** It covers the index only. The rest of the schema, including a `LockableList`'s contents and
its `isLocked` flag, still relies on the schema itself being safely published after `lock()`, as it did before. The
index does not weaken that.

`EnumSchema.symbolIndex`, `type` and `logicalTypeName` are constructor-set `val`s, so they are exactly as safe as every
other field of the schema (for example `symbols` and `name`). They add no new publication requirement.

## Mutation checks

1. **Drop the lock check in `fieldIndex()`.** `recursiveRecordFieldLookupThrowsBeforeLockAndWorksAfter` fails:
   `"Cannot access a non-locked list" should include substring "before its LockableList of fields is locked"`.
   - Honest caveat: without the check, `LockableList`'s own guard still throws, but with a generic message and only
     because this list type happens to guard `size`.
   - The explicit check makes the contract independent of the list implementation. It also guarantees that nothing is
     cached before the lock.
2. **Build the index at construction** (the shape the brief warns about). 15 of the 28 model tests fail:
   - every recursive schema, whether built by hand or parsed from JSON, throws `Cannot access a non-locked list` at
     construction;
   - `rejectsInvalidDefaults` gets the wrong exception type;
   - the mutant's alias-less index also fails `recordFieldLookupByNameAndAlias`.

The source was restored after each mutation, and the full suites above ran on the restored tree.

## What was rejected, and why

- **Keeping the index built at validation time (at construction or `lock()`), made volatile.** It would save the
  first-lookup build, but every record would keep the map forever. The lazy version keeps memory ≤ today's for records
  that are looked up, and uses nothing for records that are not. Its first-lookup build is a one-time cold cost.
- **`lazy {}` for any cached value:** a lock plus an extra object per instance, ruled out by the brief.
- **Returning `-1` instead of `Int?` from the lookups.** The maps store boxed `Integer`s anyway. Returning the looked-up
  box allocates nothing, and positions below 128 are cached boxes. Revisit only if a profile shows unboxing.
- **Aligning `logicalTypeName` with Apache's "textual only" rule** (a numeric `logicalType` would become `null`).
  Rejected to avoid a silent change beyond making it non-throwing. The old code returned `"123"` for a number, and so does
  the new one.

## Follow-ups

- **M3-07 (helper layer):**
  - `fixedSize` and `enumSymbols` accessors return `Int` and `List<String>` directly.
  - `getIndexLogicallyTyped` must compare `logicalTypeName`, a `String` field, never `props`.
  - Kind switches should read `type`, a field, or use sealed `is` checks. Both are cheap now.
  - No helper may call `getField*` on a record that could still be unlocked.
- **M3-09 (schema generation on `AvroSchema`):**
  - Build `FixedSchema(size = annotation.size)` with an `Int`.
  - Recursive records must be `lock()`ed before anything queries their fields by name. The lookup throws otherwise,
    loudly.
- **M3-11 (runtime):**
  - Encode an enum with `getSymbolIndexOrNull`. Null means: fall back to the default symbol, or throw.
  - Decode an enum with `symbols[index]`.
  - `RecordResolver` should resolve writer ↔ reader fields with `getFieldIndexOrNull`. Do it once per identity-cached
    (writer, reader) pair, never per value. The volatile read is cheap but not free, and it has no place in a per-value
    loop.
  - `logicalTypeName` comparisons are `String` compares, which are allowed on the hot path. §1 forbids equality on
    schemas, not on their names.
- **B8 migration guide:** `FixedSchema.size` is `Int`; `logicalTypeName` is a member of `AvroSchema`; plus the behaviour
  changes listed under the API diff.
- **Still open from B1** (not in this unit's scope): the inconsistent equality rule across record, fixed, enum and field
  (doc and aliases), and the mutable collections in `toJsonElement` / `fromJsonString` signatures.
