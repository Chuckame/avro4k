## What changed

- **The converter moved** from `apache-interop/.../AvroSchemaApacheInterop.kt` to
  `core/src/jvmMain/.../internal/AvroSchemaApacheConversion.kt`. It has four entry points, all
  `@InternalAvro4kApi public`:
  - `apacheToAvro4k(Schema)` and `avro4kToApache(AvroSchema)`: cached, and paired both ways.
  - `apacheToAvro4kUncached` and `avro4kToApacheUncached`: they read and write no cache. Use them for fresh-per-call
    schemas (§1, per-value boundary rule).
  - Plus `apacheConversionCacheSize()`, for tests only.
- Git does not record the move as a rename: the file changed too much (pairing code, identity memo) to pass the 50%
  similarity threshold.
- **`apache-interop` keeps only the two public one-line delegates.** Their KDoc now states the pairing guarantee, and
  that the cached results must not be mutated.
- **`ApacheToAvro4k` memoises by identity, not by full name.** B1's converter memoised named types by `fullName`, so two
  distinct Apache instances of one named type shared one avro4k node. Now each Apache node has exactly one avro4k node,
  and the other way round, so pairing can return the caller's exact node at every position.
  - The result is still `==` to what B1 produced (the 436 fidelity tests are unchanged).
  - Only the sharing differs: core's schema generation can emit two instances of the same enum/fixed, and they now
    give two equal avro4k nodes.
  - This cannot break the json route: `toJsonElement` dedupes named types by *name* (`knownNamedTypes`), so a type
    that appears twice is still defined once.
  - Recursion goes through the same Apache instance, so the identity memo is enough to terminate it.

## Pairing ("two-way seeding")

For every node `s` of a converted Apache schema and the node `a` at the same position in its conversion:
`s.toAvro4k() === a` **and** `a.toApacheSchema() === s`. The same holds when the conversion starts on the avro4k
side, and it holds for every sub-node, not just the root. M3-11's facade depends on this: `currentWriterSchema` must
return the caller's original Apache node.

- **Apache → avro4k:** the walk records every node it creates with its source. A sub-schema that is already paired
  (for example, converted alone before) is reused together with its whole subtree.
- **avro4k → Apache** goes through json (`Schema.Parser`):
  - Afterwards, `pairParsedNodes` walks both trees in parallel and records the pairs.
  - A node that is already paired keeps its old partner, and the node at its position in the new result stays
    unpaired until it is converted itself. Apache's parser copies every record it resolves, so this route cannot
    reuse an existing Apache node.
  - An avro4k node shared at several non-named positions meets a distinct parsed node at each one. Only the first is
    paired.
- **`seed`** publishes one conversion, in three steps:
  1. **Back links:** every new node gets a weak link to its source.
  2. **Root claim:** the root's link is claimed with a CAS. A loser returns the winner's result.
  3. **Other nodes:** every other source node is linked to its new node. A source that is already paired keeps its
     partner, and our back link to it is cleared.
- Nothing is visible before step 2 publishes the root. The cached walk locks a recursive record's fields only at the
  end.

## Why the weak keys stay collectable

The requirement from the handoff: the two caches hold A→B and B→A, so the note must argue why neither key pins the
other.

**Both caches are `WeakIdentityKeyCache`s. The key is weak, the value is strong.** If both values held their partner
strongly, `avro4kByApache[s] → a` and `apacheByAvro4k[a] → s` would keep each other's keys alive through two static
tables forever. The classic cross-table cycle: each value reaches the other table's key.

Each cache value is a `Link` (one `AtomicReference`), which holds either a strong target or a `WeakTarget` (a
`WeakReference` subclass). **Each pair has exactly one strong link, under the key of its origin**, the node the caller
converted:

| Conversion | `avro4kByApache[s]` | `apacheByAvro4k[a]` |
|---|---|---|
| `s.toAvro4k()` (Apache origin) | strong `a` | weak `s` |
| `a.toApacheSchema()` (avro4k origin) | weak `a` | strong `s` |

**The argument:**

1. **Everything the tables hold strongly is a strong partner.** The keys are weak, and a weak link holds nothing.
2. **A strong partner never reaches its own origin.** Neither schema model references the other. An avro4k node
   references only avro4k nodes; an Apache node references only Apache nodes. The Apache trees parsed on the json
   route are fresh, and never contain a caller's node.
3. **So an origin is strongly reachable only from outside the caches.** Once the caller drops it, it is collected. Its
   entry goes stale, and the next rebuild of that table drops it together with the strong partner (deferred
   reclamation, `CopyOnWriteWeakTable` KDoc). The partner is then unreachable too; its own entry goes stale and is
   dropped at the next rebuild of the other table. **Reclaiming a pair therefore takes one rebuild of each table.**
4. **Mixed histories keep the property.** Suppose an Apache-origin conversion reuses an avro4k subtree whose origin
   was avro4k. The new strong partner `a0` then references `a1`, which is itself a key holding a strong `s1`. That
   keeps `a1` alive as long as `s0`'s entry lives, which is intended: `s0`'s conversion contains `a1`. `s1` is a
   parsed tree, which cannot reach `s0`, so no strong path leads back to any origin.

**Consequences:**

- The origin keeps its partner alive: a hit stays a hit while the caller holds the node it converts.
- The partner never keeps the origin alive.
- A weak link whose target was collected is dead. The next conversion of that key re-pairs it, with that key as the
  new origin (tested: "…is paired again with a new one").

**The WIP had this wrong.** Step 1 of `seed` passed `strong = true`, despite its own comment ("weak back links"). That
put a strong link on both sides of every pair, which is exactly the cycle above: nothing converted with the cache
could ever be collected. The collectability tests failed on it, but only after a very long run (next section).

### A test-design flaw fixed along the way

- **The flaw.** `churnCaches` inserts throw-away conversions to force the table rebuilds that reclaim stale entries.
  It had no size bound in the "keeps alive" tests, and a bound relative to the current size in the others.
- **Why it hid the leak.** Under a leak, the churn's own entries are never collected, and a put is O(capacity), so the
  churn goes quadratic. On the WIP, the first collectability test was still in `CopyOnWriteWeakTable.with` after
  15 minutes (jstack). The relative bounds also compounded from one test to the next.
- **The fix.** One limit, fixed at the first churn (`4 × size + 10 000` entries), applied to every churn, with
  `churnCaches(…) shouldBe true` at every call site.
- **The result.** Under the leak, all six collectability tests now fail in under 0.25 s each. With the fix, the whole
  class runs in ~1.8 s.

## Rules checked

- **No structural equality.** A grep of both changed main files for `==`/`!=`/`indexOf`/`contains`/`in` finds only
  enum and string comparisons. Every schema-keyed collection is identity-based (`IdentityHashMap`, identity sets,
  `WeakIdentityKeyCache`).
- **Shared state.** Both caches are copy-on-write with CAS. A `Link` changes only by CAS. Per-conversion state (the
  memo, the `created` list) lives on the walk object.
- **Hit path:** `getOrNull` (no insert, no lambda) → `Link.get()` (one atomic read and an `instanceof`). The WIP's hit
  path went through `getOrPut { Link() }` and inserted an empty `Link` on every miss. It now uses `pairedWith`, and
  only keys that are about to be paired get a `Link`.
  - It is one dereference longer than B1's cache: the `Link` sits between the entry and the partner.
  - **M3-11 serves `currentWriterSchema` through this hit path per value.** The M3-11+12 A/B is where that shows up,
    if it matters.
- **Perf:** cold path only. The runtime does not call the converter yet. No A/B (none is due, per §9).

## Risks carried forward

- **Core `jvmMain` now reaches Jackson (`JsonNode`) and Apache's `util.internal.Accessor`.** This is intended until
  M3-14 moves the converter back to `apache-interop`.
- **A stale origin entry keeps its partner until the next rebuild of its table.** That is bounded by capacity, like
  every `CopyOnWriteWeakTable` value, but a pair needs one rebuild of *each* table to be fully reclaimed.
- **The cached results are shared.** Callers must not mutate them (`addProp`…), exactly as with the schemas
  `Avro.schema()` already caches. The public KDoc says so.
