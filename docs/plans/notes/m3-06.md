# M3-06 — Common caches and descriptor-keyed call sites

**Outcome:** done. No locked decision touched. Not api: `core.api` unchanged, and `WeakKeyCache`'s JVM ABI (public
constructor + `getOrPut(Object, Function0)`, implements `Cache`) is byte-for-byte the same shape (`javap`), so
Confluent's `Serializers.cache` links unchanged.
**Commit:** the one that adds this file (`git log -1 -- docs/plans/notes/m3-06.md`).

## What changed

### `WeakKeyCache` is a common `expect class` (same FQN, still `@InternalAvro4kApi`)

- **JVM and native:** the copy-on-write table B6 wrote for `WeakIdentityKeyCache`, generalised with one constructor
  constant, `identity: Boolean`. The table moved out of `WeakIdentityKeyCache.jvmAndNative.kt` into
  `jvmAndNativeMain/.../internal/CopyOnWriteWeakTable.kt`, which carries the whole concurrency KDoc. Both actuals —
  `WeakIdentityKeyCache.jvmAndNative.kt` and the new `WeakKeyCache.jvmAndNative.kt` — are four-line delegations to it.
  **There is one concurrent table in the code base**, reviewed once:
  - identity mode: `identityHashCode` + `===`;
  - equality mode: `hashCode()` + `stored === key || key == stored`. `equals` is skipped for collected entries,
    whose referent is `null`.
  - Everything else is shared: the bucket walk, the CAS publication, the rebuild that drops stale entries.
- **JS:** a plain strong `HashMap` (`WeakKeyCache.js.kt`). See "JS leak trade-off" below.
- The old JVM-only `ConcurrentHashMap` + `WeakReference` + `ReferenceQueue` file is deleted.
- The **equality mode keeps the O(capacity) put**. Its callers must feed a bounded key set; the `expect` KDoc lists them
  and why each is bounded:
  - `IdentityFirstCache`'s equality layer holds descriptors. Fresh equal instances hit rather than insert, so the bound
    is the number of distinct types.
  - `RecordResolver.fieldCache` (outer level), `AnySerializer.decodingCache` and `AvroSingleObject.fingerprintCache`
    hold writer schemas, which are few per application.
  - Confluent's `Serializers.cache` holds registry schemas, bounded by the schema ids a consumer sees.
- **New internal members** on both expect classes (invisible to BCV, mangled `$core` on the JVM):
  - `getOrNull(key): V?`
  - `putIfAbsent(key, value): V?`, which returns null when it inserted and the existing value otherwise. In equality
    mode, "inserted" means `key` is now the canonical instance.
  - `size`, for tests. On JS, `WeakIdentityKeyCache.size` counts insertions, since a `WeakMap` cannot be counted.

### New `IdentityFirstCache` (common, `internal`)

- **Structure:** an identity layer (`WeakIdentityKeyCache`) in front of an equality layer (`WeakKeyCache`), which is the
  source of truth.
- **`getOrPut` is `inline`:**
  1. identity `getOrNull` → return;
  2. equality `getOrNull` → return;
  3. otherwise compute, then `putComputed`: `equality.putIfAbsent(key, value)`. If that returns null, seed
     `identity.putIfAbsent(key, value)`; otherwise return the existing value and seed nothing.
- **Why not a `Cache`:** its `getOrPut` must be `inline`, so that the call sites allocate no capturing lambda.

## How the hit path is allocation-free

The pre-M3-06 `WeakKeyCache` hit allocated two objects:

1. **`Key.Lookup`.** `ConcurrentHashMap<Key, V>` stores `WeakReference` subclasses as keys, so `get` needs a key object
   that `equals` a stored one. The wrapper escaped into `ConcurrentHashMap.get`, so it was a real allocation with
   escape analysis off (M1).
2. **The caller's capturing lambda**, e.g. `{ loadCache(enumDescriptor) }`. Kotlin creates it (via `invokedynamic`) on
   every call, before `getOrPut` even looks.

Now:

- **Equality mode needs no wrapper.** `Table.find(key, hash, identity)` receives the caller's key and its precomputed
  hash as plain arguments, walks one immutable bucket chain, and compares each entry's `WeakRef.get()` referent with
  `===` and then `==`. Nothing needs to *be* a map key, so nothing is wrapped. The identity mode was already built this
  way (B6).
- **No lambda on a hit.**
  - `IdentityFirstCache.getOrPut` is `inline`, so `compute` exists only as inlined code on the miss branch.
  - `EnumResolver` calls `getOrNull` first.
  - `RecordResolver`'s outer lambda `{ IdentityFirstCache() }` captures nothing, so it is a singleton.
  - Checked in the bytecode (`javap -c`) for `Avro.schema`, `PolymorphicResolver.getFullNamesAndAliasesToSerialName`
    and `EnumResolver.getDefaultValueIndex`: each reaches `getOrNull$core`, and returns on a hit, with no `new` and no
    `invokedynamic` on the way. Those instructions appear only on the miss branch: the `Ref`, the `ValueVisitor` and
    the lambdas.
- **The remaining work on a hit:**
  - identity: one atomic load, one bucket walk, `WeakRef.get()`, `===`;
  - equality: the key's `hashCode()` plus one `equals`. kotlinx-serialization descriptors allocate in neither:
    `PluginGeneratedSerialDescriptor` caches its hash in a `lazy`, and list, map and nullable descriptors compose their
    elements' hashes.
- **Not converted, deliberately:** the callers of `AnySerializer.decodingCache` and `AvroSingleObject.fingerprintCache`
  still pass capturing lambdas. Their wrapper is gone, but the lambda stays until M3-11/M3-14 retype those caches.

## Seeding policy, and its proof

**Rule:** the identity layer is seeded only on step 3, and only when `equality.putIfAbsent` returns null, i.e. when
this very instance became the equality layer's canonical key.

- **Fresh instances are never seeded.**
  - A fresh instance that is equal to a live canonical key returns at step 2, and step 2 never writes.
  - A fresh instance that misses step 2 but loses the insertion to an equal key (a race, or a re-entrant compute) gets
    a non-null value from `putIfAbsent` and returns it without seeding.
  - So the identity layer holds at most one live instance per equality class. Stale entries are dropped at the next
    rebuild.
- **Consequence:** a fresh-per-call descriptor (`serializer<List<Foo>>().descriptor`) pays the equality lookup on every
  call. That is the pre-M3-06 cost minus the `Key.Lookup` wrapper, never more.
- **A stable instance can wait:** if an equal *fresh* instance won canonicity first, the stable one also pays the
  equality lookup, until that fresh instance is collected. The next lookup then misses, recomputes (as the equality-only
  cache always did after a collection), and makes the stable instance canonical.

## JS leak trade-off

- **`WeakKeyCache` on JS is a strong `HashMap`.**
  - A `WeakMap` compares by identity only, so it cannot implement an equality cache.
  - JS is single-threaded, so no synchronization is needed.
- **Cost:** keys and values are never evicted, so they live as long as the cache: for `Avro.Default`'s caches, forever.
  The leak is bounded by the number of distinct keys ever inserted, which is why the callers must feed bounded key sets
  (the same restriction the O(capacity) put already imposes on JVM and native).
- **In `IdentityFirstCache` on JS**, the strong equality layer also keeps every canonical key alive, so the `WeakMap`
  identity layer never loses them either.
- **Rejected:** a hand-made table of ES2021 `WeakRef`s reached through `dynamic`. It was not worth it for bounded key
  sets.
- **Today this is theoretical:** no JS caller exists yet, because the call sites are still in `jvmMain` until M3-15.

## Concurrency

- **Shared-state rule** (C3 row): every shared object is immutable-once-published or CAS-based.
  - JVM and native: the table's single `compareAndSet`.
  - JS: single-threaded.
  - `IdentityFirstCache` composes two such caches and has no state of its own.
- **Visibility:** argued from stdlib `AtomicReference` → `@Volatile` ("sees … all side effects that led to writing that
  value"). It does not rely on the JVM final-field freeze. The B6 argument moved verbatim into `CopyOnWriteWeakTable`'s
  KDoc.
- **Behaviour change on the JVM:** the equality cache may now compute twice on a lost race. `ConcurrentHashMap.computeIfAbsent`
  computed once. The `Cache` contract always allowed it ("the value can be re-computed at any time"), and every thread
  still observes the winner's value. The old `WeakKeyCacheTest` asserted compute-exactly-once under concurrency; its
  successor asserts `≥ keys` computations and one value per key everywhere, as B6's identity test does.

## What was measured

Nothing: the orchestrator runs the A/B. **Recommended A/B** (§9 confirmed, with one addition). Base = the commit before
this one. Every run is EA-off, serialized, and ≥ 3 invocations per side for any throughput delta under 10%:

```bash
./gradlew :benchmark:benchmarkAlloc -Pbench='micro\.PolymorphicMicroBenchmark' -Pparams='shapeCount=1000' \
  -PallocJmhArgs='-jvmArgsAppend -XX:-DoEscapeAnalysis'
./gradlew :benchmark:benchmarkAlloc -Pbench='micro\.NestedRecordMicroBenchmark' -Pparams='depth=8' \
  -PallocJmhArgs='-jvmArgsAppend -XX:-DoEscapeAnalysis'
./gradlew :benchmark:benchmarkAlloc -Pbench='micro\.SchemaInferenceMicroBenchmark' \
  -PallocJmhArgs='-jvmArgsAppend -XX:-DoEscapeAnalysis'
```

**What to expect from each run:**

- **`PolymorphicMicroBenchmark.readPolymorphic` at `shapeCount=1000`** is the headline. `PolymorphicResolver` runs per
  value, and a non-generic sealed descriptor is now an identity hit. That removes a `Key.Lookup` and a capturing lambda
  per value, so B/op should drop by roughly 2 objects × 1000. `readConcrete` and the writes are controls, expected flat.
- **`NestedRecordMicroBenchmark` at `depth=8`** is a regression guard. C2's memo already absorbs almost every
  `fieldCache` lookup, so expect it neutral.
- **`SchemaInferenceMicroBenchmark`:**
  - `warmCacheHit` is a stable-descriptor identity hit, so expect lower B/op and higher throughput.
  - `coldInference` and `newAvroInstance` are the addition: run the whole class, not only `warmCacheHit`. Each `Avro`
    now builds two small copy-on-write tables per `IdentityFirstCache` (and one per plain cache) instead of a
    `ConcurrentHashMap` + `ReferenceQueue`, so construction B/op can move either way. Record it, don't gate on it.

## What was rejected, and why

- **A second concurrent table for equality.** The brief forbids it, and B6's reasons (one concurrency argument to
  review) apply.
- **`putIfAbsent` returning the stored value** (compare with `===` to detect insertion). It was ambiguous when two keys'
  computations return the same shared instance, e.g. `emptyMap()` from `PolymorphicResolver`: a non-canonical instance
  could then be seeded after a race. Returning null on insertion is unambiguous.
- **Making `IdentityFirstCache` a `Cache`.** Its non-inline `getOrPut` would force a lambda allocation per call at every
  call site. `inline` plus an internal class gives the zero-allocation hit.
- **Delegating through `getOrPut { … }` everywhere and relying on escape analysis.** Native and JS have none, and
  platform-neutral cost is the metric (M1).
