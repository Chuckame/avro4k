# M3-08 — Defaults without `GenericData`

**Outcome:** done. No locked decision touched. Not api: `core.api` and `apache-interop.api` unchanged. The
`GenericData` APIs and the generic trees are **kept** (Q1 = move, M3-19); only the default-value path changed.
**Commit:** the one that adds this file (`git log -1 -- docs/plans/notes/m3-08.md`).
**Done inline** by the orchestrator (no agent).

## What changed

- **`DecodingStep.GetDefaultValue.defaultValue: Any?` → `JsonElement`.**
  - `RecordResolver` now keeps the json parsed from `@AvroDefault`: a value that looks like json is parsed, anything
    else becomes a string primitive, the same rule as before.
  - It no longer converts the json to `GenericData.Record`/`Fixed`/lists/maps. The implicit defaults become
    `JsonNull`, `[]` and `{}`.
  - `GetDefaultValue.schema` for an explicit default is now the union branch matching the json's kind
    (`resolveDefaultBranch`), so it is never a union. The implicit defaults already stored their branch.
  - `RecordResolver` no longer imports anything from `org.apache.avro.generic`.
- **New `core/src/jvmMain/.../internal/decoder/JsonDefaultDecoder.kt`.** It is an `AvroDecoder` over a
  `JsonElement` plus the reader schema, with composite decoders for arrays, maps, records and polymorphic types.
  - Each node is decoded against the schema at its position, and a union is resolved by the json's kind.
  - A record goes through the `RecordResolver` workflow of its reader schema, and its fields are read from the json
    object by name.
  - It lives in `internal/decoder/`, not `direct/` as the brief said, because both trees use it.
  - Its only Apache dependencies are the `Schema` model, which M3-11 flips, and `GenericData.Fixed` for
    `decodeFixed()`, which M3-12 turns into `ByteArray`.
- **`RecordDirectDecoder`** hands every `GetDefaultValue` read to a `JsonDefaultDecoder`, instead of
  `AvroValueGenericDecoder` over the converted value.
- **`RecordGenericDecoder`**, part of the generic tree that M3-19 moves, delegates defaults the same way:
  - `decodeSerializableValue` goes to the json decoder as a whole, so structures are covered.
  - Primitive reads keep going through the base class's `decodeValue()` table, fed by
    `JsonDefaultDecoder.decodeValue()`.
  - **So M3-19's minimal `@InternalAvro4kApi` set must include `JsonDefaultDecoder` (or a small `decodeDefault`
    entry point) and `DecodingStep`.**

## Semantics: preserved, and how that is proven

`JsonDefaultDecoderTest` (9 tests, `jvmTest`) keeps the **former path as its oracle**. It holds a verbatim copy of the
old `convertDefaultToObject`, fed to `AvroValueGenericDecoder` (still in core until M3-19). For every case, both
paths must return equal values, or both must fail.

- **Serializer matrix.** Every primitive and nullable, `Char` (with the `char` logical type), `ByteArray` (UTF-8,
  including `é` and `\u0000`), enums (known, unknown, `@AvroEnumDefault`), lists, maps (including `Int` keys and
  nullable values), nested records (including a json object missing a field), value classes, sealed types, and
  fixed/decimal/char schemas taken from annotated fields.
- **Cross-type matrix.** 13 `decode*` methods (including the deprecated `decodeValue()` and `decodeFixed()`), times
  11 schema types, times 7 default literals. This pins leniencies such as a boolean read from a string, an int from
  a long (exact), and a float from a double (exact).
- **Generic path:** `decodeFromGenericData` of a record with missing fields decodes the same defaults.
- **Mutation-checked.** 15 mutations of `JsonDefaultDecoder` and `RecordDirectDecoder` were each run against the
  suite, and 14 were killed. The survivor is the non-sequential index path of the list/map decoders, which kotlinx
  never takes: it always decodes collections sequentially.
- The existing oracles, `AvroDefaultEncodingTest` and the record-compatibility tests, pass unchanged.

### Deliberate differences, all fixes or unreachable in practice

1. **`currentWriterSchema` is never a union inside a default**, as `AvroDecoder`'s KDoc promises.
   - Before, the top level and the elements of a list in a nullable union saw the union.
   - `ArrayGenericDecoder` would throw on `union.elementType` for any element serializer that reads the schema (the
     backlog row). That bug no longer affects defaults. The row stays open for the generic-data API itself (M3-19).
2. **`RecordDirectDecoder.decodeEnum` on a default** decoded it with `Int.serializer()`, so `"B".toInt()` threw.
   - It is reachable when a hand-written composite deserializer calls `decodeInlineElement(…).decodeEnum(…)`.
   - It is now fixed and pinned by a test, which a mutation back to the old call fails.
3. **A record default with a json key that is not a field of the record** is ignored. It used to be an NPE at
   workflow resolution (`schema.getField(name).pos()`). Apache's default validation ignores extra keys too.
4. **Polymorphic lookup** uses the resolved branch. For a non-record, non-fixed default, the old path searched the
   whole union by name. This only differs for a sealed type whose default is a json primitive, which no test or
   known use exercises.
5. **When conversion errors are thrown.** A malformed nested default (e.g. `"1.5"` for an `Int`) now fails when the
   element is decoded, not when the workflow is resolved. Both happen in the first decode that meets the missing
   field, and the failure repeats on every decode, as before.

### Known limitation, unchanged

A field missing from a *nested* record default decodes as `null`, as before. It does not use that field's own
default, which Apache would use. Changing this means reading nested field defaults from the schema, which is better
done once M3-09 has made the reader schema an `AvroSchema` (`Field.defaultValue: JsonElement`).

## Performance

Not measured: **no benchmark decodes a missing field** (see `notes/m3-decomposition.md` §9).

- **Allocations.** One `JsonDefaultDecoder` per default read, where there used to be one `AvroValueGenericDecoder`.
  Structures allocate one child decoder per element. Before, they allocated one per structure plus the
  `GenericData` value built at resolution.
- **Parsing.** A primitive default's json content is now parsed on each read (`JsonPrimitive.int`), not once at
  resolution. It is a short string parse per missing field per record, accepted for a path that is not measured.
  If a consumer ever needs it, memoise the parsed primitive on the `GetDefaultValue` step.
- Per-value boundary and structural-equality rules: no schema conversion, and no `==`/`indexOf`/`contains` on a
  `Schema` or `Field`. The only comparisons are on the `Schema.Type` enum.

## For M3-19: sharing `GenericData` with the Confluent module (user remark, 2026-09-24)

Two `GenericData` layers exist today, and M3-19 is where they can meet:

- **core's generic trees.** `AvroGenericDataExtensions` with `internal/{encoder,decoder}/generic/*` converts
  Kotlin objects to and from `GenericData` trees. They are deprecated, and move to `apache-interop` in M3-19.
- **Confluent's own.**
  - `Serializers.kt`: `GenericRecordKSerializer`, `GenericFixedKSerializer`, `GenericEnumKSerializer`,
    `Utf8KSerializer`, `ByteBufferKSerializer` and the `AnySerializer` subclasses. They serialize `GenericData`/Java
    values through avro4k's encoders.
  - `AbstractAvro4kKafkaSerializer.getAnySchema`: **schema inference from runtime values** (`GenericContainer`,
    `ByteBuffer`, `Utf8`, `Collection`, `Map`, otherwise the value's serializer).

`confluent-kafka-serializer` already depends on `apache-interop` (M3-03). So M3-19 should decide whether the
Java/`GenericData` serializers and the value-based schema inference move into `apache-interop` next to the generic
trees, so that both modules share them rather than keep two copies. This is a decision for M3-19 (api on both modules),
or for B7 if it grows. M3-08 did not touch either layer, beyond the default delegation above.

## Validation against the Avro specification (2026-09-24, after the commit)

Checked against the spec's latest published version, **1.12.0**
(`https://avro.apache.org/docs/++version++/specification/`: Records → `default`, Unions, Schema Resolution), and against
Apache Java 1.12.1's own behaviour (`Schema.isValidDefault`, `ResolvingGrammarGenerator.encode`, `JacksonUtils`).
Every divergence below was run end to end with a throwaway test. The same bytes were read by avro4k and by Apache's
resolving `GenericDatumReader`, both with the reader schema avro4k generates. **All of them predate M3-08**: the
differential test shows the old `GenericData` path behaved identically. None is fixed yet, pending the user's decision.

The spec rules that apply:

- A default is "only used when reading instances that lack the field". The reader "should use the default value
  from its field". A reader field without a default, missing from the writer, is an error.
- The type table: null → null, boolean → boolean, int/long → integer, float/double → number, bytes/string/enum/fixed →
  string, record/map → object, array → array.
- "Default values for union fields correspond to the **first schema that matches** in the union." Before 1.12 this
  read "the first schema in the union".
- "Default values for bytes and fixed fields are JSON strings, where Unicode code points 0-255 are mapped to unsigned
  8-bit byte values 0-255", i.e. ISO-8859-1.

What conforms: when a default is used (writer lacks the field, reader has a default, otherwise an error), the type
table, null defaults, arrays, maps, enums, and the char logical type (stored as its int code, which is consistent).
avro4k's extensions stay outside the spec's scope. They are the Kotlin default when there is no Avro default
(`IgnoreOptionalElement`) and `implicitNulls`/`implicitEmptyCollections`. The implicit ones are also written into the
generated schema, so other readers see them.

The decoder's lenient conversions (a number read from a JSON string, and so on) **cannot be reached from a generated
schema**. Schema generation builds each field with Apache's validating `Schema.Field` constructor, which rejects any
default that does not fit the type table. So a leniency is not a divergence.

| # | Divergence | avro4k | Spec / Apache 1.12.1 |
|---|---|---|---|
| S1 | **bytes/fixed charset** — `@AvroDefault("ÿ") ByteArray` | `C3 BF` (UTF-8) | `FF` (code points 0-255 → bytes); Apache: `FF` |
| S2 | **union branch chosen by json kind only**: any json primitive takes the first bytes/fixed/string/enum/boolean/int/long/float/double branch. `["int","string"]` with `"foo"` | picks `int` → `NumberFormatException` | spec: first *matching* → `string`; Apache: `"foo"` |
| S3 | **union of records** — sealed `[Circle, Square]` with `{"side":2}` | picks the first record → fails | spec: first matching → `Square`; Apache also fails (its `isCompatible` accepts any record) |
| S4 | **nested record default missing a field that has its own default** — `{"a":1}` for `Inner(a, b = "dflt")` | fails (missing → `null`) | Apache: `b = "dflt"` (uses the nested field's default, as its own validation allows) |
| S5 | **`@AvroDefault("null")` on a non-null `String`** | fails | the generated schema says default `"null"` (a string); Apache: `"null"` |
| S6 | **fixed default of the wrong length** — `"\u0001"` for `fixed(4)` decimal | 1 byte → `1` | spec silent; Apache pads with zeros to the size → `[1,0,0,0]` → 16777216 |
| S7 | **the common model** (`AvroSchema.RecordSchema.Field` init) checks a union default against `types[0]` only (the pre-1.12 wording) | `toAvro4k()` of `["null","string"]` + `"foo"` throws `IllegalArgumentException` | Apache 1.12.1 parses it (any branch) |

**Root cause of S4 and S5:** avro4k decodes the *annotation*, not the reader schema's field default, which the spec
says to use. Schema generation transforms the annotation (`"null"` on a non-nullable → the string `"null"`, the char
code, number normalisation), and the decoder does not see those transformations. Once M3-09 makes the reader schema an
`AvroSchema` whose `Field.defaultValue` is a `JsonElement`, reading the default from there is cheap. It fixes S4 and S5,
and makes the known limitation above spec-conformant.

**Recommended fixes** (each a behaviour change, so they need the user's approval):

- S1 and S6: ISO-8859-1 for bytes and fixed, and pad or truncate fixed to its size as Apache does. S1 changes decoded
  values for non-ASCII bytes defaults; it goes in B8's migration guide.
- S2 and S3: pick the first branch the json is valid for, reusing the model's `isValidJsonForSchema`.
- S7: validate union defaults against any branch.
- S4 and S5: read defaults from the reader schema, in or right after M3-09.

### How the other Apache implementations behave (2026-09-24)

Read from the sources: `apache/avro` `main` at `209a373` (2026-09-21), and `apache/avro-rs` at `d6d93eb`, where Rust now
lives. "Read" is what the implementation does when a reader field is missing from the writer; "parse" is the check it
makes when a schema is loaded. The spec's union wording changed in **1.12.0**: 1.11.x said "the first schema in the
union", 1.12.0 says "the first schema that matches". The byte rule (code points 0-255) is the same in both.

| Impl | S1 bytes/fixed charset | S2/S3 union branch, read | union default, parse | S4 nested record missing a field | S6 fixed of wrong length |
|---|---|---|---|---|---|
| **Java** 1.12.1 = `main` (`ResolvingGrammarGenerator.encode`; the fast reader uses it through `GenericData.getDefaultValue`) | ISO-8859-1 | first branch **compatible with the json kind** (text → string/bytes/fixed, number → numeric, boolean, null; record/enum/array/map always compatible) | any branch | nested field's default, error if none | pads/truncates to the size |
| **C#** (`IO/Resolver.cs`) | ISO-8859-1 | branch 0 | — | nested field's default | **error** |
| **C++** (`Compiler.cc`, `JsonIO.hh`) | code points 0-255, **error** above `ÿ` | branch 0 | effectively branch 0 (the datum is built at parse) | **error** | not checked |
| **JavaScript** (`schemas.js`) | `'binary'` (latin1) | first type only | first type only (rejects others) | nested field's default | **error** |
| **Python** (`io.py`) | **UTF-8** (`str.encode()`) | `schemas[0]` | not validated ("TODO") | nested field's default | not checked |
| **Ruby** (`io.rb`, `schema.rb`) | raw json string (UTF-8) | `schemas[0]` | first branch only | nested field's default | not checked |
| **PHP** (`AvroIODatumReader.php`) | raw string (UTF-8) | index 0 | — | nested field's default | not checked |
| **Rust** (`avro-rs` `types.rs`, `field.rs`) | **UTF-8** (`into_bytes`) | `variants()[0]` | any branch | nested field's default | not checked |
| **Perl** (`BinaryDecoder.pm`) | parsed json used as-is, no conversion | none | `is_data_valid` | no | no |
| **C** (`resolved-reader.c`) | defaults **not supported**: a reader field missing from the writer is always an error ("TODO: Handle default values!") | | | | |
| **avro4k** (M3-08) | UTF-8 | first branch of the json kind, primitives not told apart | `toApacheSchema` side: Apache (any); `AvroSchema` model: first branch only | `null` | kept as is (wrong length) |

What this changes in the recommendations:

- **S1: follow the spec and Java (ISO-8859-1).** The ecosystem is split. Java, C#, C++ and JS follow the spec;
  Python, Ruby, PHP and Rust effectively use UTF-8. avro4k's users interoperate mostly with the JVM (Kafka,
  Confluent), and the spec is unambiguous. Code points above `ÿ` are undefined by the spec: C++ rejects them, while
  Java silently replaces them with `?`. **Recommend rejecting them** when the schema is generated, so no default can
  mean different bytes in different languages.
- **S2: at least match Java**, which picks the first branch compatible with the json *kind*. That alone fixes
  `["int","string"]` with `"foo"`.
- **S3: no implementation does "first that matches" for records.** Java takes the first record and fails; the others
  take branch 0. So a union default outside branch 0 **is not portable**: only Java and Rust accept it at parse, and
  only Java reads it correctly, and only for primitives. The portable fix belongs to schema generation: `ClassVisitor`
  already moves the null or char branch to the head of the union for the default; it should move **the branch the
  default matches** (e.g. `Square` for `{"side":2}`) to the head as well. Every implementation then reads it
  correctly. The read side should still pick the first branch the json is valid for, which is the spec's rule and a
  superset of Java's.
- **S4: use the nested field's default.** Java, C#, JS, Python, Ruby, PHP and Rust all do; only C++ errors.
- **S6: pad or truncate like Java.** The alternative is to reject it like C# and JS, but that would break the existing
  `AvroDefaultEncodingTest` case (`"\u0000"` for a `fixed(16)` decimal) and any user relying on it. Note that padding
  goes on the right, so for a big-endian decimal `"\u0001"` in `fixed(4)` means 2^24, not 1, exactly as Java reads it.
- **S7: validate against any branch**, as Java and Rust do (1.12). `toAvro4k()` must accept every schema Java accepts.
- **S5:** unchanged (reading defaults from the reader schema is what every implementation does).

## Follow-up applied (2026-09-24): S1, S2, S3, S6, S7, and S5 for top-level fields

Approved by the user after the validation above. S4 and, for nested values, S5 stay with M3-09.

- **One default, shared by generation and decoding** (new `J/internal/AvroDefaults.kt`, `toFieldDefault`).
  - `ClassVisitor` writes this json in the schema, and `RecordResolver` decodes the same json. It parses the annotation
    (json-looking values), normalizes numbers (`1.0` → `1`), turns `null` for a non-nullable field into the string
    `"null"`, and turns a char into its code.
  - Before, the decoder re-read the raw annotation, which is how S5 happened. It is now fixed for top-level fields
    (`@AvroDefault("null") val s: String` decodes `"null"`, as Apache does).
- **Validity** (`isValidDefaultFor`): Apache Java's rules on kotlinx json, plus the spec's 0-255 rule for bytes and fixed.
  A record's missing field is valid if it has a default; a union accepts any branch.
- **S1.**
  - The decoder maps each code point 0-255 of a bytes/fixed default to one byte (`defaultValueBytes`, platform-neutral).
  - Schema generation rejects a bytes/fixed default with a code point above 255, with a `SerializationException`. Java
    would silently write `?`, and the other implementations disagree on what it means.
  - String and enum defaults are still read as UTF-8 when decoded as bytes, as a string is written.
- **S6.** The decoder pads a fixed default with zeros or truncates it to the size, as Java does.
- **S2 read side.** `resolveDefaultBranch` takes the first union branch the json is valid for (spec 1.12). It throws if
  none is valid, which schema generation makes unreachable.
- **S3 generation side.**
  - After the existing ordering (null first for a null default, char first, null last otherwise), `ClassVisitor` moves
    the first branch the default is valid for to the head of the union. This covers another subclass of a sealed type,
    or `["int","string"]` with `"foo"`.
  - This way every implementation reads it, not only those that implement "first that matches".
  - A generated schema changes **only** where that branch was not already first, i.e. where Java or another
    implementation used to fail or misread the default. The existing schema tests are unchanged.
- **S7.** The common model's `RecordSchema.Field` accepts a union default matching any branch (commonMain).
  `toAvro4k()` of `["null","string"]` with default `"foo"` now converts, and round-trips to an equal Apache schema.

**Tests.**

- **New `AvroDefaultSpecTest`** (7 tests), with Apache Java as the oracle. avro4k and `GenericDatumReader` decode the
  same bytes with the generated reader schema, and both results must re-encode to identical bytes. It covers bytes
  `ÿ`/`é`, fixed padding, fixed truncation and a fixed decimal, the `€` rejection, the `[int,string]` union, sealed
  defaults (plain, nullable and first-branch), `"null"`, and a mix of char, number normalization, enum, list, map and
  nested record.
- **`JsonDefaultDecoderTest`.** Its oracle now carries exactly the approved changes, each marked `spec:` (ISO-8859-1
  bytes, fixed padding, char as its code). The serializer matrix feeds the new path through `toFieldDefault`, as
  `RecordResolver` does. The union test now pins "first that matches".
- **`AvroSchemaTest`** (common): `rejectsInvalidDefaults` now rejects a union default matching no branch, and the new
  `acceptsUnionDefaultsMatchingAnyBranch` pins the 1.12 rule.
- **`AvroSchemaApacheInteropTest`:** the interop case.
- **Mutation-checked.** 8 mutations, each one reverting a fix: the bytes charset, fixed padding, generation reordering,
  read-side branch choice, the generation rejection, `"null"`, record validity, and number normalization. All were

- **Counts.** `:core:jvmTest` 866 → 874. apache-interop 450 → 451. Confluent 72 = 72. Both `ACC` invocations are

**For B8's migration guide:**

1. A bytes/fixed default with non-ASCII characters now decodes to the spec's bytes (`"é"` → `E9`, was `C3 A9`).
2. A bytes/fixed default above `ÿ` is rejected when the schema is generated.
3. A fixed default of the wrong length is padded or truncated.
4. A union field whose default matches a later branch now has that branch first in the generated schema, which gives a
   new schema fingerprint. Before, such a default could not be read.
5. `@AvroDefault("null")` on a non-nullable string decodes `"null"`, as the schema always said.

**For M3-09:**

- Port `toFieldDefault`/`isValidDefaultFor`/`resolveDefaultBranch` to `AvroSchema`. The model's `isValidJsonForSchema`
  is the same rule minus the 0-255 check, which must stay generation-only so that `toAvro4k()` accepts every schema
  Java accepts.
- Then read nested defaults from the reader schema's `Field.defaultValue` (S4, and S5 for nested values).
