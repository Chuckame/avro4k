# M3-08 — Defaults without `GenericData`

**Outcome:** done. No locked decision touched. Not api: `core.api` and `apache-interop.api` unchanged. The
`GenericData` APIs and the generic trees are **kept** (Q1 = move, M3-19); only the default-value path changed.
**Commit:** the one that adds this file (`git log -1 -- docs/plans/notes/m3-08.md`).
**Done inline** by the orchestrator (no agent).

## What changed

- **`DecodingStep.GetDefaultValue.defaultValue: Any?` → `JsonElement`.**
  - `RecordResolver` now keeps the json parsed from `@AvroDefault`: a value that looks like json is parsed, anything
    else becomes a string primitive, the same rule as before.
  - It no longer converts the json to `GenericData.Record`/`Fixed`/lists/maps. The implicit defaults become
    `JsonNull`, `[]` and `{}`.
  - `GetDefaultValue.schema` for an explicit default is now the union branch matching the json's kind
    (`resolveDefaultBranch`), so it is never a union. The implicit defaults already stored their branch.
  - `RecordResolver` no longer imports anything from `org.apache.avro.generic`.
- **New `core/src/jvmMain/.../internal/decoder/JsonDefaultDecoder.kt`.** It is an `AvroDecoder` over a
  `JsonElement` plus the reader schema, with composite decoders for arrays, maps, records and polymorphic types.
  - Each node is decoded against the schema at its position, and a union is resolved by the json's kind.
  - A record goes through the `RecordResolver` workflow of its reader schema, and its fields are read from the json
    object by name.
  - It lives in `internal/decoder/`, not `direct/` as the brief said, because both trees use it.
  - Its only Apache dependencies are the `Schema` model, which M3-11 flips, and `GenericData.Fixed` for
    `decodeFixed()`, which M3-12 turns into `ByteArray`.
- **`RecordDirectDecoder`** hands every `GetDefaultValue` read to a `JsonDefaultDecoder`, instead of
  `AvroValueGenericDecoder` over the converted value.
- **`RecordGenericDecoder`**, part of the generic tree that M3-19 moves, delegates defaults the same way:
  - `decodeSerializableValue` goes to the json decoder as a whole, so structures are covered.
  - Primitive reads keep going through the base class's `decodeValue()` table, fed by
    `JsonDefaultDecoder.decodeValue()`.
  - **So M3-19's minimal `@InternalAvro4kApi` set must include `JsonDefaultDecoder` (or a small `decodeDefault`
    entry point) and `DecodingStep`.**

## Semantics: preserved, and how that is proven

`JsonDefaultDecoderTest` (9 tests, `jvmTest`) keeps the **former path as its oracle**. It holds a verbatim copy of the
old `convertDefaultToObject`, fed to `AvroValueGenericDecoder` (still in core until M3-19). For every case, both
paths must return equal values, or both must fail.

- **Serializer matrix.** Every primitive and nullable, `Char` (with the `char` logical type), `ByteArray` (UTF-8,
  including `é` and `\u0000`), enums (known, unknown, `@AvroEnumDefault`), lists, maps (including `Int` keys and
  nullable values), nested records (including a json object missing a field), value classes, sealed types, and
  fixed/decimal/char schemas taken from annotated fields.
- **Cross-type matrix.** 13 `decode*` methods (including the deprecated `decodeValue()` and `decodeFixed()`), times
  11 schema types, times 7 default literals. This pins leniencies such as a boolean read from a string, an int from
  a long (exact), and a float from a double (exact).
- **Generic path:** `decodeFromGenericData` of a record with missing fields decodes the same defaults.
- **Mutation-checked.** 15 mutations of `JsonDefaultDecoder` and `RecordDirectDecoder` were each run against the
  suite, and 14 were killed. The survivor is the non-sequential index path of the list/map decoders, which kotlinx
  never takes: it always decodes collections sequentially.
- The existing oracles, `AvroDefaultEncodingTest` and the record-compatibility tests, pass unchanged.

### Deliberate differences, all fixes or unreachable in practice

1. **`currentWriterSchema` is never a union inside a default**, as `AvroDecoder`'s KDoc promises.
   - Before, the top level and the elements of a list in a nullable union saw the union.
   - `ArrayGenericDecoder` would throw on `union.elementType` for any element serializer that reads the schema (the
     backlog row). That bug no longer affects defaults. The row stays open for the generic-data API itself (M3-19).
2. **`RecordDirectDecoder.decodeEnum` on a default** decoded it with `Int.serializer()`, so `"B".toInt()` threw.
   - It is reachable when a hand-written composite deserializer calls `decodeInlineElement(…).decodeEnum(…)`.
   - It is now fixed and pinned by a test, which a mutation back to the old call fails.
3. **A record default with a json key that is not a field of the record** is ignored. It used to be an NPE at
   workflow resolution (`schema.getField(name).pos()`). Apache's default validation ignores extra keys too.
4. **Polymorphic lookup** uses the resolved branch. For a non-record, non-fixed default, the old path searched the
   whole union by name. This only differs for a sealed type whose default is a json primitive, which no test or
   known use exercises.
5. **When conversion errors are thrown.** A malformed nested default (e.g. `"1.5"` for an `Int`) now fails when the
   element is decoded, not when the workflow is resolved. Both happen in the first decode that meets the missing
   field, and the failure repeats on every decode, as before.

### Known limitation, unchanged

A field missing from a *nested* record default decodes as `null`, as before. It does not use that field's own
default, which Apache would use. Changing this means reading nested field defaults from the schema, which is better
done once M3-09 has made the reader schema an `AvroSchema` (`Field.defaultValue: JsonElement`).

## Performance

Not measured: **no benchmark decodes a missing field** (see `notes/m3-decomposition.md` §9).

- **Allocations.** One `JsonDefaultDecoder` per default read, where there used to be one `AvroValueGenericDecoder`.
  Structures allocate one child decoder per element. Before, they allocated one per structure plus the
  `GenericData` value built at resolution.
- **Parsing.** A primitive default's json content is now parsed on each read (`JsonPrimitive.int`), not once at
  resolution. It is a short string parse per missing field per record, accepted for a path that is not measured.
  If a consumer ever needs it, memoise the parsed primitive on the `GetDefaultValue` step.
- Per-value boundary and structural-equality rules: no schema conversion, and no `==`/`indexOf`/`contains` on a
  `Schema` or `Field`. The only comparisons are on the `Schema.Type` enum.

## For M3-19: sharing `GenericData` with the Confluent module (user remark, 2026-09-24)

Two `GenericData` layers exist today, and M3-19 is where they can meet:

- **core's generic trees.** `AvroGenericDataExtensions` with `internal/{encoder,decoder}/generic/*` converts
  Kotlin objects to and from `GenericData` trees. They are deprecated, and move to `apache-interop` in M3-19.
- **Confluent's own.**
  - `Serializers.kt`: `GenericRecordKSerializer`, `GenericFixedKSerializer`, `GenericEnumKSerializer`,
    `Utf8KSerializer`, `ByteBufferKSerializer` and the `AnySerializer` subclasses. They serialize `GenericData`/Java
    values through avro4k's encoders.
  - `AbstractAvro4kKafkaSerializer.getAnySchema`: **schema inference from runtime values** (`GenericContainer`,
    `ByteBuffer`, `Utf8`, `Collection`, `Map`, otherwise the value's serializer).

`confluent-kafka-serializer` already depends on `apache-interop` (M3-03). So M3-19 should decide whether the
Java/`GenericData` serializers and the value-based schema inference move into `apache-interop` next to the generic
trees, so that both modules share them rather than keep two copies. This is a decision for M3-19 (api on both modules),
or for B7 if it grows. M3-08 did not touch either layer, beyond the default delegation above.
