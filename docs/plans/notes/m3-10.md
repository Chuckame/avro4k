## Algorithm and the spec rules applied

A recursive walk that appends to one `StringBuilder`. It follows Apache's `SchemaNormalization.build` branch by branch,
and the spec's rules ("Parsing Canonical Form for Schemas", 1.12) map onto it like this:

| Spec rule | Implementation |
|---|---|
| PRIMITIVES | Any primitive (`null`, `boolean`, `int`, `long`, `float`, `double`, `bytes`, `string`) is written as `"<type>"`, whatever its props. So `{"type":"string","logicalType":"uuid"}` becomes `"string"`. |
| FULLNAMES | Named types are written with `Name.fullName`. The model has already folded the namespace into it (inherited, overridden, emptied with `""`, or ignored because the name is dotted): the `Name` resolution happened at parse or generation time. |
| STRIP | Only `name`, `type`, `fields`, `symbols`, `items`, `values`, `size` are written. Doc, aliases (of types and of fields), defaults (field and enum), `order`, logical types and every custom prop are dropped. |
| ORDER | `name`, `type`, then `fields` / `symbols` / `size` for a named type; `type`, then `items` / `values` for an array or map; `name`, `type` for a field. |
| STRINGS | Names and symbols are written as-is, never escaped (see the deviations). |
| INTEGERS | `size` is written with `StringBuilder.append(Int)`: plain decimal, no leading zeros, no quotes. |
| WHITESPACE | None is ever written. |
| Named types | Written in full on the first occurrence, then as `"<full name>"`, recursive references included. The name is registered **before** the fields are walked, so a recursive record terminates. |

**Which "seen" set.** "Already written" is a `HashSet<String>` of **full names**, one per call, as in Apache (its `env`
map). It is not an `IdentitySet`, which the brief suggested for visited-sets. This is deliberate. Two distinct but equal
instances of a named type must give the same form as one shared instance. Apache's own parser shares instances, but
hand-built and generated `AvroSchema`s often don't, and an identity set would then write the second instance in full.
Apache writes it as a name, and so must we, or the fingerprint changes. Mutation 6 below shows the tests catch the
identity version. The set holds `String`s only, so the no-structural-equality rule holds: nothing compares an
`AvroSchema` or a `Field` structurally.

**CRC-64-AVRO.** This is the spec's table-driven Rabin fingerprint: `fp = (fp ushr 8) xor TABLE[(fp xor b) and 0xff]`,
starting from `EMPTY`, and the table is built with the spec's loop. `crc64Avro(String)` encodes UTF-8 inline, with no
`encodeToByteArray()` and so no array allocated per fingerprint. It reproduces the JVM's `String.getBytes(UTF_8)` byte
for byte, **including an unpaired surrogate written as `?`**. Kotlin's `encodeToByteArray()` gives `?` on the JVM but
U+FFFD (`EF BF BD`) on JS and native. A valid schema never contains an unpaired surrogate, but whatever the model holds
must fingerprint the same way on every platform, and the same as Apache.

## Apache vs. spec: deviations found

The differential test found **no difference between our output and Apache's**, and none between Apache's output and
the spec text, on any valid schema. Two points where the spec text is silent or looser, and Apache decides:

1. **No escaping at all (STRINGS).** The spec says to replace escaped characters with their UTF-8 equivalent. Apache
   writes names and symbols raw, so a name containing `"` or `\` would give invalid JSON. Apache's parser rejects such
   names by default, but the model does not validate names. We write them raw like Apache, so the bytes stay the same
   as Apache's.
2. **"Later occurrences" means the same full name, not the same definition.** The spec works on schema text, where each
   named type is defined once. Apache works on an object graph and keys by full name. We key by full name too (above).

## Shared state and publication

The only shared state is `private val CRC64_AVRO_TABLE: LongArray`, a top-level `val`. It is fully filled by
`buildCrc64AvroTable()` before the single write that stores it, and it is never written again: it is private, and only
read here. It is also never handed out, so no caller can mutate it.
- **JVM:** it is a static field of the file facade class `SchemaFingerprintKt`, assigned in its `<clinit>`. Class
  initialization runs under the JVM's initialization lock, and it happens-before any use of the class by any thread
  (JLS 12.4.2). So every reader sees the filled array. This is the same mechanism as Apache's `FP64` holder class.
- **Kotlin/Native:** a file's top-level properties are initialized on the first access to the file, under the runtime's
  per-file initialization guard (`CallInitGlobalPossiblyLock`): a thread that arrives during initialization waits for
  the initializer to finish. So no thread can observe a partly filled array.
- **JS:** single-threaded.

Nothing else is shared. The `StringBuilder` and the name set are per call, and the returned `ByteArray` is fresh on
each call.

## Performance

This is cold code, not benchmarked (no benchmark was run in this unit). Each call walks the whole schema once and
allocates one `StringBuilder`, its `String`, one `HashSet<String>`, and the 8-byte array for the bytes variant. The CRC
itself allocates nothing. Callers memoize per schema instance (M3-14), exactly as today's `AvroSingleObject` memoizes
Apache's result.

## What M3-14 must do to wire it into `AvroSingleObject`

1. Replace `SchemaNormalization.parsingFingerprint("CRC-64-AVRO", this)` (`AvroSingleObject.kt:58-60`) with
   `parsingFingerprintCrc64AvroBytes()` on the `AvroSchema` writer schema. It is a drop-in: the same 8 bytes, pinned by
   the differential test on the whole corpus.
2. Key `fingerprintCache` by identity (`WeakIdentityKeyCache<AvroSchema, …>`, still per instance), as the decomposition
   says. Equal-but-distinct schemas just miss the cache: that costs a recomputation, not a correctness problem.
3. Optional and simpler: cache the `Long` (`parsingFingerprint64()`) and write it with kotlinx-io's
   `sink.writeLongLe(fp)`, which matches the decode side's `readLongLe()`. That removes the mutable cached `ByteArray`
   and the "never escapes" argument in its KDoc.
4. The KDoc of `schemaRegistry` tells users to compute fingerprints with Apache's
   `SchemaNormalization.parsingFingerprint64`. Once core has no Apache dependency, a multiplatform user has no way to
   fingerprint a schema for their registry unless core exposes one. Exposing `AvroSchema.parsingFingerprint64()`
   (or similar) as public API is an **api** decision for M3-12/M3-14, and needs the user's approval. Until then, JVM
   users can keep using Apache through `apache-interop` (`toApacheSchema()`), which gives the same value.
