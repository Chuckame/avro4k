# M3-16 — Cross-platform golden fixtures

**Outcome:** done, tests only (no main code changed). **45 fixtures**, the same schema, bytes and values on jvm, js
(node and browser) and native (macosArm64, iosSimulatorArm64), checked against Apache Avro on the JVM. Writing them
found **six gaps**: five predate the migration (reproduced on `main`, recorded in `backlog-pre-existing-bugs.md`, not
fixed by rule), one is a new JS divergence (stringable floating-point numbers), migration scope: see "Findings".

`core/src/jvmTest/.../fixtures/GoldenFixturesApacheOracleTest.kt` (2 tests): each pasted schema parses to the
Apache form of the inferred one; each pasted hex is what Apache's `GenericDatumWriter` writes for the value (the value
reaches Apache through avro4k's generic-data encoder, so no byte comes from avro4k's binary encoder); Apache reads the
hex to the end, and reads every alternative encoding as the same datum; for the resolution fixtures, Apache's own
resolving reader (`GenericDatumReader(writer, reader)`) reads the hex into the same datum as the expected value.

How the goldens were produced: a throwaway JVM test wrote each fixture's inferred schema, Apache's bytes and the
`Any` rendering to a JSON file, pasted by a script, then deleted; the oracle test keeps them honest from now on. The
1,025-item block and the 256 bytes are written as expressions (`"8210" + "00".repeat(1025) + "00"`).

**`Any` rendering** (`renderGeneric`) is driven by the writer schema, not the runtime type: on Kotlin/JS every number
`is Int`, and `toString` writes floating-point numbers differently there (`-2` vs `-2.0`). Floats and doubles are
written by their bits, longs with an `L`. `AvroDuration` by its fields (its `toString` is wrong, finding 4).

## Findings

**Classified with the user on 2026-10-13.** Rule: a gap that predates the migration is not fixed during it, only
recorded (`backlog-pre-existing-bugs.md`). Each was re-run on `main` (`56dc7da8`) with a throwaway test:

| Finding | On `main`? | Where it goes |
|---|---|---|
| A non-nullable record property cannot read a writer union | yes, same error | backlog §1 (GitHub issue by the user) |
| No `int`/`long` → `float`/`double` promotion at decoding | yes, all four fail | backlog §2 (GitHub issue by the user) |
| Same-serial-name classes share `Avro.schema()`'s cached schema | yes | backlog §3, to revisit after the migration |
| `AvroDuration` fractional seconds (`PT0.5S` → 5 ms) | yes (`parse` → 4005 / 5, `toString` → `PT4.5S`) | backlog §4 (GitHub issue by the user) |
| Relative enum `@AvroAlias` not resolved at decoding | yes | backlog §5 |
| **Stringable `Float`/`Double` written differently on JS** | no (JS is new) | **migration scope**, fix proposed to the user |

The stringable floating-point divergence, measured on 2026-10-13 (`toString` on each platform; native is identical to
the JVM for every value tried):

| value | JVM, native | JS |
|---|---|---|
| `1.0`, `-0.0`, `9999999.0` | `1.0`, `-0.0`, `9999999.0` | `1`, `0`, `9999999` |
| `1.0E7`, `1.2345678E10`, `1.0E21` | `1.0E7`, `1.2345678E10`, `1.0E21` | `10000000`, `12345678000`, `1e+21` |
| `1.0E-4`, `1.0E-7` | `1.0E-4`, `1.0E-7` | `0.0001`, `1e-7` |
| `Double.MIN_VALUE` | `4.9E-324` | `5e-324` |
| `Float` 0.1 decoded (32-bit value) | `0.1` | `0.10000000149011612` |

Encoding goes through `value.toString()` in `AbstractAvroEncoder.encodeFloat`/`encodeDouble` (`STRING` writer). Decoding
parses either form on every platform, so only the written bytes differ. The `values written as strings` fixture omits
whole doubles until it is fixed.

Also observed, not a bug: decoded as `Any`, `timestamp-nanos` stays a `Long` on every platform while `timestamp-millis`
and `timestamp-micros` become an `Instant` (the default logical types have no `timestamp-nanos` entry).
