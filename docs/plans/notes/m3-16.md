# M3-16 — Cross-platform golden fixtures

**Outcome:** done, tests only (no main code changed). **45 fixtures**, the same schema, bytes and values on jvm, js
(node and browser) and native (macosArm64, iosSimulatorArm64), checked against Apache Avro on the JVM. Writing them
found **five gaps in avro4k**, all reproduced on `main` except the JS-only one, none fixed here (main-code changes,
outside a tests-only unit): see "Findings", each with a recommendation for the user.

`core/src/jvmTest/.../fixtures/GoldenFixturesApacheOracleTest.kt` (2 tests): each pasted schema parses to the
Apache form of the inferred one; each pasted hex is what Apache's `GenericDatumWriter` writes for the value (the value
reaches Apache through avro4k's generic-data encoder, so no byte comes from avro4k's binary encoder); Apache reads the
hex to the end, and reads every alternative encoding as the same datum; for the resolution fixtures, Apache's own
resolving reader (`GenericDatumReader(writer, reader)`) reads the hex into the same datum as the expected value.

How the goldens were produced: a throwaway JVM test wrote each fixture's inferred schema, Apache's bytes and the
`Any` rendering to a JSON file, pasted by a script, then deleted; the oracle test keeps them honest from now on. The
1,025-item block and the 256 bytes are written as expressions (`"8210" + "00".repeat(1025) + "00"`).

**`Any` rendering** (`renderGeneric`) is driven by the writer schema, not the runtime type: on Kotlin/JS every number
`is Int`, and `toString` writes floating-point numbers differently there (`-2` vs `-2.0`). Floats and doubles are
written by their bits, longs with an `L`. `AvroDuration` by its fields (its `toString` is wrong, finding 4).

## Findings (not fixed here; each needs the user's go-ahead)

1. **A non-nullable property inside a record cannot read a writer union** (`["null","int"]` into `Int`, `["long","int"]`
   into `Int`, …): `AvroSchemaMismatchException: Unsupported schema named 'union[null, int]' for decoded type of INT`.
   Cause: `AbstractAvroDirectDecoder` resolves a union only in `decodeSerializableValue` and `decodeNotNullMark`; a
   primitive record element goes through `decodeIntElement` → `decodeInt` (and the other primitive/`decodeString`/
   `decodeEnum` paths) without either. A whole value (`Avro.decodeFromByteArray(["null","int"], Int.serializer(), …)`)
   works. The Avro spec allows it (the writer's branch is resolved against the reader's type). Same on `main`.
   *Recommendation:* resolve the union at the start of each primitive `decode*` of the direct decoder (one type
   compare per value on the hot path; an A/B on `complex` read), with tests. The fixtures use nullable properties
   until then (`IntHolder`, `StringHolder`, `MaybeV2`).
2. **No `int`/`long` → `float`/`double` promotion** at decoding (`decodeFloat`/`decodeDouble` accept `FLOAT`,
   `DOUBLE`, `STRING` only), though the spec lists them; conversely, `double` → `float` is accepted (with an exactness
   check). Same on `main`. *Recommendation:* add the four promotions (`toFloat()`/`toDouble()`, as Apache's casts),
   with tests; a promotions fixture can then gain them back (they were in its first version: `16_777_217` → `16_777_216f`
   matches Apache).
3. **Two different classes with the same serial name can get each other's schema** from `Avro.schema()`. kotlinx's
   descriptor `equals` compares the serial name and the element descriptors' serial names and kinds, not the element
   names nor annotations, and `Avro.schemaCache` is backed by descriptor equality (identity first since M3-06; plain
   equality on `main`). Seen with `PaletteV1(known: ColorV1, unknown: ColorV1)` and `PaletteV2(known: ColorV2, …)`, both
   `@SerialName("…Palette")` and their enums both `"…Color"`: the reader schema came back with the writer's symbols.
   Rare in production (one process, one serial name, two shapes: schema-migration code and tests), silent when it
   happens. *Recommendation:* decide whether the equality layer is worth keeping for descriptors (it exists for generic
   descriptors created per call), or key it on something that includes element names and annotations.
4. **`AvroDuration.toString` and `AvroDuration.parse` disagree with ISO-8601 on fractional seconds.** `toString` does
   not pad the milliseconds (4,005 ms → `PT4.5S`, 3 ms → `PT0.3S`), and `parse` reads the digits after the point as a
   count of milliseconds (`PT4.5S` → 4,005 ms, `PT0.5S` → 5 ms; ISO and `java.time.Duration` read 4,500 and 500 ms). They
   round-trip with each other, so avro4k's own tests pass, but a duration from another producer, or a string-encoded
   duration (`@AvroStringable`), is misread by a factor of up to 100. Same on `main`. *Recommendation:* pad to three
   digits in `toString`, scale the fraction in `parse` (`"5"` → 500, `"05"` → 50), with tests; a behaviour change for
   anyone who stored avro4k's own output with a one- or two-digit fraction (`PT4.5S` meaning 4,005 ms): migration item.
5. **Cross-platform (JS only): a stringable `Double`/`Float` is written with the platform's `toString`**: `1.0` is
   `"1.0"` on the JVM and native but `"1"` on JS (and JS writes exponents differently: `1e+21` vs `1.0E21`). The bytes
   then differ between platforms. Found on JS; native matches the JVM for the values tried. *Recommendation:* format
   the stringable floating-point value in common code the way the JVM does (at least the `.0` suffix for whole values;
   the exponent form needs a decision), with a fixture per form. The `values written as strings` fixture omits whole
   doubles until then.

Also observed, not a bug: decoded as `Any`, `timestamp-nanos` stays a `Long` on every platform while `timestamp-millis`
and `timestamp-micros` become an `Instant` (the default logical types have no `timestamp-nanos` entry), and a relative
`@AvroAlias` on an **enum** is not resolved in the enum's namespace at decoding (schema generation and Apache do resolve
it): a qualified alias works, so the fixture uses one. That last one is close to a bug; it is listed with the findings
in the ledger for the user to classify.
