## What moved, what was deleted

  `apache-interop/src/main/kotlin/.../internal/{encoder,decoder}/generic/`. They are `internal` there, as before.
- Tests: `GenericDataMapEncodingTest` (13), `GenericDataArrayEncodingTest` (5, new in this unit),
  `GenericDataRecordEncodingTest` (2, new in this unit) → `apache-interop/src/test/kotlin/.../encoding/`, **unchanged**

Deleted (#320): `core/src/jvmMain/.../ListRecord.kt` (`Record`, `ListRecord`). `RecordGenericEncoder` now writes

## What core exposes now (`@InternalAvro4kApi`), and why

Each item is needed by a moved tree to behave exactly like core's binary encoders/decoders; anything trivially
copyable was copied instead (above).

| Symbol | Where | Why the generic trees need it |
|---|---|---|
| `AbstractAvroEncoder` (class, its abstract `currentAvroSchema` and `get*Encoder`/`encode*Unchecked` members now `public`) | `commonMain/internal/encoder/` | the generic encoder extends it: union resolution, logical types, the whole per-type writer-schema check |
| `AbstractPolymorphicDecoder` (class; `newDecoder` now `public`, the rest `protected`/`final` as before) | `commonMain/internal/decoder/` | `PolymorphicGenericDecoder` extends it: serial-name lookup through core's `polymorphicResolver` |
| `SerializationWorkflow` (`decoding`, `encoding`; constructor and `missingElements` stay `internal`) | `commonMain/internal/RecordResolver.kt` | the record workflow both record trees iterate |
| `EncodingWorkflow` + `ExactMatch`, `ContiguousWithSkips`, `NonContiguous`, `MissingWriterFields` (constructors `internal`) | same | `RecordGenericEncoder` dispatches on it |
| `DecodingStep` + `ValidatedDecodingStep`, `DeserializeWriterField`, `GetDefaultValue`, `SkipWriterField`, `IgnoreOptionalElement`, `MissingElementValueFailure` | same | `RecordGenericDecoder` reads the validated steps. The last three are not used by it, but **Kotlin forbids an `internal` class nested in an interface**; making them top-level or turning the sealed interface into a sealed class would rename or reshape core's hot-path types for nothing |
| `Avro.resolveRecordFields(writerSchema, descriptor): SerializationWorkflow` | `jvmMain/internal/AvroInternalExtensions.kt` | forwards to the `internal` `recordResolver.resolveFields` (keeps `RecordResolver` and `Avro.recordResolver` internal) |
| `Avro.enumDefaultIndex(enumDescriptor): Int?` | same | forwards to the `internal` `enumResolver` (the cached `@AvroEnumDefault` lookup) |
| `interceptedDeserializer(deserializer)` | same | forwards to the `internal` `SerializerLocatorMiddleware.apply` (`ByteArray`, `Duration`, `Uuid`, `Instant`) |
| `Avro.defaultValueDecoder(step: DecodingStep.GetDefaultValue): AvroDecoder` | same | M3-08's requirement: a missing field's default is decoded by core's `JsonDefaultDecoder`, which stays `internal` |

The four functions live in `jvmMain`, next to the existing `encodeWithApacheEncoder`/`decodeWithApacheDecoder`
internal entry points: only the JVM-only `apache-interop` calls them. The classes are `commonMain`, so they are public
on every platform (marked internal API). Nothing was exposed for `ListRecord` (deleted first). Already public before
and simply reused: `apacheToAvro4k`/`avro4kToApache` (not even those: the trees call apache-interop's own
`toAvro4k()`/`toApacheSchema()`).

**Perf:** visibility only; no JVM name changes (the members were never `internal`-mangled), no added dispatch on the
binary path. The four forwarding functions are one call each on the deprecated, unbenchmarked generic path.

## The backlog bug: `ArrayGenericDecoder` with a nullable union

The generic tree decoder does not resolve unions. A plain `java.util.List` (unlike a `GenericArray`, which carries its
own schema) in a nullable position got its `["null", array]` union as writer schema, and the element schema getter
(`writerSchema.elementType`) threw `Not an array: […]` as soon as anything read it: an element serializer reading the
writer schema (a decimal), a nested plain list (`beginStructure` builds its decoder from it), a custom serializer.
Fix, same shape as `MapGenericDecoder.mapSchema` (`notes/backlog-map-decoder-and-alloc.md`): the array decoder picks the
union's `ARRAY` branch once, at construction (`arraySchema`, falling back to the schema itself, never throwing there);
the getter stays lazy, so a decode that never reads the schema cannot start failing.

Test first (`GenericDataArrayEncodingTest`, 5 tests): a nullable plain list of decimals in a record, a `null` one, a
nullable plain list at the root, nullable plain lists of plain lists in map values, and a schema-capturing element
serializer expecting `int` twice. **On the old code 4 fail** with `RuntimeException: Not an array: ["null",{…}]`; the
`null` case passes (a guard). **Mutation-checked twice**: before the move in core (4 fail) and after the move in
apache-interop, by reverting the getter to `writerSchema.elementType` (the same 4 fail, the restored code passes).

## Confluent's GenericData/Java-value layer: not shared — recommendation

Considered as asked by `notes/m3-08.md`. **Not done**, because there are not two copies of one thing:

- The moved generic trees convert **Kotlin objects ↔ GenericData trees** (an `Encoder` that builds `GenericData`
  values, a `Decoder` that reads them), with no bytes involved.
- Confluent's layer (`GenericRecordKSerializer`, `GenericFixedKSerializer`, `GenericEnumKSerializer`,
  `Utf8KSerializer`, `ByteBufferKSerializer`, `ReflectKSerializer`/`GenericKSerializer`) are **`KSerializer`s of
  GenericData/Java values**, which write them to and read them from Avro **binary** through avro4k's own encoders,
  for `Any`-typed Kafka values; `getAnySchema` infers a registry schema from a runtime value (its errors even name
  Confluent's `NonRecordContainer`).

They are the two opposite sides of the same model, and share no code path. Moving Confluent's layer next to the trees
would not delete any code; it would turn ~6 Confluent `internal` classes plus the `CoreBridge` helpers they use
(`apacheWriterSchema`, `decodeGenericFixed`, `missingFieldEncodingException`, …) into `@InternalAvro4kApi public`
symbols of apache-interop with Confluent as their only consumer, i.e. a bigger internal surface for no deduplication.
Confluent's public API would be unaffected either way (all of it is `internal`).

**Recommendation:** keep them in Confluent. Revisit only if apache-interop gets a **public** feature that needs them,
e.g. decoding `Any` into `GenericRecord`s or encoding `GenericRecord`s with avro4k without a schema registry (a
`GenericData` serializers module). That is a new public API, so a user decision, best taken with B7 (Confluent's
own Apache exit), not here.
