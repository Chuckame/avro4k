# M3-21 — `uuid` decodes to `kotlin.uuid.Uuid` on the JVM too

**Outcome:** done. Not **api**: `core.api`, `apache-interop.api` and every other `.api` file unchanged (`apiCheck` and
`actionsBeforeCommit`'s `apiDump` leave no diff). GitHub #429. Reverses the 2026-09-25 M3-13 default "the JVM keeps
`java.util.UUID`" for `uuid` only; the java.time and `BigDecimal` defaults stay. No public name or shape changed, no new
public API.
**Commits:** the `feat!: decode the uuid logical type to kotlin.uuid.Uuid on the JVM too` commit and the
`docs(plans)` commit carrying this note.

## Core

- `commonMain/internal/Platform.kt`: `defaultLogicalTypes()` is now a **common** function: `duration` →
  `AvroDurationSerializer` and `uuid` → `KotlinUuidSerializer` (the entries every platform shares), plus a new
  `internal expect fun platformLogicalTypes()`. Still a new map on each call (`mapOf(…) + …`).
- `jvmMain/internal/Platform.jvm.kt`: `actual platformLogicalTypes()` = `decimal`/`big-decimal` → `BigDecimalSerializer`,
  `date` → `LocalDateSerializer`, `time-millis`/`-micros` → `LocalTimeSerializer`, `timestamp-millis`/`-micros` →
  `InstantSerializer` (java.time). `UUIDSerializer` is no longer a default.
- `nonJvmMain/internal/Platform.nonJvm.kt`: `actual platformLogicalTypes()` = `timestamp-millis`/`-micros` →
  `KotlinInstantSerializer`. Behaviour on JS/native unchanged.
- KDoc: `AvroBuilder.setLogicalTypeSerializer` (the defaults list: `uuid` shared, how to get `java.util.UUID` back with
  `setLogicalTypeSerializer("uuid", UUIDSerializer)`), `AvroConfiguration.logicalTypes`.
- `java.util.UUID` stays fully supported where a property is typed so (`@Contextual` or `UUIDSerializer`); only what
  generic decoding produces changes.
- **Encoding through `Any`** needed no change: `AnySerializer.serialize` looks the value's class up in the serializers
  module, where `Avro.Default` registers both `UUIDSerializer` (contextual, JVM) and `KotlinUuidSerializer` (contextual,
  and the middleware that swaps kotlinx's built-in `Uuid` serializer for it). Tested for string and `fixed(16)` writer
  schemas, and a decoded `Uuid` re-encodes to the same bytes.

## Opt-in finding (`@ExperimentalUuidApi`)

With the project's Kotlin 2.4.20, `kotlin.uuid.Uuid` is **stable**: `@SinceKotlin("2.4") @WasExperimental(ExperimentalUuidApi::class)`
on the class and on `parse`, `random`, `toByteArray`, `toJavaUuid`, `toKotlinUuid` (checked in
`kotlin-stdlib-2.4.20-sources.jar`; only `generateV4`/`generateV7*`/`LEXICAL_ORDER` are still experimental). No module
sets `apiVersion`, so nothing in this repo needs an opt-in (the existing `@file:OptIn(ExperimentalUuidApi::class)` lines
are now redundant, left as is).

Effect on a JVM user who never opted in:
- **Kotlin 2.4+:** none — receiving, naming or matching a `Uuid` needs no opt-in.
- **An older Kotlin API version** (e.g. a Kotlin 2.3 compiler, the oldest that can read avro4k's 2.4 metadata): receiving a
  `Uuid` as `Any` needs no opt-in (the type is never named); writing `is Uuid` / `as Uuid` or compiling **generated code**
  that types a property `Uuid` requires opting in to `kotlin.uuid.ExperimentalUuidApi` (an error-level marker). The
  generator does not add that opt-in to the generated files' `@file:OptIn` (it would need a per-file scan of the used types,
  and the E2E project compiles on Kotlin 2.4: its `kotlin("jvm") version "2.2.10"` is overridden by the plugin classpath's
  KGP 2.4.20, the compiled class carries metadata `mv=[2,4,0]`). Recorded in `b8-migration-items.md`; open to the user
  (see "For the user").

## kotlin-generator

It derives its built-in logical types from `Avro.configuration.logicalTypes` (core's JVM default), so generated `uuid`
properties became `@Serializable(with = KotlinUuidSerializer::class) Uuid`. No generator code changed.

Golden sources regenerated deliberately (`./gradlew :kotlin-generator:test` without `CI`, which runs
`updateExpectedGeneratedSources`), each reviewed — only the import lines and the property type change
(`UUIDSerializer`/`java.util.UUID` → `KotlinUuidSerializer`/`kotlin.uuid.Uuid`):
- `kotlin-generator/src/test/expected-sources/root-logicalType-uuid-string/TestSchema.kt`
- `kotlin-generator/src/test/expected-sources/root-logicalType-uuid-fixed/ns/TheUuid.kt`
- `kotlin-generator/src/test/expected-sources/fixed-types/fixed/ns/TheUuid.kt` (also compiled and round-tripped by
  `fixedTypesRoundTripTest`, green)

**Going back to `java.util.UUID`** uses the existing option (no new API): the gradle plugin's
`logicalTypes { register("uuid").asType("java.util.UUID", "com.github.avrokotlin.avro4k.serializer.UUIDSerializer") }`,
i.e. `KotlinGenerator(additionalLogicalTypes = listOf(LogicalTypeDescriptor("uuid", "java.util.UUID", "…UUIDSerializer")))`.
Tested twice:
- new generator case `kotlin-generator/src/test/resources/nested-logicalType-uuid-as-java-uuid.avsc` (string, `fixed(16)`,
  nullable and array `uuid`s), generated with that mapping (`KotlinGeneratorTest.resolveTestCaseLogicalTypes`, keyed on the
  `-uuid-as-java-uuid` suffix); new golden directory `expected-sources/nested-logicalType-uuid-as-java-uuid/`
  (`NestedLogicalTypeUuidAsJavaUuid.kt`, `FixedUuid.kt`), compiled by its own source set like every golden;
- the gradle plugin's `Avro4kGradlePluginIntegrationTest` now registers exactly the README's mapping and asserts the generated
  `UUIDSerializer`/`java.util.UUID` (it used to register a fake `your.own.CustomUuidKSerializer` for `kotlin.uuid.Uuid`, which
  is now the default type and would no longer prove the override).

**Gotcha:** the `CI` environment variable is not an input of `:kotlin-generator:test`, so after a non-CI (rewriting) run a
`CI=true` run is UP-TO-DATE and verifies nothing (`verifyGeneration` shows as skipped in the XML). The final ACC used
`--rerun` on the test tasks; the XML then shows `updateExpectedGeneratedSources` skipped and the 52 `verifyGeneration` cases run.

## Confluent

`GenericKSerializer`/`ReflectKSerializer` extend `AnySerializer`, so their generic decoding of `uuid` now gives `Uuid`
(root values and `GenericRecord` fields). No existing test pinned `java.util.UUID` (none referenced it). Encoding:
`getAnySchema` resolves both `Uuid` and `UUID` to `{"type":"string","logicalType":"uuid"}` and the values encode; a
`GenericRecord` decoded with a `Uuid` field re-serializes to the same Kafka bytes. Added tests below.

## For the user

- Generated code naming `kotlin.uuid.Uuid` does not compile on a Kotlin API version below 2.4 unless the project opts in to
  `kotlin.uuid.ExperimentalUuidApi` (or maps `uuid` back to `java.util.UUID`). Should the generator add
  `kotlin.uuid.ExperimentalUuidApi::class` to the `@file:OptIn` of files using `Uuid`? Not done: it changes generated output
  beyond this issue, and it depends on the minimum Kotlin version avro4k v3 supports, which is not decided in the plan.
