# M3-22 — `AvroSerializationException` hierarchy (step 1: design; step 2: implementation, at the end)

**Outcome:** design only, **waiting for the user's approval**. No source code was changed. All scratch work (a fuzz
test, a re-parenting experiment, an `apiCheck` run) was deleted afterwards; the tree is unchanged apart from this note.
**Base:** `v3/m2-foundation` at `c3ddcdcc`. Every `file:line` below is at that commit.
**Inputs:** GitHub #267 (schema-generation errors need the path to the failing element), #269 (bad bytes must fail
with a `SerializationException`, add a randomized test), `m3-decomposition.md` §3 M3-22, `m3-18.md`, `m3-14.md`, `m3-19.md`.

Shorthands: `C` = `core/src/commonMain/kotlin/com/github/avrokotlin/avro4k`, `J` = `core/src/jvmMain/…/avro4k`,
`NJ` = `core/src/nonJvmMain/…/avro4k`, `AI` = `apache-interop/src/main/kotlin/…/avro4k`.

## 0. Summary

```
kotlinx.serialization.SerializationException          (is an IllegalArgumentException)
└── AvroSerializationException                         open, new: the base, every avro4k failure
    ├── AvroSchemaGenerationException                  open, public now (was internal), + path   (#267)
    ├── AvroSchemaParseException                       open, new: AvroSchema.fromJsonString/fromJsonElement   (question 1)
    ├── AvroSchemaMismatchException                    open, new: the writer schema does not fit the Kotlin type or value
    │   └── MissingFieldsEncodingException             final, existing, re-parented
    ├── AvroMalformedDataException                     open, new: the bytes are not a valid encoding   (#269)
    ├── AvroValidationException                        open, new: validateSerialization, + path
    └── AvroDurationParseException                     final, existing, re-parented
```

- Two existing public exceptions are re-parented, none renamed. The JVM `.api` diff is additions plus two changed
  superclass lines (checked with a scratch `apiCheck`, §2.5). Binary compatibility was checked with a scratch
  experiment (§2.5).
- **#269, measured.** A seeded random-bytes fuzz (340,000 decodes in 3 runs) found **27 distinct throw points, of 8
  exception classes that are not `SerializationException`s**, reaching the caller of `Avro.decodeFromByteArray`: `EOFException`,
  `IndexOutOfBoundsException`, `IllegalStateException("Unreachable")`, `NumberFormatException`,
  `IllegalArgumentException`, `NoSuchElementException`, `DateTimeException`, and **`OutOfMemoryError`** from a
  5-byte collection count. With `validateSerialization = true` there are the same kinds, except the index ones (§1.3).
- Behaviour for user code: every `catch (e: SerializationException)` and `catch (e: IllegalArgumentException)` keeps
  catching everything it caught before, and more. Only code that catches `IllegalStateException`,
  `UnsupportedOperationException`, `IndexOutOfBoundsException`, `EOFException`/`IOException`, `DateTimeException`,
  `ArithmeticException` or `RuntimeException` (a `SerializationException` is not a `RuntimeException`) around avro4k
  calls stops catching some failures (§3).

### 1.3 What escapes from bad bytes today (#269): the fuzz

**Setup** (scratch kotest `StringSpec` in `core/src/jvmTest`, run with `./gradlew :core:jvmTest --tests …`, then
deleted). Each iteration picks one of 15 targets, builds an input, and decodes it with `Avro.decodeFromByteArray(writerSchema,
serializer, bytes)` twice, with `validateSerialization` off then on. Any `SerializationException` counts as expected,
and every other `Throwable` is recorded by class and first avro4k stack frame.
- Inputs: one third pure random bytes (0-47 bytes), two thirds a valid encoding of the target mutated 1-3 times (byte
  overwritten, truncated tail, byte inserted, byte removed).
- Targets: primitives (`Int`, `Long`, `Float`, `Double`, `Boolean`, `String`, `Char`, `ByteArray`, `Byte`, `Short`);
  collections (`List<String>`, `Map<String, Int>`, `List<record>`, `Set<Long>`); unions (nullable `Int`/`String`/record,
  sealed interface, enum); logical types (`BigDecimal` as `big-decimal`, `decimal` bytes and `decimal` fixed, Java
  `UUID`, `kotlin.uuid.Uuid`, `LocalDate`, `LocalTime`, `LocalDateTime`, Java and Kotlin `Instant`, Java and Kotlin
  `Duration`, `Period`); a record of strings read into `Int`/`Long`/`Double`/`Boolean`/`Char`/enum properties (avro4k's
  string conversions); and one-field records for `Char` from a string, `big-decimal`, `LocalDate`, `LocalDateTime`,
  `Instant`, `Period`, Java `Duration`, Kotlin `Duration` and `Instant`, and `IntArray` plus `List<Int>`.
- Runs: seed `20261010` × 20,000 iterations, seed `20261010` × 50,000, and seed `20261011` × 100,000 with the
  one-field targets added. 170,000 iterations, 340,000 decodes in all. The 50,000 run took 27 s wall clock, Gradle
  included.

## 2. Proposed hierarchy

### 2.1 Classes

All in one new file, `C/AvroSerializationException.kt` (package `com.github.avrokotlin.avro4k`, `commonMain`), except
the two existing classes, which stay where they are (`C/AvroEncoder.kt`, `C/serializer/AvroDuration.kt`) so that
nothing else moves. Explicit secondary constructors instead of default arguments: a default argument adds a synthetic
`$default` constructor to the `.api` (seen in the scratch `apiCheck`).

```kotlin
/** Base class of every failure avro4k reports for a schema, an encoding or a decoding. */
public open class AvroSerializationException(message: String?, cause: Throwable?) : SerializationException(message, cause) {
    public constructor(message: String?) : this(message, null)
}

/** A schema cannot be generated from a descriptor. [path] locates the element that failed, from the root type. */
public open class AvroSchemaGenerationException(message: String, public val path: String, cause: Throwable?) :
    AvroSerializationException("$message (at '$path')", cause) {
    public constructor(message: String, path: String) : this(message, path, null)
}

/** A schema's json is not a valid Avro schema. */
public open class AvroSchemaParseException(message: String?, cause: Throwable?) : AvroSerializationException(message, cause) {
    public constructor(message: String?) : this(message, null)
}

/** The writer schema does not fit the Kotlin type, or the value being encoded or decoded does not fit the other side. */
public open class AvroSchemaMismatchException(message: String?, cause: Throwable?) : AvroSerializationException(message, cause) {
    public constructor(message: String?) : this(message, null)
}

/** The input is not a valid Avro encoding of the writer schema: truncated, corrupted, or out of the encoding's bounds. */
public open class AvroMalformedDataException(message: String?, cause: Throwable?) : AvroSerializationException(message, cause) {
    public constructor(message: String?) : this(message, null)
}

/** With validateSerialization, a serializer's calls do not follow the writer schema. [path] is where. */
public open class AvroValidationException(message: String, public val path: String) : AvroSerializationException(message, null)

// re-parented, not renamed, constructors unchanged:
public class MissingFieldsEncodingException(message: String) : AvroSchemaMismatchException(message) { /* unchanged */ }
public class AvroDurationParseException(value: String) : AvroSerializationException("Unable to parse duration: $value")
```

- **`open` everywhere new.** `AvroSchemaMismatchException` must be `open`, since `MissingFieldsEncodingException`
  derives from it. The other families are `open` too, so that a later, finer subclass (say, a missing default) can be
  added under them without breaking anyone. `sealed` is not possible: apache-interop and users subclass or throw them
  from other modules. The two existing classes stay `final`.
- **Public constructors**, because apache-interop (another module) throws them, and because a custom `AvroSerializer`
  should be able to report "this writer schema does not fit" exactly like the built-in ones.
- **Opt-in markers:** the base is stable (no marker), since users must be able to `catch` it freely. The families are
  `@ExperimentalAvro4kApi`, like the two existing classes, so that their split can still change in 3.x (question 4).
- **Paths.** `AvroSchemaGenerationException.path` (#267) and `AvroValidationException.path` are always known where
  they are thrown. A path is **not** added to `AvroSchemaMismatchException`/`AvroMalformedDataException`: the
  non-validating decoder does not track where it is, and tracking it costs on every value (question 2). The validating
  decoder's malformed-data messages already contain the path (`m3-18.md`'s messages, unchanged).
- **The path in the message.** `AvroSchemaGenerationException` appends ` (at '<path>')` to the reason, so the stack
  trace a user pastes shows it (#267's complaint), and `message` starts with the old message. `AvroValidationException`
  takes the validator's message as is (it already reads `… at '<path>' …`).

### 2.2 Schema generation: how the path is built

- **Format**, from the root: the root serial name, then `.<property>` for a class property (the Kotlin element name,
  not the field name the naming strategy writes), `[]` for a list item, `{key}`/`{value}` for a map key or value,
  `<serial name>` for a subclass of a polymorphic type. A value class or a contextual descriptor adds nothing. Example
  for #267: `com.example.Wrapper.serializer` (a `KSerializer` property, contextual polymorphic, without subclasses), or
  `com.example.Order.lines[].product<com.example.Digital>.price`.
- **Carried in `VisitorContext`** (`C/internal/schema/VisitorContext.kt:26`) as a parent-linked, immutable `SchemaPath`
  node (internal), extended where the visitors already call `context.copy(…)` for each element (`ClassVisitor.kt:62`,
  `ValueVisitor.kt:74-86`, and the list, map and polymorphic visitors). One small object per visited element, during
  generation only, which runs once per descriptor and is cached. Rendered to a `String` only when an exception is
  thrown.
- **One boundary**, in `ValueVisitor.visitValue` (`ValueVisitor.kt:97`), the frame that every element goes through:
  `catch (e: Exception)` → rethrow as is if it is an `AvroSchemaGenerationException`, else throw
  `AvroSchemaGenerationException(e.message ?: e::class.simpleName, path, e)`. The innermost frame wraps first, so
  the path is the deepest one, and the outer frames pass it through. That covers the model `require`s, the custom
  `AvroSerializer.getSchema`s, `@AvroDecimal`/`@AvroDefault` checks and `EnumResolver`, without touching them. The
  direct throw sites listed in §1.2 throw `AvroSchemaGenerationException` with `context.path` themselves.
- `Avro.schema()` already caches per descriptor; a failure is not cached, as today.

### 2.3 Decoding: where each #269 escape is fixed

- **End of input**: one `try`/`catch (e: kotlinx.io.EOFException)` in `Avro.decodeWithValidation`
  (`C/internal/AvroCodecEntryPoints.kt:43`), the single entry point of every decode (byte array, `ByteBuffer`, `Source`,
  and apache-interop's `decodeWithApacheDecoder`, whose Apache decoder throws the same `java.io.EOFException` on the
  JVM) → `AvroMalformedDataException("Unexpected end of input: …", e)`. One `try` region per decode call, nothing per
  value. Question 5 covers what this means for `decodeFromSource`.
- **`readVarLong` at the end of input** (`KotlinxIoDecoder.kt:158`): `request(1)` → `require(1)`, like `readVarInt`,
  so it throws `EOFException` (mapped above) instead of reaching `error("Unreachable")`.
- **Union and enum indexes**: an explicit range check before indexing, at `AbstractAvroDirectDecoder.kt:136, 232, 252,
  307` and `AvroSchemaHelpers.kt:425`, throwing malformed data (`Malformed data: union index <i> out of range [0, <n>)
  for <schema>`). It is one int compare on the hot path (the list `get` already compares). Step 2 checks it with an A/B
  run of the complex read benchmark (unions and enums), with the usual rules (serialized, on AC power).
- **Collection counts** (`CollectionsDirectDecoder.kt:23-58`): a block count above `MAX_BINARY_LENGTH` (`Int.MAX_VALUE - 8`,
  the bound strings and bytes already use) is malformed data, so `.toInt()` can no longer truncate. Question 3 covers
  the capacity the count requests from kotlinx.
- **Value conversions** (§1.2, *value level, decoding*): each site catches the specific exception it calls into
  (`NumberFormatException`, `IllegalArgumentException`, `DateTimeException`, `ArithmeticException`,
  `MalformedURLException`) or uses the `…OrNull` form (`toIntOrNull()` …), and throws `AvroSchemaMismatchException` with
  a message naming the value, the writer type and the Kotlin type, plus the original as `cause`. These are new messages,
  on paths that threw something other than a `SerializationException` before.
- **Decimals**: `BigInteger(empty)` and `BigDecimal(null, …)` (`JavaStdLibSerializers.kt:382, 427`) → malformed
  data, checked before the call (Apache's message is kept as the reason). The inner `big-decimal` reader also rejects
  leftover bytes.
- **The validator** (`WriterSchemaCallValidator`): `mismatch(...)` takes the family as a parameter. Checks of a value the
  wrapped decoder *returned* (enum index, union index, item count) → `AvroMalformedDataException`; checks of a *call*
  → `AvroValidationException`. Messages unchanged.
- **apache-interop's `ApacheDecoderAdapter`**: each read is wrapped by a small inline helper that turns Apache's
  `AvroRuntimeException` (and so `SystemLimitException`, `AvroTypeException`) into `AvroMalformedDataException`, `cause`
  kept. Doing it per adapter call, rather than around the whole decode, means an `AvroRuntimeException` thrown by user
  code inside a custom serializer is not mislabelled. The JIT treats a `try` with no throw as free, and this adapter
  is not on core's path. `EOFException` is handled by the core entry point.

### 2.4 Message building stays lazy

- Every factory is a plain function that returns the exception, called only in the `throw` branch. It captures no
  lambda, and no string template runs on the success path (this is how the code is written today; step 2 only changes
  the class each one creates).
- The generation path is built from nodes that already exist, and rendered only on failure. The validator's path is
  already built only on failure (`m3-18.md`).
- No `override val message` getters: on Kotlin/JS, the underlying JS `Error`'s message (and so its stack text) is
  set at construction, so the message is passed to the constructor (§3.4). It is built once, at the throw, which is a cold path.
- The only additions to the hot path are the index range checks (one compare per union or enum value) and one `try`
  region per decode call. The perf statement in the spec ("throw paths only") holds, except for the index checks,
  which step 2 measures.

## 3. Compatibility notes (migration-guide item)

1. **`catch` blocks.** `SerializationException` extends `IllegalArgumentException`, so moving an
   `IllegalArgumentException` site (schema JSON parsing, the generation-time `require`s, `NumberFormatException`,
   `UUID`/`Uuid` text) to the hierarchy breaks no existing `catch`. Code that catches these **stops** catching the
   listed failures:
   - `IllegalStateException`: `AvroSingleObject` magic/version byte, `RecordResolver`'s ambiguous match, `readVarLong`'s
     "Unreachable";
   - `UnsupportedOperationException`: multiple `@AvroEnumDefault` (during generation), apache-interop's
     `AvroSchemaApacheConversion` defaults and `PolymorphicEncoder` null;
   - `IndexOutOfBoundsException`, `EOFException`/`IOException`, `DateTimeException`, `ArithmeticException`,
     `NoSuchElementException`: the decoding escapes of §1.3;
   - apache-interop: Apache's `AvroRuntimeException` from the Apache decoder.
   Each one now arrives as an `AvroSerializationException` subclass with the original as `cause`. The JVM-only
   `MalformedURLException` (a checked exception) also becomes unchecked.
2. **Messages.** Unchanged for every site that already threw a `SerializationException`, with two exceptions:
   `AvroSchemaGenerationException` gains the ` (at '<path>')` suffix, and the sites that threw something else get new
   messages (the original message stays reachable through `cause`). No existing test asserts a generation message
   (`MapEncodingTest`, `UnionSchemaTest` assert the type only).
3. **The generic trees in apache-interop** use the public classes directly (no internal API needed). Its copies in
   `GenericDataHelpers.kt` create the same classes as core's factories, so a `catch (AvroSchemaMismatchException)` sees
   both trees alike. Confluent needs no change: it does not catch avro4k's exceptions by class.
4. **KMP.**
   - Subclassing `SerializationException` and passing `(message, cause)` works on JVM, JS and native. The scratch
     hierarchy compiled for every target.
   - No `java.*` type is in the classes: `path` is a `String`, and the only type the decode boundary catches is
     kotlinx-io's common `EOFException`. The JVM-only exceptions (`DateTimeException`, `MalformedURLException`) are
     caught only in the `jvmMain` serializers.
   - On Kotlin/JS, the final message is passed to the constructor, never computed in an `override val message`,
     because the underlying JS `Error`'s message and stack text are set at construction.
   - Tests check types with `shouldThrow<T>`/`shouldBeInstanceOf<T>` (`is` checks), never `::class.qualifiedName`,
     which is `null` on JS.
   - On Kotlin/Native, a Kotlin exception that crosses into Swift/Objective-C still needs `@Throws`. That is not new,
     and not in scope.
5. **`b8-migration-items.md`** gets one item in step 2: the hierarchy, the re-parenting, the list in point 1, and the
   EOF behaviour of `decodeFromSource` (question 5).

## 5. Open questions for the user

1. **Schema JSON parsing: a family of its own?** *Recommended:* yes, `AvroSchemaParseException`
   (`fromJsonString`/`fromJsonElement` today throw a mix of `IllegalArgumentException` and json `SerializationException`s;
   catch-compatible, since both are `IllegalArgumentException`s). *Alternative:* leave parsing out of the hierarchy and
   keep `IllegalArgumentException`, treating a bad schema string as a bad argument.
2. **A path in decoding errors?** *Recommended:* not in this unit. Only validation and generation carry a path. The
   non-validating decoder would have to track its position per value, or rebuild it on unwind with a `try`/`catch`
   in each record and collection decoder (free on the JVM when nothing is thrown, but more code on every structure
   path). If wanted, that is a follow-up with its own benchmark. *Alternative:* add `path: String?` to
   `AvroSchemaMismatchException`/`AvroMalformedDataException` now, filled on unwind.
3. **The `OutOfMemoryError` from a collection count.** *Recommended:* fix it here, since the random-bytes test cannot
   pass reliably without it. Each array/map block decoder hands kotlinx at most a fixed chunk (e.g. 4,096 items) per
   `decodeCollectionSize`, and the existing block-merging loop (`AbstractAvroDirectDecoder.kt:76-83`) continues
   until the block's real count is used up. A truncated input then allocates at most one chunk before failing on
   end of input. Unchanged for collections under the chunk; one more merge per 4,096 items above it (primitive
   arrays copy on each merge, which is what multi-block arrays already pay). *Alternative:* only reject counts above
   `Int.MAX_VALUE - 8` (which fixes the truncation and the `IllegalArgumentException`), and leave allocation bounding
   to a later hardening unit. The fuzz test would then exclude collections or run with a small count bound. The CPU
   cost of zero-width items (§1.3) stays a known, documented limitation either way, as in Apache.
4. **Opt-in on the families?** *Recommended:* the base is stable; the families are `@ExperimentalAvro4kApi` for now,
   like `MissingFieldsEncodingException` and `AvroDurationParseException`. *Alternative:* all stable from 3.0, which
   commits to the split as designed.
5. **End of input on `decodeFromSource`.** *Recommended:* map it to `AvroMalformedDataException` everywhere (cause:
   the `EOFException`), as kotlinx-serialization's own formats do for truncated input. A caller reading datums back
   to back until the end of a stream checks `source.exhausted()` before each decode instead of catching
   `EOFException` (migration item). *Alternative:* keep `EOFException` for `Source` input (an I/O-level signal), and map
   it only for in-memory input (byte array, `ByteBuffer`).

## 6. User answers (2026-10-11) — the design as approved

1. **Yes**: `AvroSchemaParseException` for `fromJsonString`/`fromJsonElement`.
2. **No path** on decoding errors in this unit.
3. **Not the 4,096-item chunking** (each extra merge copies the whole collection for `Array` and primitive arrays, whose
   `toBuilder()` copies, so the cost is quadratic in the collection size). Instead, two of Apache Avro 1.12.2's guards:
   - **Count limit:** the total count of one collection, summed over its blocks, must stay within
     `MAX_BINARY_LENGTH` (`Int.MAX_VALUE - 8`); a negative count, an overflow, or a count that does not fit an `Int`
     is `AvroMalformedDataException` (today `.toInt()` silently truncates it).
   - **No up-front reservation above 1,024 items:** a block whose count is above 1,024 is decoded with
     `decodeSequentially() = false` (kotlinx then adds items one by one through `decodeElementIndex`, growing the
     collection as items arrive, with no `ensureCapacity(count)`); blocks of 1,024 items or fewer keep today's
     sequential path. Same result; the only cost is the collection's normal growth on large blocks (A/B on `lists`).
   Apache's two other guards (count × minimum bytes against the bytes left; a cap on zero-byte items) are deferred:
   `backlog-decoding-hardening.md`. The random-bytes test therefore keeps zero-byte item schemas (`array<null>`, …) out
   of its generated schemas, or bounds their claimed counts, and says why.
4. **Stable base, `@ExperimentalAvro4kApi` families.**
5. **`AvroMalformedDataException`** for end of input everywhere, `Source` included (cause: the `EOFException`).

### What changed, against the design

- **Hierarchy** exactly as §2.1 (explicit secondary constructors, no default arguments), stable base, families
  `@ExperimentalAvro4kApi`. `AvroValidationException.path` is the raw dotted path (`list[1].l`), empty for the root
  and after the end of the datum; the message keeps the quoted form (`at 'list[1].l'`, `at the root`).
- **Generation path** as §2.2. Deviation in the mechanism, same result: the sites avro4k throws itself during
  generation throw an internal `SchemaGenerationFailure` (an `AvroSerializationException`), which the boundary turns
  into `AvroSchemaGenerationException(message, path)` **without a cause**, instead of each site reading `context.path`
  (most of them, like the name validation, have no context). Every other exception (model `require`s, custom
  `getSchema`, `@AvroDecimal`, `EnumResolver`, `@AvroDefault` decimals, a contextual descriptor not found, a parse
  failure of `@AvroGenerated`'s schema) is wrapped with its cause. The root path is the root descriptor's serial name.
- **Schema parsing** as designed: the six messages, plus one wrap at `fromJsonString`/`fromJsonElement` of any
  `IllegalArgumentException` (json syntax, json accessors, model `require`s), cause kept.
- **Decoding** as §2.3 and §6: EOF mapped once in `decodeWithValidation` (and in `AvroSingleObject`'s header reads,
  which are outside it); `readVarLong` `require(1)`; range checks on union (decoder, polymorphic decoder, `skip`) and
  enum indexes; collection guards (below); value conversions through one helper, `convertDecoded`, which catches
  `Exception` around the conversion only (the read happens before it), so the JVM's checked `MalformedURLException` is
  covered without a JVM-only catch; decimals (empty unscaled value, a `big-decimal` ending before its scale or with
  bytes left after it). **Added, not in the inventory:** a negative byte size of a skipped block (`doSkipItems` passed
  it to `Source.skip`: `IllegalArgumentException`), and every json-default primitive conversion is wrapped
  (`convertingDefault`), not only the listed ones.
- **`AvroDefaults.defaultValueBytes`** (§1.2 listed it under generation) is only reached while decoding a default, so it
  is an `AvroSchemaMismatchException`; its generation counterpart is `ClassVisitor`'s check.
- **Validator:** `readValueMismatch`: the enum index, union index and negative counts are malformed data on the decoder,
  validation on the encoder; every other mismatch and `Incomplete datum` is an `AvroValidationException` with `path`.
- **apache-interop** as designed; `ApacheDecoderAdapter.reading { }` maps `AvroRuntimeException` and
  `InvalidNumberEncodingException` (an `IOException` in Apache 1.12.2, not an `AvroRuntimeException`).
- **`IllegalIndexedAccessError` of the collection block decoders** (§1.2 "stays"): gone, since those decoders now answer
  `decodeElementIndex` (needed for blocks above 1,024 items).

### Collection guards (§6 point 3)

- The block count is read in `AbstractAvroDirectDecoder.beginStructure` (no longer lazily in `decodeCollectionSize`, so
  that `decodeSequentially()` can depend on it; same bytes read in the same order) and checked by `checkBlockSize`:
  negative (including `Long.MIN_VALUE`, which stays negative once negated) or bringing the collection's total above
  `MAX_BINARY_LENGTH` → `AvroMalformedDataException`. The per-block callback lambda is gone (the count is passed to the
  block decoder's constructor).
- `MAX_PRESIZED_BLOCK_ITEMS = 1024` (`CollectionsDirectDecoder.kt`, its KDoc says why). Above it,
  `decodeSequentially() = false`: `decodeElementIndex` returns `0, 1, 2, …` relative to the block (kotlinx adds
  `startIndex`), then `DECODE_DONE`. For a map, kotlinx asks the value's index and requires the key's absolute index
  plus one, which only `beginElement` sees (the builder's size counts distinct keys, not the sum of the block counts),
  so `beginElement` records it (`pendingValueIndex`: one field store per map key, also on the sequential path).
- Positive check: with the threshold set to 0 (every non-empty block item by item), the whole `:core:jvmTest` passed
  except two tests of the new class that derive their sizes from the constant itself (a size of `-1`, and an empty
  block in the middle of a multi-block collection, which ends it).

### Hot path (for the orchestrator's A/B)

- `complex` read: `AbstractAvroDirectDecoder.decodeAndResolveUnion` (`:158`) and `readEnumSymbol` (`:168`), and the
  polymorphic decoder's union read: one range check per union and enum value. `decodeWithValidation` (`:53`): one `try`
  per decoded value.
- `lists` read: `beginStructure` (`:99`, `:110`): `checkBlockSize` (`:144`: two compares, two field stores per block)
  and no lambda allocated per block; blocks above 1,024 items go through `decodeElementIndex`
  (`CollectionsDirectDecoder.kt:49`, `:90`) instead of `readAll`, the collection growing instead of being pre-sized.
  Map keys: one store in `beginElement` (`:74`).
- `KotlinxIoDecoder.readVarLong` (`:164`): `require(1)` instead of `request(1)` (same buffer check; throws instead of
  returning false). `doSkipItems` (`:123`): one compare per skipped block of known size. `skip`
  (`AvroSchemaHelpers.kt:429`): one range check per skipped union.
- String-to-number conversions (`:192-244`): a `try` around the conversion, nothing else.
