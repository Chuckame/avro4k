## gradle-plugin and the multiplatform publication
The plugin adds `enforcedPlatform(avro4k-bom)` and `avro4k-core` to the user's `implementation`. The published root
`avro4k-core-local-SNAPSHOT.module` carries the `-jvm` variants (6 references to `avro4k-core-jvm`), so a JVM project
resolves the jvm artifact through Gradle module metadata. The E2E test compiles and runs generated code with only those
two, so generated code needs no `apache-interop` and no Apache Avro at runtime. `:gradle-plugin:test --rerun` passes.

## 1. Per-value `toApacheSchema()` in the generic serializers: kept, documented
`avro4kToApache` starts with `apacheByAvro4k.pairedWith(schema)`: a `WeakIdentityKeyCache.getOrNull` (identity probe of a
copy-on-write table, documented allocation-free) then `Link.get()` (an atomic read, plus a `WeakReference.get()` when the
partner is weakly held). No hashing, no `equals`, no allocation. The writer-schema nodes core hands the decoder come from
`toAvro4k()` of the registry's Apache schemas and are paired with them, so a per-value call hits. Hoisting would add a
second cache to keep in step with core's. Comment in `CoreBridge.kt` updated with this reasoning. No behaviour change.

## 2. `ThreadLocal<Schema>` in `SpecificAvro4kKafkaDeserializer`: scoping is right, a stale-value bug exists (pre-existing)
Per-instance, per-thread, set in `getDatumReader`, cleared in `deserialize`: no leak of the schema across instances (a
retained Apache schema per thread at most). But it is only cleared on success: see backlog item 12 in
`backlog-pre-existing-bugs.md` (reproduced with a scratch test on this branch; the code is identical on `main`, lines
164/254). Not fixed, per the working rules. Scratch test removed.

## 3. `Serializers.kt` `WeakKeyCache<Schema, SerialDescriptor>`: equality keys kept, documented
Apache's `Schema.hashCode` is cached in the instance and `equals` begins with `this == o`, so a repeated instance is a
hash read plus an identity hit. Equality also lets equal schemas that the registry parsed apart (e.g. different ids, same
shape) share one descriptor, which an identity key would not. Confluent's `CachedSchemaRegistryClient` keeps parsed schemas
per id, so the instance is usually repeated either way; I did not read its source (not in the Gradle cache here), so no
benefit test was written and no change made. The key set is bounded by the schema ids a consumer sees. Comment added.
