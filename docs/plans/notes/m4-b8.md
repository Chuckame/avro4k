## 2. klib ABI dump

`library-multiplatform-module-conventions.gradle.kts`: `@OptIn(kotlinx.validation.ExperimentalBCVApi::class)` +
`klib { enabled = true }` inside `apiValidation`. BCV stays at 0.18.2 (no newer version needed), works on this macOS
host: `./gradlew apiDump` produced `core/api/core.klib.api` (714 lines, one merged dump for js and 17 native targets; the
non-buildable-on-this-host targets are all buildable here, macOS compiles every Kotlin/Native target).

- The JVM dump stays `core/api/core.api` (BCV only splits per target when there are several JVM targets, as b0 found).
  **The JVM `.api` files did not change.**
- Reviewed: the only `InternalAvro4kApi` occurrence is the marker annotation class itself (public, also in the JVM dump).
  No `@InternalAvro4kApi` member, no `WithDoc` / `WithProps`, no `java.*` type, no Apache type. JVM-only serializers
  (`java.time`, `UUID`, `BigDecimal`…) are absent; `KotlinInstantSerializer` and `KotlinUuidSerializer` are present.
- Caveat: on a Linux CI runner the Apple targets cannot build, BCV infers their dump from the other targets. I could not
  run Linux here, so `apiCheck` on `ubuntu-latest` is untested; the pull-request workflow runs `check` there and will show
  it. If it reports a diff on the Apple sections, move the check to the macOS job.

## 3. Publication check (local, `publishToMavenLocal`)

Signing is skipped by the project for `version == "local-SNAPSHOT"` (the default in `gradle.properties`), so no key is
needed. Everything went to `~/.m2`.

Produced: `avro4k-core` (root: `.jar` metadata, `.module`, `.pom`, sources, javadoc, kotlin-tooling-metadata),
`avro4k-core-jvm`, `-js`, and native `-androidnativearm32/arm64/x64/x86`, `-iosarm64/iossimulatorarm64/iosx64`,
`-linuxarm64/linuxx64`, `-macosarm64`, `-mingwx64`, `-tvosarm64/tvossimulatorarm64`, `-watchosarm32/arm64/devicearm64/simulatorarm64`
(each a `.klib` + `.module` + `.pom`), `avro4k-apache-interop`, `avro4k-confluent-kafka-serializer`,
`avro4k-kotlin-generator`, `avro4k-bom`. Artifact ids are as planned.

POMs of the JVM modules: `avro4k-apache-interop` → `avro4k-core-jvm` (compile) + `avro` (compile);
`avro4k-confluent-kafka-serializer` → `avro4k-core-jvm` and `avro4k-apache-interop` (runtime, as v2 had core as
`implementation`), `avro` (compile); `avro4k-kotlin-generator` → `avro4k-apache-interop` and `avro` (runtime). They reference
`-jvm`, not the root: the dependency graph through the confluent artifact works for Maven.

**Problem found, verified with Maven 3.9 (dependency:tree + a Java `compile` against `Avro.Default`):** the root
`avro4k-core` POM listed only the common dependencies, at runtime scope, and no `avro4k-core-jvm`. A Maven user writing
`avro4k-core` (what every v2 Maven user has, and what the README said) got a jar without classes and no avro4k classes at
runtime either. Through `avro4k-confluent-kafka-serializer` it works (runtime scope, `-jvm`), but compile-time access to
`Avro` needed core declared directly. The BOM listed only the root `avro4k-core`.

**Fix (build config only, no public API impact):**

1. `core/build.gradle.kts`: the `kotlinMultiplatform` publication's POM gets a compile-scope dependency on
   `avro4k-core-jvm` (as kotlinx.coroutines and kotlinx.serialization do). Gradle consumers are unaffected (they follow the
   `.module` metadata and ignore the POM). A `checkMavenRootPom` task (hooked to `check`) fails if the generated POM loses it.
2. `bom/build.gradle.kts`: a constraint on `avro4k-core-jvm`, so Maven users get its version managed.

Verified again with Maven against `~/.m2` (scratch projects, not committed): BOM + `avro4k-core` now resolves
`avro4k-core-jvm` and compiles; BOM + `avro4k-core-jvm` + `avro4k-apache-interop` + `avro4k-confluent-kafka-serializer`
(no versions) resolves and compiles against `Avro` and `AvroObjectContainer`. (The host's Maven settings point to an
unreachable corporate mirror: the checks used a scratch settings file with Maven Central and a scratch local repository.)
Note for users: through the confluent artifact alone, core is runtime-only; the README says to declare core as well.

### Release workflow

- `release.yml` ran on `ubuntu-latest`: the Apple targets are disabled there, so a release would have published `core`
  without the ios/macos/tvos/watchos artifacts and a root `.module` listing variants whose artifacts do not exist. **Changed
  to `macos-latest`** (a macOS host builds every other Kotlin/Native target too, so one runner publishes the whole matrix).
- `main.yml` published the snapshot from the ubuntu job: same problem. **Split into a `publish-snapshot` job on
  `macos-latest`** that needs the `build` job (the tests stay on ubuntu). Its steps are the old ones, unchanged.
- Not changed: `pr.yml` (tests on ubuntu, Apple tests are skipped there), `codeql.yml`, `dependency-submission.yml`.
- Cost: macOS runners are billed at a higher rate, and `./gradlew build` in the release job now also runs the Apple test
  tasks where a simulator runtime exists. The `gh release create … ./*/build/libs/*.jar` step is unchanged and attaches the
  JVM jars only. None of this was run (no push).

## 5. Open questions for the user

1. **Versions matrix** in the README has no `3.0.0` row: I do not know the minimum Kotlin / API / kotlinx-serialization of
   v3 (built with 2.4.20, kotlinx-serialization 1.11.0, kotlinx-io 0.9.1). The `>= 2.0.0` row is left as is.
2. **A public fingerprint function** for the non-JVM platforms: `AvroSingleObject` needs a `Long -> AvroSchema?` registry
   keyed by the CRC-64-AVRO fingerprint, and `parsingFingerprint64()` is internal, so only the JVM can build the map
   (Apache's `SchemaNormalization`). A multiplatform single-object user must hand-roll the CRC. New API, so not done.
3. **`WithDoc` / `WithProps`** are `@InternalAvro4kApi` supertypes of public classes: fine for the dump, but a user can see
   `props`/`doc` members without an opt-in. Intended?
4. **Release on macOS**: confirm the runner change (cost, and that `build` on macOS should run before publishing), and
   whether the Linux `apiCheck` of the klib dump is acceptable on `ubuntu-latest` (see 2).
5. **Maven + Confluent**: through `avro4k-confluent-kafka-serializer` alone core is a runtime dependency (as in v2). Making
   it `api` would change the module's published scope, not its API; left as is.
