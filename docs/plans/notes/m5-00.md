# M5-00 — Multiplatform common benchmarks

**Status (2026-10-28):** built on branch `v3/common-benchmarks`, compiled and linked on the three targets, never run
(units never run benchmarks, §1 of `m5-decomposition.md`). The orchestrator's smoke run is the first execution of the
harness; the set-up and both measured methods of every row are already exercised once per platform by a unit test
(below).

## 1. What was built

A Gradle module `benchmark-common/`: Kotlin multiplatform, targets `jvm`, `js(IR) { nodejs() }` and `macosArm64`,
plugins `org.jetbrains.kotlinx.benchmark` 0.5.0 (as `benchmark/`), `kotlin("plugin.allopen")` (JMH's `@State`, which
`kotlinx.benchmark.State` aliases on the JVM) and `kotlin("plugin.serialization")`. It depends on `project(":core")` and
`kotlinx-benchmark-runtime:0.5.0`.

```
benchmark-common/
  build.gradle.kts
  src/commonMain/kotlin/com/github/avrokotlin/benchmark/common/
    simple/SimpleBenchmark.kt        recordCount = 1, 25
    complex/ComplexBenchmark.kt      clientCount = 1, 15
    lists/ListsBenchmark.kt          entryCount  = 100 (1 wrapper, 100 longs per entry, as benchmark/)
    internal/RandomData.kt           seeded generator
    internal/SimpleDataClass.kt      copy of benchmark/'s SimpleDataClass, SimpleDatasClass
    internal/ListWrapperDataClass.kt copy of benchmark/'s ListWrapperDataClass, StatsEntry, ListWrapperDatasClass
    internal/Clients.kt              common Client, Partner hierarchy kept, ClientsGenerator
  src/commonTest/kotlin/com/github/avrokotlin/benchmark/common/BenchmarkDataTest.kt
```

Each benchmark class has `read()`, which decodes the `ByteArray` encoded once in `@Setup`
(`Avro.decodeFromByteArray<T>(schema, data)`), and `write()`, which calls `Avro.encodeToByteArray(schema, value)`. Both
return their result: kotlinx-benchmark's generated JS and native descriptors take the method as a `T.() -> Any?` next to
a `Blackhole`, and JMH consumes return values, so returning is supported on all three targets and nothing is dead code.
No kotlinx-io anywhere. 10 rows per target: `simple` @1/@25, `complex` @1/@15, `lists` @100, each `read` and `write`.

Row names are `com.github.avrokotlin.benchmark.common.<workload>.<Workload>Benchmark.<read|write>`, so regexes filter by
workload (`\.simple\.`) or side (`\.read$`) as in `benchmark/`.

**Changes outside the module:**
- `settings.gradle.kts`: `include("benchmark-common")`.
- `build.gradle.kts` (root): `actionsBeforeCommit` skips `benchmark-common`. It collected `jvmMainClasses`,
  `jvmTestClasses` and `compileCommonMainKotlinMetadata` from every subproject, this one included (checked with
  `--dry-run` before and after).
- `kotlin-js-store/yarn.lock`: the JS benchmark runner needs the npm `benchmark` package (2.1.4, with `lodash` and
  `platform`). Without the lock update, `kotlinStoreYarnLock` fails every JS task ("Lock file was changed").

**Not published, not in `bom`, not in `actionsBeforeCommit`, no API dump:** the module applies none of the
`library-*-conventions` plugins (so no publishing, no binary-compatibility validator, no spotless, like `benchmark/`),
`bom` lists its constraints by hand and does not name it, and the root aggregate skips it. CI's `./gradlew check` and
`build` do reach it, as they reach `benchmark/`: on a Linux runner that compiles the JVM and JS sides and runs the 3
tests; on a Mac `build` also links the native release benchmark binary (~37 s). The release workflow's
`./*/build/libs/*.jar` glob would attach this module's jars to a GitHub release, as it already does `benchmark/`'s.

## 2. The common model

`Client` keeps every field of `benchmark/`'s, with common types where `benchmark/` has JVM ones:

| Field | `benchmark/` | here | Encoded as |
|---|---|---|---|
| `balance` | `BigDecimal?`, `@AvroStringable` | `String?` (`"123.4567"`, 4 decimals) | string, both |
| `registered` | `LocalDate?` (`LocalDateSerializer`) | `Int?`, days since the epoch, 1900–2009 | int (`date` logical type there, none here) |
| `GoodPartner.since`, `BadPartner.since` | `java.time.Instant` (`InstantSerializer`) | `kotlin.time.Instant` | long `timestamp-millis`, both |

`kotlin.time.Instant` uses core's existing **`com.github.avrokotlin.avro4k.serializer.KotlinInstantSerializer`**
(`core/src/commonMain/.../serializer/KotlinStdLibrarySerializers.kt`), named with `@Serializable(with = …)` like
`benchmark/` names `InstantSerializer`. It defaults to `timestamp-millis`. Every `Long` of milliseconds fits in
`kotlin.time.Instant`'s range, so `Instant.fromEpochMilliseconds(random.nextLong())` round-trips exactly. No compiler
opt-in was needed with Kotlin 2.4.20. Nothing in core changed.

The `Partner` sealed hierarchy (`GoodPartner`, `BadPartner`, enum `Stranger`, null) and `EyeColor` are kept. The
models and benchmark classes are public: kotlinx-benchmark's generated JS and native descriptors are public functions in
another compilation, which an `internal` benchmark class or return type fails to compile with. The generator stays
`internal`.

## 3. Seeding

`RandomData` wraps `kotlin.random.Random(139793881379292435L)`, `benchmark/`'s seed; each `@Setup` creates a fresh
one, so every trial and every platform gets the same values. A seeded `Random` is pure Kotlin (XorWow) on every
platform. Strings are drawn from a fixed alphabet with `nextInt`, not from Apache Commons' `RandomStringUtils`, so the
values are not `benchmark/`'s, but the nulls (by index), sizes and ranges are. Floats are only drawn as `nextFloat()`
(a multiple of 2^-24) or `nextInt(n * 1024) / 1024f`, both exact as a `Float`: a `Float` multiplied on JS is a double
rounded late, so `nextFloat() * 180f` could differ by one ulp from the JVM's. `lists` draws every entry from the one
generator, where `benchmark/` restarts its seed per entry (the same 100 longs repeated); the encoded size is the same.

**Proof of determinism:** `BenchmarkDataTest` runs each `@Setup`, `read()` and `write()` once outside the harness on
each platform, checks that `write()` and a re-encode of `read()` give the set-up bytes, and pins the size and FNV-1a
hash of the encoded payload. The same constants pass on all three targets (`:benchmark-common:jvmTest`,
`:benchmark-common:jsNodeTest`, `:benchmark-common:macosArm64Test`, 3 tests each):

| Row | Payload bytes |
|---|---|
| `simple` @1 | 114 |
| `simple` @25 | 2,772 |
| `complex` @1 | 462 |
| `complex` @15 | 48,589 |
| `lists` @100 | 96,324 |

## 4. Configurations and task names

| Configuration | Warmups × time | Iterations × time | Rows |
|---|---|---|---|
| `main` | 5 × 1 s | 5 × 1 s | all 10 |
| `smoke` | 1 × 1 s | 1 × 1 s | all 10 |
| `read` | 5 × 1 s | 5 × 1 s | `…\.read$` |
| `write` | 5 × 1 s | 5 × 1 s | `…\.write$` |

All in throughput mode, ops/s, text reports under `benchmark-common/build/reports/benchmarks/<configuration>/`.
The JVM runs one fork per row, kotlinx-benchmark's default when `jvmForks` is not set (`JvmBenchmarkRunner`), as in
`benchmark/`. A `main` run is about 10 rows × 10 s ≈ 2 min of measurement per target, plus set-up and, for native, the
link; `smoke` about 20 s per target.

| Target | `main` | `smoke` | `read` / `write` |
|---|---|---|---|
| JVM | `:benchmark-common:jvmBenchmark` | `:benchmark-common:jvmSmokeBenchmark` | `jvmReadBenchmark` / `jvmWriteBenchmark` |
| JS (Node.js) | `:benchmark-common:jsBenchmark` | `:benchmark-common:jsSmokeBenchmark` | `jsReadBenchmark` / `jsWriteBenchmark` |
| macosArm64 | `:benchmark-common:macosArm64Benchmark` | `:benchmark-common:macosArm64SmokeBenchmark` | `macosArm64ReadBenchmark` / `macosArm64WriteBenchmark` |
| all three, one after another | `:benchmark-common:benchmark` | `:benchmark-common:smokeBenchmark` | `readBenchmark` / `writeBenchmark` |

Every task whose name ends with `Benchmark` depends on `:benchmark:checkBenchmarkPower`, the AC power / Low Power Mode
guard of `benchmark/` (checked with `--dry-run`); the build-only tasks below do not.

Build without running:
- JMH jar: `:benchmark-common:jvmBenchmarkJar`
- JS: `:benchmark-common:compileJsBenchmarkProductionExecutableKotlinJs` (the run tasks use the production executable)
- native: `:benchmark-common:linkMacosArm64BenchmarkReleaseExecutableMacosArm64`
  (`build/benchmarks/macosArm64/classes/macosArm64Benchmark.kexe`, 3.4 MB)
- JVM and native together: `:benchmark-common:assembleBenchmarks` (it does not build the JS executable)

## 5. Native link time

Release mode, the plugin's default. `linkMacosArm64BenchmarkReleaseExecutableMacosArm64` alone, with its klib inputs
already compiled and no build cache: **36.5 s** (Gradle `--profile`), 41 s wall clock for the Gradle invocation. The
benchmark klib compiles in a few seconds. A native run task relinks only when core or this module changed.

## 6. Risks

- **JS timer resolution and harness.** kotlinx-benchmark runs JS rows through benchmark.js (the npm package added to
  the lock), which times with `process.hrtime` on Node.js and sizes its batches to the timer, so resolution itself is
  not the limit; benchmark.js's own cycles and V8's GC between iterations are. The `@1` rows are a few microseconds per
  op and the ones to watch. A longer `iterationTime` is the first knob if JS iterations spread widely.
- **No JIT on native, and V8's JIT on JS**: warmup matters on JS as on the JVM; the 5 × 1 s warmup was chosen like
  `benchmark/`'s, not measured.
- **Native GC.** Kotlin/Native's GC runs concurrently; rows that allocate a lot (`complex` @15 read, `lists`) can show
  wide iteration spread. `advanced("nativeGCAfterIteration", true)` is the knob if it does.
- **`main` on all targets in one task** (`:benchmark-common:benchmark`) runs them one after another, never in parallel,
  but it is one long task; per-target tasks are easier to schedule around the power guard.
- **Not comparable with `benchmark/`'s numbers.** Different values (same shape), `registered` without its `date`
  logical type, `balance` already a string, and `write` is `benchmark/`'s `writeToByteArray`. Compare the JVM rows here
  with the JS and native rows here, and each with itself across commits.
