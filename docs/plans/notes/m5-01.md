# M5-01 — One merge per single-block collection

**Outcome:** implemented, tests green on JVM, JS (Node) and macosArm64; not measured (the orchestrator measures it in
the read A/B). Internal code only: no API change (`core/api`, `apache-interop/api` clean), no new field on any decoder.

**Branch** `v3/collection-single-merge`, base `b6015cd4`, one commit (code, tests, this note).

## Problem

Avro writes a collection as blocks `count, items…, count, items…, 0`; avro4k and Apache write one block and the closing
`0`. `decodeCollectionBlocks` looped `deserializer.merge(this, result)` while the last block read was non-empty, so the
closing `0` cost a whole second `merge`:

- a second `ArrayBlockDirectDecoder`/`MapBlockDirectDecoder` from `beginStructure` (48 B each);
- kotlinx's `previous.toBuilder()` and `builder.toResult()`, which copy for arrays and primitive arrays
  (kx-ser 1.11.0 `CollectionSerializers.kt:27,40`):
  - `Array<T>` (`ReferenceArraySerializer`, `:196,198`): `ArrayList(this.asList())` then `toNativeArrayImpl`. On JDK 21
    that is an `Arrays$ArrayList` wrapper (16 B), `Arrays$ArrayList.toArray()` copying the array into an `Object[n]`,
    `ArrayList(Collection)` copying it again (its class is not `ArrayList`), the `ArrayList` (24 B), and the result
    `String[n]` (`Array.newInstance`): three arrays of `n` references;
  - `LongArray` (`PrimitiveArraysSerializers.kt`): `LongArrayBuilder(this)` (24 B), whose `init` grows the buffer to
    `max(10, 2n)` longs when `n < 10` (`INITIAL_SIZE = 10`), then `build()` = `buffer.copyOf(position)`, a new
    `LongArray(n)`;
  - `List`, `Set`, `Map` (`ArrayList`, `LinkedHashSet`, `LinkedHashMap`… builders): `toBuilder` is a cast of the
    previous result, `toResult` returns the builder. Only the block decoder is wasted.

## What changed

`core/src/commonMain/kotlin/com/github/avrokotlin/avro4k/internal/decoder/direct/AbstractAvroDirectDecoder.kt` only.

- **`decodeCollectionBlocks`** merges the first block, then, while the last block read was non-empty, reads the next
  block's count itself (`readNextBlockSize`: `arrayNext()`/`mapNext()` + `checkBlockSize(firstBlock = false)`, exactly
  what `beginStructure` called before), stops on `0`, and only otherwise hands that count to the next `merge`.
- **The count is handed over in the existing `decodedCollectionSize` field**, stored as its bitwise complement
  (`inv()`: a pending count of 1 is stored as -2), so a pending block is any value below -1. No field was added on
  purpose: `RecordDirectDecoder` is exactly 48 B today (12 B header + 16 B of base fields + 20 B of its own, compressed
  oops), and `MapBlockDirectDecoder` too, so any new `Int` or `Boolean` on `AbstractAvroDirectDecoder` would have grown
  both to 56 B: +8 B per record and per map block, eating into the saving (and making `simple` worse per record).
- **Array or map** for `mapNext()` vs `arrayNext()` is read from `currentAvroSchema.type`, which `merge` cannot change on
  this decoder (it only calls `beginStructure` on it; the items go to the returned block decoder), and which is the
  union branch already resolved by `decodeSerializableValue` for a collection in a union.
- **`beginBlock(isMap)`** (shared by the `ARRAY` and `MAP` branches of `beginStructure`): a pending count is taken as is
  (and `decodedCollectionSize` set back to it, so the loop sees a non-empty block); otherwise the old logic, unchanged:
  `readArrayStart()`/`readMapStart()` as a first block when `decodedCollectionSize == -1`, else
  `arrayNext()`/`mapNext()` as a next block. That last path is now reachable only when a serializer begins a list or
  map without `decodeSerializableValue` (a serializer delegating to `ListSerializer(...).deserialize(decoder)`, backlog
  entry 10, #548) after another collection on the same decoder; it was kept so that even that case keeps its codec
  calls.
- KDoc of `decodeCollectionBlocks` and `decodedCollectionSize` rewritten to describe the new behaviour.

### Codec calls, errors

The codec sees the same calls in the same order: `readArrayStart` (or `readMapStart`), the items, one `arrayNext` (or
`mapNext`) per further block, the closing `0` included. Only the Kotlin frame changes: a next-block count is now read
in `decodeCollectionBlocks` instead of inside the next `merge`'s `beginStructure`, after kotlinx's `toBuilder()` (which
touches no codec). `checkBlockSize` is called with the same arguments at the same point of the input, so the
hardening bounds and their messages (`Cannot read an array or map block of N items after M items…`, `Unexpected end of
input`, `negative item count`) are unchanged, and `ValidatingAvroBinaryDecoder` sees the same calls. Verified by the
JVM recording test below, run against the old and the new decoder.

## Cases checked

| Case | Why it is safe | Test |
|---|---|---|
| Empty first block | `decodedCollectionSize` is 0 after the first merge: no loop, no extra read | `empty collections decode`, recording `empty` |
| Record read as a map (`RecordAsMapDirectDecoder`) | `decodedCollectionSize` stays -1 (reset at entry): no loop | `records read as maps inside a collection split into blocks decode` |
| Nested collections | items are decoded on the block decoder `beginStructure` returns, which has its own state; the outer state on this decoder is untouched between merges | `nested`, `items` fields; recording `several blocks` |
| Collection in a record in a collection | the record decoder is a child of the block decoder, with its own state | `items: List<MergedItem>` with `tags` and `scores` |
| Collection in a union (array and map branch) | `decodeSerializableValue` resolves the union before `decodeCollectionBlocks`; `currentAvroSchema` is the branch | `maybeList`, `maybeMap`; recording `INDEX(..) MAP_START…` |
| Value class / inline item whose serializer calls `decodeSerializableValue` on the item decoder | `decodeInline` returns the item (block) decoder, whose own `decodedCollectionSize` is not the outer collection's | `value classes wrapping collections inside a collection split into blocks decode` |
| Root collection (`AvroValueDirectDecoder`) | same code path | `a top level LongArray and Array of String and map decode from several blocks` |
| Negative counts with a byte size | the codec returns the absolute count; unchanged | every `…Sized…` layout, recording `ARRAY_NEXT(2)` after a `-2` block |
| Malformed count in a later block | same `checkBlockSize` call | `a malformed count in a later block fails as it does in the first`, existing `CollectionBlockGuardsTest` |
| Missing closing block | `arrayNext()` hits the end of input, as before | `a collection whose closing block is missing fails at the end of the input` |
| Delegating serializer (`ListSerializer.deserialize` called directly) | old branch kept | recording `a list read through the list serializer's deserialize…` |

6. `a top level LongArray and Array of String and map decode from several blocks` (and empty ones)
7. `records read as maps inside a collection split into blocks decode` (and a root record read as a map)

9. `a collection whose closing block is missing fails at the end of the input`
10. `value classes wrapping collections inside a collection split into blocks decode` (the inner list is decoded on the
    item's own decoder, through `decodeInline` and `decodeSerializableValue`)

## Predicted effect (measured in the read A/B)

Deterministic objects no longer allocated, on the escape-analysis-off allocation rows (`-XX:-DoEscapeAnalysis`), JDK 21,
compressed oops, 12-byte headers, 8-byte alignment. `A(n)` = a reference array of `n` = `align8(16 + 4n)`;
`L(k)` = a `long[k]` = `16 + 8k`.

Per non-empty collection read in one block:

- every list, set or map: −48 B (one block decoder);
- `Array<T>` of `n` items: −48 − 16 (`Arrays$ArrayList`) − 24 (`ArrayList`) − 3·A(n) (two `Object[n]`, one `T[n]`);
- `LongArray` of `n` items: −48 − 24 (`LongArrayBuilder`) − L(n) (`build()`'s copy) − L(max(10, 2n)) when `n < 10`
  (the builder's grown buffer; from 10 items the builder keeps the previous array as its buffer).

Per workload:

| Workload | Non-empty collections per call | Predicted B/op |
|---|---|---|
| `simple` (`SimpleDatasClass`, @1, @25, @500) | the root `data` list (an `ArrayList`) | **−48** at every size (not per record) |
| `lists` (1 wrapper × E entries × 100 longs, `List<Long>`) | `data`, `entries`, E × `values`, all `ArrayList` | **−48·(E + 2)**: @100 −4,896; @10,000 −480,096 |
| `complex` (`Clients`, @1, @15, @200) | the root `clients` list, then per client `emails: Array<String>` (5–9), `phones: LongArray` (5–9), `tags: List<String?>` (5–24), `map: Map<String,String>` (10) | **−48 − Σ clients** (see below) |

Per `complex` client, with `n_e` emails and `n_p` phones, both uniform in 5..9 (`ClientsGenerator`):

- `emails`: 48 + 16 + 24 + 3·A(n_e) → 208, 208, 232, 232, 256 B for n_e = 5..9 (mean 227.2);
- `phones`: 48 + 24 + L(max(10, 2n_p)) + L(n_p) → 224, 248, 272, 296, 320 B (mean 272);
- `tags`: 48; `map`: 48.

That is 528 to 672 B per client, **≈ −595 B per client on average**, so ≈ −643 B @1, ≈ −8,976 B @15, ≈ −119,088 B
@200 (the exact figure is the sum over the seeded dataset's sizes). The decomposition's "~510 B" estimate missed the
second `Object[n]` copy that `ArrayList(Collection)` makes on JDK 21 and the `LongArrayBuilder`'s grown buffer.

`CollectionMicroBenchmark`: `readLongs` and `readRecords` −48 B at every size (one `List`); `readTwoCollections`
−48·(1 + 2·size): @10 −1,008, @1000 −96,048, @100000 −9,600,048 B.

**Should not move:** every write row (the encoder is untouched), every row of another library (Apache, Jackson…), and
read rows whose model has no array or map (the string, union, record and field-order micro-benchmarks). EA-on rows of
the reads above may drop by less than the EA-off figure or not at all, depending on what HotSpot already scalar-replaced;
time per op should improve slightly on collection-heavy reads (`lists`, `readTwoCollections`, `complex`), one virtual
`merge`, `beginStructure` and builder round trip fewer per collection. On JS and native, which have no escape analysis,
the same objects disappear (sizes differ).
