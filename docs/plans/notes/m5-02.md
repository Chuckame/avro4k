# M5-02 — Decoders reused per nesting level

**Outcome:** implemented, tests green on JVM, JS (Node) and macosArm64. Not measured: the orchestrator measures it in
the read A/B. Internal code only: no API change (`core/api` and `apache-interop/api` are clean).

**Branch** `v3/decoder-reuse`, base `c12fde49`, one commit (code, tests, this note).

## What changed and why

Before, `AbstractAvroDirectDecoder.beginStructure` built a new decoder for every structure:
- a `RecordDirectDecoder` per record (48 B, which also resolved its workflow in its constructor);
- an `ArrayBlockDirectDecoder` per array block (48 B);
- a `MapBlockDirectDecoder` per map block (48 B).

A list of N records cost N record decoders, and every record's collections cost one block decoder each.

Now each decoder keeps three lazily created child slots: `recordDecoder`, `arrayBlockDecoder` and `mapBlockDecoder`.
`beginStructure` takes the slot's instance and calls `reset(...)` on it. Kotlinx decodes depth-first, so a level only
ever has one structure begun at a time. A structure begun inside a child is begun by that child's own slots, so the
decoders of one decode call form a tree whose size depends on the depth of the type and the kinds at each level, not on
the data size. `PolymorphicDecoder`, `RecordAsMapDirectDecoder` and `JsonDefaultDecoder` still allocate per value, as
before. The polymorphic path is a later unit.

Files (all in `core/src/commonMain/.../internal/decoder/direct/`):
- `AbstractAvroDirectDecoder.kt`:
  - the three slots and the `inUse` flag (`protected`, `private set`);
  - `recordDecoder()`, `arrayBlockDecoder()` and `mapBlockDecoder()`;
  - `beginReuse()`, the base class's part of every reset;
  - `endStructure` clears `inUse`;
  - `noElementBegunError()`;
  - `beginStructure` calls `slot().reset(...)`.
- `RecordDirectDecoder.kt`:
  - the constructor now takes `(avro, binaryDecoder)`;
  - `reset(writerSchema, descriptor)` with the identity memo;
  - the decoding steps array is held directly, without the `SerializationWorkflow` around it;
  - the current step and the current field schema are nullable, behind getters that throw when unset, as `lateinit` did.
- `CollectionsDirectDecoder.kt`:
  - `ArrayBlockDirectDecoder.reset(arraySchema, blockSize)` caches `elementType`;
  - `MapBlockDirectDecoder.reset(mapSchema, blockSize)` caches `valueType`;
  - in both, the item or entry schema is nullable, behind a getter that throws when unset, as `lateinit` did;
  - `beginElement` still assigns the item schema for every item, and the key or value schema for every map element,
    because resolving a union overwrites it. It now writes the backing field directly, not through the virtual setter.

### Workflow memo

`RecordDirectDecoder.reset`:

```kotlin
if (writerRecordSchema !== this.writerRecordSchema || descriptor !== resolvedDescriptor) {
    decodingSteps = avro.recordResolver.resolveFields(writerRecordSchema, descriptor).decoding
    this.writerRecordSchema = writerRecordSchema
    resolvedDescriptor = descriptor
}
```

- **Scope.** One entry per slot. It is per-call state, as the shared-state rule allows: no pooling, no `ThreadLocal`,
  nothing shared. A homogeneous list never reaches `RecordResolver` after its first item.
- **Identity only.** Both halves use `===`. The previous schema is the decoder's own `writerRecordSchema`, so the memo
  needs only one extra field (`resolvedDescriptor`).
- **Two record types alternating on one slot.** For example a parent with `a: A, b: B` fields: the memo misses on each
  switch and falls through to `RecordResolver`'s 16-entry identity cache, which allocates nothing on a hit.
- **Keys assigned after resolving.** A resolution that throws (for example two reader fields matching one writer field)
  leaves the previous steps with their own keys. If the keys were assigned first, a record of the failed type begun again
  would hit the memo and be decoded with another type's steps. A test covers this, and so does a mutation check.

### Busy guard

`reset` ends with `beginReuse()`, which sets `inUse = true`. `endStructure` sets it back to `false`. The slot helper
reuses the kept instance only when it is not in use. Otherwise it builds a **fresh** instance and does not store it in
the slot (the slot keeps the busy one):

```kotlin
val kept = recordDecoder
if (kept != null && !kept.inUse) return kept
val decoder = RecordDirectDecoder(avro, binaryDecoder)
if (kept == null) recordDecoder = decoder
return decoder
```

How `endStructure` is called, checked in the kotlinx-serialization-core 1.11.0 sources (`*-sources.jar` in the Gradle
cache):
- `AbstractCollectionSerializer.merge` (`CollectionSerializers.kt:26-41`) calls `beginStructure`, then reads the items
  either through `readAll` (the `decodeSequentially` path) or through the `decodeElementIndex` loop. On both paths it
  then calls `compositeDecoder.endStructure(descriptor)`, without `try/finally`.
- `Decoder.decodeStructure` (`Decoding.kt:566-574`), which `ObjectSerializer`, `AbstractPolymorphicSerializer`, the
  `Pair`/`Map.Entry`/`Triple` serializers (`Tuples.kt`) and `InstantComponentSerializer` use, calls `endStructure` after
  its block, without `try/finally`. A `return@decodeStructure` still reaches it.
- Plugin-generated serializers have the same shape: `beginStructure`, then the sequential path or the index loop, then
  `endStructure` before building the object. There is no exception table: the bytecode of `Inner$$serializer.deserialize`
  was checked.

So a decode that throws never ends its structure, and kotlinx itself never begins two structures on one decoder.

The cases that do not follow the protocol stay correct, each tested:

| Serializer | What happens |
|---|---|
| begins a second structure on a decoder before ending the first | the second structure is decoded on a fresh decoder; the first keeps the slot |
| never calls `endStructure` | the slot stays busy for the rest of the call: every later structure of that kind at that level is decoded on a fresh decoder (allocating as before) |
| catches an error inside a structure and goes on with it | it keeps using its own decoder, which is still marked busy, so nobody else gets it |
| abandons a structure on an error, unended, and begins it again on the parent | the abandoned decoder is busy: the new attempt gets a fresh decoder |
| calls `endStructure` twice | harmless |

**Limit.** A serializer that **keeps using a composite decoder after calling `endStructure` on it**, while its parent
begins another structure of the same kind, would share that decoder. That breaks the kotlinx contract (`endStructure`
ends the structure), and no kotlinx or plugin serializer does it. It is the one misuse that is not guarded, and guarding
it would require one decoder per structure again.

**Why a `Boolean`, not a sentinel value.** The busy state could have been packed into an existing index (for example
`nextDecodingStepIndex = -1` once ended), which would save 8 B per record and per array block decoder (see the layouts
below). That would be clearer to keep apart, and this unit's decoders are allocated per call rather than per record, so
a `Boolean` was kept. If the A/B numbers make 8 B worth it, the index sentinel is the alternative, with these figures.

Notes on the audit:
- **Ordering.** Every reset assigns its own fields first and calls `beginReuse()` last. A reset that throws (only the
  record's resolution can) therefore leaves the decoder free and unchanged.
- **A state that only a reused decoder could have.** In a sequential map block, kotlinx never calls
  `decodeElementIndex`, so `pendingValueIndex` is left at the last value index. Before this change, the next block got a
  new decoder. Now, without the reset, a following non-sequential block (more than 1,024 entries) would return that
  stale index. A test covers it: a map in blocks of 3 and 1,100.
- **The throwing getters.** A new decoder failed (reading an unset `lateinit`) when asked for its field or item before
  one was begun: a serializer reading an element without `decodeElementIndex`, or asking for `currentWriterSchema`
  first. A reused one would otherwise have answered with the previous structure's state, for example a previous
  record's default value. The getters keep that failure, and compile to the same null check `lateinit` had
  (`getCurrentAvroSchema` is 13 bytes, against 16). The exception type is the one deviation: see the last section.
- **`decodedCollectionTotal`'s reset is an equivalent mutant.** Once `decodedCollectionSize` is -1, the next block read
  is a first block, and a first block overwrites the total before anything reads it. The reset is kept so that the reset
  stays complete if that ever changes.

## Tests added (16, `commonTest`, run on JVM, JS, native)

`core/src/commonTest/kotlin/com/github/avrokotlin/avro4k/encoding/DecoderReuseTest.kt` (new). Every round trip decodes
with `Avro` and `Avro { validateSerialization = true }`. The protocol-breaking serializers are decoded with `Avro` only,
because they read bytes in an order the validator rightly rejects.

1. `sibling records lists and maps decode at several depths`: a `Tree` of `Branch`es of `Leaf`s, with nullable records,
   lists and maps of records, lists of `Int` then of `String`, maps of `Int` then of `Boolean`, lists of lists, maps of
   maps and maps of lists. Decoded alone and as a list of three trees.
2. `a recursive type decodes six levels deep`: `Node(value, children: List<Node>, byName: Map<String, Node>, next: Node?)`,
   six levels, siblings at every level.
3. `two record types alternating as fields of one parent decode`: `a: RecA, b: RecB, a2, b2`, a list of pairs, a list
   of each.
4. `records of one writer schema read into two reader types in turn decode`: one `Shared` schema instance read into
   `OnlyX` then `OnlyY`, as fields and as lists. This exercises the descriptor half of the memo.
5. `a list of records whose writer type alternates through a union decodes`: `array<[First, Second]>` (fields in
   another order) read into `List<XY>`, in blocks 2, -3, 1, and the nullable `[null, First, Second]` into `List<XY?>`.
   This exercises the schema half of the memo.
6. `maps of lists of records decode`.
7. `collections split into several blocks decode on one block decoder per level`, hand-written blocks:
   - records in 1, -3, 1;
   - a map in 2, 1;
   - a list in 1,100, -1,030 and a map in 1,100, 1,050, both above the presized limit, so the indexes are counted by the
     block decoder;
   - a map in 3, 1,100 (sequential, then not);
   - lists of lists in single-item blocks.
8. `a serializer beginning a second structure before ending the first decodes both`: at the root, as a record field
   between records of the same kind, and as list items (two records per item).
9. `a serializer beginning a second list or map before ending the first decodes both`.
10. `a serializer that never ends its structures decodes`: as fields, list items and map-of-list items, with ordinary
    siblings after them.
11. `a serializer catching a decoding error inside a structure goes on decoding`: one serializer catches a mismatch
    (`decodeBooleanElement` on an int, which fails before reading) and goes on in the same structure. Another abandons
    the structure on that error and decodes the record again on the parent. Used as fields and list items.
12. `successive structures of one kind are decoded by one decoder`: the record decoders of a list's items are one
    instance (`===`). When the serializer never ends them, each is a new one. Run against `c12fde49`'s decoders, this
    test fails, by design. So does 13, but only because the exception type changed (see the last section). The 14
    others pass there too: they pin behaviour, not the implementation.
13. `a reused decoder knows no field or item before one is begun`: a record, a list and a map asked for
    `currentWriterSchema`, and a record asked for an element, before any is begun. Checked at the root (new decoder) and
    after a sibling of the same kind (reused decoder, the previous record ending on a default value).
14. `a list read by a delegating serializer on a reused record decoder starts a new collection`: a
    `ListSerializer.deserialize` delegate (the backlog-10 path) on each record of a list, with validation.
15. `a missing reader field names the writer schema of its record`.
16. `a record whose fields cannot be resolved fails again when begun again`.

## Object layouts (JVM, compressed oops, 12-byte headers, 8-byte alignment)

Measured with `Unsafe.objectFieldOffset` on the compiled classes (JDK 21.0.11), before and after.

| Class | Before | After | Fields after |
|---|---:|---:|---|
| `RecordDirectDecoder` | 48 | **72** | base 32 B (2 ints, `inUse` + 3 B padding, `avro`, `binaryDecoder`, 3 slots) + `nextDecodingStepIndex`, `writerRecordSchema`, `resolvedDescriptor`, `decodingSteps`, `decodingStep`, `fieldSchema` (24 B): 68, rounded up to 72 |
| `ArrayBlockDirectDecoder` | 48 (44 used) | **64** | base + `blockSize`, `nextItemIndex`, `elementType`, `itemSchema`: 60, rounded up to 64 |
| `MapBlockDirectDecoder` | 48 | **64** | base + `blockSize`, `decodedEntries`, `pendingValueIndex`, `valueType`, `entrySchema`: 64 |
| `AvroValueDirectDecoder` (root, and one per polymorphic value) | 32 | **48** | base + `currentAvroSchema` |
| `RecordAsMapDirectDecoder` (rare) | 40 | 56 | base + 3 |

The base class grows by 16 B: 3 slot references, plus `inUse` with its padding. With no `inUse` (the index sentinel
above), the record decoder would be 64 B and the array block decoder 56 B. The map block and value decoders would not
change.

Native and JS, estimated rather than measured:
- **Kotlin/Native**: 8 B header, 8 B references, 8-byte alignment. The record decoder goes from ≈72 to ≈104 B, the
  array block decoder from ≈56 to ≈88, the map block decoder from ≈64 to ≈88, and the value decoder from ≈40 to ≈72.
- **JS (V8 without pointer compression)**: about 24 B plus 8 B per property. The record decoder goes from 9 properties
  (≈96 B) to 14 (≈136 B), the array block decoder from 8 to 12, the map block decoder from 9 to 13, and the value
  decoder from 5 to 9.

Neither platform has escape analysis, so each object these platforms no longer allocate is saved in full.

## Predicted effect (measured in the read A/B)

These are escape-analysis-off allocation rows (`-XX:-DoEscapeAnalysis`), JDK 21, with the layouts above, counted on top
of M5-01's corrected numbers (`m5-01.md`), that is with the closing-block decoder already gone. They count decoder
objects only. Nothing else in the read path changes:
- the same codec calls;
- the same kotlinx builders;
- `RecordResolver` is no longer called on a memo hit, but it allocated nothing on a hit before either.

| Workload | Decoder tree | Before | After | Δ B/op |
|---|---|---:|---:|---:|
| `simple` @N (`SimpleDatasClass` → `List<SimpleDataClass>`) | root value, outer record, 1 array block, item records | 32 + 48 + 48 + 48·N | 48 + 72 + 64 + 72 = 256 | **128 − 48·N**: @1 **+80**, @25 **−1,072**, @500 **−23,872** |

| `complex` @C (`Clients` → `List<Client>`) | root, `Clients`, `clients` block, C × (client record + `emails`/`phones`/`tags` blocks + `map` block) + partners | 128 + 240·C + partners | 384 + partners | **256 − 240·C + 40·g + 16·s** |

For `complex`, g is the number of `GoodPartner`/`BadPartner` partners and s the number of `Stranger` partners (an
enum: a value decoder with no record decoder). A polymorphic value still builds a new `AvroValueDirectDecoder`
(32 → 48 B) and, for a record subtype, a new record decoder (48 → 72 B) in that value decoder's own slot: +40 B per
Good/Bad partner and +16 B per Stranger, until the polymorphic unit reuses them. With g ≈ C/2 and s ≈ C/4 that is
**≈ 256 − 216·C**:
- @1: between **+16 and +56**, depending on the first client's partner;
- @15: ≈ **−2,984**;
- @200: ≈ **−42,944**.

The exact figure follows from the seeded dataset's partner mix.

The rows that grow are the ones with no repeated structure at any level: `NestedRecord`, flat records, `simple` @1,
`complex` @1 and `readLongs`. The fixed per-call cost of the slots and the larger decoders is what the design accepted
(§3: "about 5–10 small objects"). `readPolymorphic` grows per value only because its per-value decoders are larger.

**Should not move:**
- every write row (the encoder is untouched);
- every row of another library;
- generic-data and Apache-interop rows;
- schema inference.

**Throughput** is likely within noise on the JVM, EA on, as the decomposition expected. `RecordResolver`'s identity
cache scan is skipped on a memo hit, `decodeElementIndex` reads one field fewer per element, and the `elementType`/
`valueType` cast moves from once per item to once per block. On the other side, `beginStructure` gains a slot load and
a busy check. On JS and native, which have no escape analysis, the same objects disappear, at the sizes estimated above.

## Deviations and things to review

- **Misuse fails with `IllegalStateException`, not `UninitializedPropertyAccessException`.** `currentAvroSchema` and
  the current step became nullable fields behind getters, because a `lateinit` cannot be unset. The getters cannot throw
  `UninitializedPropertyAccessException`, as the `lateinit` did: the class is internal in the Kotlin/Native
  stdlib, so common code cannot build it (and a common test cannot name it). They throw an `IllegalStateException`
  instead, saying that no field or item is begun. Only a serializer that reads before `decodeElementIndex`, or asks for
  the writer schema before an element, sees it, and it failed before too, with an exception that is also a
  `RuntimeException`.
- **`elementType`/`valueType` replace the stored `arraySchema`/`mapSchema`.** The map decoder caches its value type
  too, which the brief asked only for the array. It costs no field.
- **`inUse` is `protected` with a `private set`.** Kotlin does not allow reading a `private` member of the base class
  through a subclass-typed reference, which is how the slot helpers hold it.
- **Two equivalent mutants**, explained above: the total's reset, and the descriptor key's assignment, which only
  matters for speed.
