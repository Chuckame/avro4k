# M5-03 — Records that match the writer schema exactly, decoded in order

**Outcome:** implemented, tests green on JVM, JS (Node) and macosArm64. Not measured: the orchestrator measures it in
the read A/B. Internal code only: no API change (`core/api` and `apache-interop/api` are clean).

**Branch** `v3/exact-record-sequential`, base `78bb7e32`, one commit (code, tests, this note).

Aimed, as M5-12 re-aimed it (`m5-read-profile.md`), at three frames of a `complex` read: `RecordDirectDecoder
.decodeElementIndex` (2.9%), the per-field decoding-step `when` of `RecordDirectDecoder.decode*` (0.8%) and the step
check reached through `decodeSerializableElement`. Not at the read gap as a whole.

## What changed and why

Before, every record was decoded by `RecordDirectDecoder`, which never overrode `decodeSequentially()`. So every
plugin-generated deserializer took its `decodeElementIndex` loop: per field, a call to `decodeElementIndex` (a loop over
the decoding steps and a `when` on the step kind), the generated `tableswitch` on its answer, then in each `decodeX`
override a second `when` on the step kind (writer field or default value).

Now a record whose elements are exactly its writer schema's fields, in the same order, is decoded by a new
`ExactRecordDirectDecoder`. It answers `decodeSequentially() = true`, so the generated deserializer takes its
sequential branch: it calls `decodeXElement(descriptor, 0)`, `decodeXElement(descriptor, 1)`, … in turn. Each one goes
through `beginElement(index)`, which sets the field's writer schema from an array indexed by the element index, then
straight to the base class's `decodeX`, with no step check. Any other record takes exactly today's path.

Files:
- `core/src/commonMain/.../internal/RecordResolver.kt`:
  - new `internal fun exactFieldSchemas(decodingSteps, elementsCount, writerFieldsCount): Array<AvroSchema>?`, the
    exactness rule, top level so that it is tested directly;
  - `loadCache` calls it on the steps `computeDecodingSteps` just built (`computeDecodingSteps` itself is unchanged:
    525 bytes before and after);
  - `SerializationWorkflow` gets an `internal val exactFieldSchemas` constructor property. Its constructor was already
    `internal`, and `@InternalAvro4kApi` keeps the class out of the dumps: `apiCheck` passes, `core/api` unchanged.
- `core/src/commonMain/.../internal/decoder/direct/RecordDirectDecoder.kt`:
  - new `ExactRecordDirectDecoder`;
  - `RecordDirectDecoder.reset(schema, descriptor)` split into `isResolvedFor(schema, descriptor)`,
    `reset(schema, descriptor, steps)` and `reset()`: the resolution moved to the parent, which needs it to choose the
    decoder;
  - its busy state is now its step index (see "Busy state" below), with its own `endStructure`.

- `core/src/commonMain/.../internal/decoder/direct/CollectionsDirectDecoder.kt`: the block decoders' busy state is now
  their item or entry index, with their own `endStructure`.

### The exactness rule

`exactFieldSchemas` is non-null only when:
1. there are as many decoding steps as descriptor elements;
2. and as many as writer fields;
3. every step i is a `DeserializeWriterField`;
4. whose `elementIndex` is i;
5. and whose `writerFieldIndex` is i.

The result is the writer field schema of each step (`step.schema`, the same instances), by element index.

What it admits and refuses, each tested through a real `@Serializable` class:

| Reader against writer | Exact | Why |
|---|---|---|
| same fields, same order | yes | |
| a field matched by an `@AvroAlias` | yes | the match only decides which writer field an element reads; the decoding is the same |
| a writer type promoted to the reader's (`int` read as `long`, `string` as `int`) | yes | both decoders call the same base `decodeX`, which converts |
| a record with no field (`object`) against a record with none | yes | `ObjectSerializer` returns at once on `decodeSequentially()` |
| fields reordered | no | step i reads element ≠ i |
| a writer field more | no | a `SkipWriterField` step, and counts differ |
| a reader field missing, with `@AvroDefault`, nullable (implicit null) or a kotlin default | no | a `GetDefaultValue` or `IgnoreOptionalElement` step, and counts differ |

Given how `computeDecodingSteps` builds the steps (writer fields in order, each a `DeserializeWriterField` or a
`SkipWriterField`, then one step per element left unmatched), conditions 1, 2 and 5 are implied by 3 and 4, and 3 by
1 and 2. They are kept anyway, because the rule then stays right if the step building changes; a unit test with
hand-built steps pins each one (see the mutation checks).

### Choosing the decoder, and the memo

```kotlin
private fun beginRecord(writerRecordSchema: AvroSchema, descriptor: SerialDescriptor): CompositeDecoder {
    val exact = exactRecordDecoder
    if (exact != null && !exact.inUse && exact.isResolvedFor(writerRecordSchema, descriptor)) return exact.reset()
    val general = recordDecoder
    if (general != null && !general.inUse && general.isResolvedFor(writerRecordSchema, descriptor)) return general.reset()
    val workflow = avro.recordResolver.resolveFields(writerRecordSchema, descriptor)
    val fieldSchemas = workflow.exactFieldSchemas
    return if (fieldSchemas != null) {
        exactRecordDecoder().reset(writerRecordSchema, descriptor, fieldSchemas)
    } else {
        recordDecoder().reset(writerRecordSchema, descriptor, workflow.decoding)
    }
}
```

- **One memo per slot, as before.** Each record decoder keeps the schema and descriptor it was last reset for, compared
  by identity. A repeat of an exact record costs a null check, the busy check and two `===`; a repeat of a general one
  also checks the exact slot first (one `===` miss, or a null check when no exact record was ever begun at that level).
- **Two record types alternating, one exact and one not,** both stay remembered: each sits in its own slot. Two exact
  types alternating miss on each switch and fall through to `RecordResolver`'s identity cache, which allocates nothing
  on a hit: as two general types did after M5-02.
- **Resolved before any decoder is touched.** A resolution that fails (two elements matching one writer field) throws
  before a key changes, so the same record begun again fails again (M5-02 test 16, still green).
- **A memo hit always picks the right kind.** Exactness is a function of the (schema, descriptor) pair, resolved once
  per pair and per `Avro`, so a slot holding a pair has the kind that pair resolves to.

### `ExactRecordDirectDecoder`

- `decodeSequentially() = true`.
- `beginElement(descriptor, index)`: `if (index != nextElementIndex - 1) fieldSchema = fieldSchemas[index]`.
  - Read in order, `decodeElementIndex` is never called, `nextElementIndex` stays 0, and every element is given its
    field's schema.
  - Read by index, the element `decodeElementIndex` just returned keeps the schema it was given there, as on the
    general decoder, whose `beginElement` is a no-op. This matters for a union field: a serializer that asks for
    `currentWriterSchema` between `decodeElementIndex` and the field's `decode…Element` reads the union's branch index
    there; reassigning the union in `beginElement` would read it a second time from the input. A test covers it, and
    the "always assign" mutant fails it.
- `decodeElementIndex`: 0, 1, …, n−1, then `DECODE_DONE` on every later call; it sets the field's schema, as the general
  decoder does. For callers that ignore `decodeSequentially()`: Confluent's `GenericRecordKSerializer`
  (`decodeElementIndex` loop, `decodeNullableSerializableElement`) is one; its suite passes unchanged.
- No `decodeX` overrides: an exact record has no default value to decode.
- `currentWriterSchema` before any field is begun still throws `noElementBegunError()`, on a new and on a reused
  decoder, as on the general one.

**One behaviour that changes, on purpose.** A serializer that calls `decodeXElement(descriptor, i)` on an exact record
without calling `decodeElementIndex` first now reads field i, where it used to fail with "No field or item is being
decoded". That is what `decodeSequentially() = true` promises kotlinx. M5-02's test 13 asserted the old failure on
`Inner` read with its own schema, now exact; it now reads `Inner` from a writer schema with a field more (`EXTENDED_INNER`),
so it keeps checking the general decoder, and `ExactRecordDecodingTest` checks the exact one.

### Busy state packed into each decoder's index

M5-02 left the choice open: a `Boolean` busy flag in the base class, or a sentinel in an existing index. Adding the
exact slot settled it (layouts below). The base class no longer has the flag. Each reusable decoder says it is in use
when its position index is 0 or more, and `NOT_IN_USE` (−1) once ended, as when created:

| Decoder | Index | Set to 0 by | Set to −1 by |
|---|---|---|---|
| `ExactRecordDirectDecoder` | `nextElementIndex` | `reset()` | `endStructure` |
| `RecordDirectDecoder` | `nextDecodingStepIndex` | `reset()` | `endStructure` |
| `ArrayBlockDirectDecoder` | `nextItemIndex` | `reset(...)` | `endStructure` |
| `MapBlockDirectDecoder` | `decodedEntries` | `reset(...)` | `endStructure` |

Each `inUse` is a final getter (`index >= 0`) on a final class, read only by the parent's slot helpers, which hold the
concrete type: the same field load and compare as the flag. Every case of M5-02's busy table behaves as before (two
structures begun at once, never ended, an error caught inside, an abandoned structure, `endStructure` twice). The one
unguarded misuse M5-02 named, using a composite decoder after ending it, now also fails differently: a record or block
decoder asked for its next element after `endStructure` starts from index −1 (an `ArrayIndexOutOfBoundsException` on
the JVM for the record decoders) where it used to answer `DECODE_DONE`. No kotlinx or plugin serializer does it.

`AvroValueDirectDecoder` and `RecordAsMapDirectDecoder` are never kept in a slot, so they need no busy state at all.

## Object layouts (JVM, compressed oops, 12-byte headers, 8-byte alignment)

Measured with `Unsafe.objectFieldOffset` on the compiled classes (JDK 21.0.11, a throwaway program, not committed), for
three builds: `78bb7e32`; this change with the busy flag kept as a `Boolean` in the base class (measured by adding the
field back); and this change as committed, with the busy state packed.

| Class | Before | With the exact slot, `Boolean` kept | **After (packed)** |
|---|---:|---:|---:|
| `ExactRecordDirectDecoder` (new) | — | 72 (68 used) | **64** |
| `RecordDirectDecoder` | 72 (68 used) | 72 | **72** (68 used) |
| `ArrayBlockDirectDecoder` | 64 (60 used) | 64 | **64** (60 used) |
| `MapBlockDirectDecoder` | 64 | 72 (68 used) | **64** |
| `AvroValueDirectDecoder` | 48 | 56 (52 used) | **48** |
| `RecordAsMapDirectDecoder` | 56 | 64 (60 used) | **56** |

After, the base class holds 2 ints and 6 references: 12 + 32 = 44 bytes, against 45 + 3 of padding with the flag.
`ExactRecordDirectDecoder` adds `nextElementIndex`, `writerRecordSchema`, `resolvedDescriptor`, `fieldSchemas`,
`fieldSchema`: 64. Field offsets after:

```
base:  12 decodedCollectionSize, 16 decodedCollectionTotal, 20 avro, 24 binaryDecoder,
       28 exactRecordDecoder, 32 recordDecoder, 36 arrayBlockDecoder, 40 mapBlockDecoder
exact: 44 nextElementIndex, 48 writerRecordSchema, 52 resolvedDescriptor, 56 fieldSchemas, 60 fieldSchema
```

**The busy-flag decision: packed.** With the new slot, the flag costs a full 8 B on the exact record decoder (72 → 64
without it), which decodes nearly every record (every benchmark record is exact, below), and on the map block, value
and record-as-map decoders. It costs nothing on the general record decoder (68 bytes used either way) or the array
block decoder (60). Packed, no existing decoder grows and the exact one is 8 B smaller than the general one it
replaces. HotSpot does not fill the flag's 3 bytes of padding with the subclasses' 4-byte fields, which is why it
cost a full word.

Native and JS, estimated, not measured: the base class loses the flag and gains a slot. On Kotlin/Native (8 B header,
8 B references) that is a wash per decoder (−8 + 8), and the exact decoder is one reference smaller than the general
one (≈96 B against ≈104 B). On JS (≈8 B per property) every decoder has the same property count as before, and the
exact decoder one fewer than the general one.

### Throughput

A guess, not measured. Rows that should move up: every avro4k read row whose records are exact, most on record-heavy
reads with many small fields:
- `simple` read @1/@25 (9 fields per record, all on the sequential branch now);
- `complex` read @1/@15 (20 fields per client), where M5-12 put the targeted frames at ≈ 4–6% of the time;
- `lists` read, `NestedRecord.read` at each depth, `Collection.readRecords`/`readTwoCollections`;

- every write row (the encoder is untouched);
- every row of another library, the generic-data and Apache-interop rows, schema inference.

## Deviations and things to review

- **The exactness rule is computed in `loadCache`, right after `computeDecodingSteps`**, by a separate top-level
  function rather than inside `computeDecodingSteps`, so that the rule can be tested on hand-built steps (which kills
  mutants the resolver alone cannot reach).
- **`decodeXElement` without `decodeElementIndex` on an exact record now reads the field** instead of failing (see
  above); M5-02's test 13 was moved to a non-exact record.
- **`beginElement` compares the index with the one `decodeElementIndex` last returned**, a load and a compare per field
  on the sequential path, to keep the index path identical to the general decoder's for union fields read through
  `currentWriterSchema`. Without it the sequential path would be one assignment; the difference only shows for a
  serializer that ignores `decodeSequentially()` and asks for the writer schema in between.
- **The busy flag is packed** into each reusable decoder's index, as M5-02 proposed as the alternative. A decoder used
  after its `endStructure` now fails on its next element instead of answering `DECODE_DONE`: the misuse M5-02 already
  listed as unguarded.
