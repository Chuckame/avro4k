# M5-05 — Encoders reused per nesting level

**Outcome:** implemented, tests green on JVM, JS (Node) and macosArm64. Not measured: the orchestrator measures it in
the write A/B. Internal code only: no API change (`core/api` and `apache-interop/api` are clean).

**Branch** `v3/encoder-reuse`, base `78bb7e32`, one commit (code, tests, this note).

## What changed and why

Before, `AbstractAvroDirectEncoder` built a new encoder for every structure it began:
- a record encoder per record (`RecordContiguousExactEncoder` 32 B, `RecordContiguousSkippingEncoder` 40 B), each
  after a call to `RecordResolver.resolveFields`;
- an `ArrayDirectEncoder` or `MapDirectEncoder` per collection (32 B);
- a `PolymorphicDirectEncoder` (24 B) plus an `AvroValueDirectEncoder` (32 B) per polymorphic value.

Now each direct encoder keeps five lazily created child slots: exact record, skipping record, array, map and
polymorphic. The polymorphic encoder keeps a sixth: the value encoder of its values. `beginStructure`/`beginCollection`
take the slot's instance and reset it. Kotlinx encodes depth-first, so a level only ever has one structure begun at a
time, and a structure begun inside a child is begun by that child's own slots: the encoders of one call form a tree
whose size depends on the depth of the type and the kinds at each level, not on the data. A record whose fields are
written in another order (`EncodingWorkflow.NonContiguous`: `ReorderingCompositeEncoder` + `RecordNonContiguousEncoder`)
still allocates per record, as the brief asks; its own children use its slots.

Files (all in `core/src/commonMain/.../internal/encoder/`):
- `AbstractAvroEncoder.kt` (public, `@InternalAvro4kApi`): one `internal fun clearSelectedUnionIndex()`. On the JVM it
  is `clearSelectedUnionIndex$com_github_avro_kotlin_avro4k_core`, absent from the `.api` and klib dumps, and invisible
  to `apache-interop` (not a friend module: its generic encoder does not compile against it).
- `direct/AbstractAvroDirectEncoder.kt`:
  - the five slots and `inUse` (`protected`, `private set`);
  - `getRecordEncoder`: the identity memo against the two record slots, then `resolveRecordEncoder` out of line;
  - the slot helpers `exactRecordEncoder(…)`, `skippingRecordEncoder(…)`, `arrayEncoder()`, `mapEncoder()`, and the
    polymorphic one inline in `getPolymorphicEncoder`;
  - `beginReuse()` (clears the union index, sets `inUse`) and `endStructure` (clears `inUse`);
  - `noElementBegunError()`;
  - `AvroValueDirectEncoder.reset(schema)`;
  - `PolymorphicDirectEncoder`: `reset(schema)`, `inUse`, `endStructure`, its value encoder slot and the
    `encodingValue` guard.
- `direct/RecordDirectEncoder.kt`: the top-level `RecordDirectEncoder(...)` function is gone. What it did is now
  `getRecordEncoder`/`resolveRecordEncoder` (the reordering case moved to `reorderingRecordEncoder(...)`, unchanged).
  The exact and skipping encoders are `internal` (the slots name them), take their memo keys in the constructor and in
  `reset`, and keep their field schema in a nullable field behind a throwing getter, as the decoders do.
- `direct/CollectionsEncoder.kt`: `ArrayDirectEncoder`/`MapDirectEncoder` lose their constructor schema and size;
  `reset(schema, size)` reads the element or value type once per collection and writes `writeArrayStart`/`writeMapStart`,
  which was in `init`. `endStructure` writes the end, then calls `super.endStructure` (the busy flag).

**Codec call sequence:** unchanged. The start is still written when the collection is begun, after any union index the
parent wrote; `startItem` still precedes each item and each map key; the end is still written by `endStructure`. Every
existing byte test (Apache oracle in `jvmTest`, golden fixtures on the three platforms) passes unchanged.

### Choosing the record encoder: identity memo per slot

```kotlin
val schema = currentAvroSchema as RecordSchema
val exact = exactRecordEncoder
if (exact != null && exact.schema === schema && exact.resolvedDescriptor === descriptor) {
    return exactRecordEncoder(schema, descriptor)
}
val skipping = skippingRecordEncoder
if (skipping != null && skipping.schema === schema && skipping.resolvedDescriptor === descriptor) {
    return skippingRecordEncoder(schema, descriptor, skipping.skippedElements)
}
return resolveRecordEncoder(schema, descriptor)
```

- **Where the memo lives.** Each record encoder already held its writer schema; it now also holds the descriptor it
  was resolved for (`resolvedDescriptor`, one field), and the skipping one its `skippedElements`. A slot's keys are only
  ever set by a reset that followed a resolution to that slot's workflow, or a hit on that slot, so a key pair matches
  at most one slot. The memo never needs a third "workflow" field on the parent.
- **Scope.** Per-call state, as the shared-state rule allows: no pooling, no `ThreadLocal`, nothing shared. A
  homogeneous list never reaches `RecordResolver` after its first item.
- **Identity only.** All four halves use `===`.
- **Misses.** Two record types alternating at one level (fields `a: A, b: B`, or a polymorphic list's values on the
  value encoder's slot) miss at each switch and fall through to `RecordResolver`'s 16-entry identity cache, which
  allocates nothing on a hit. Before, every record went there. A reordered record always does, as before.
- **Busy slot with a matching key.** The memo still tells the workflow; the record gets a new encoder of that kind,
  not stored.
- **Memo keys and failures.** `resolveRecordEncoder` resolves before touching a slot. A resolution that throws
  (`MissingWriterFields`, two elements on one writer field) leaves the slots as they were.

### Busy guard

Each reset ends with `beginReuse()` (or `inUse = true` for the polymorphic encoder); `endStructure` clears it. A slot
helper reuses the kept instance only when it is not in use; otherwise it builds a **fresh** one and does not store it
(the slot keeps the busy one):

```kotlin
val kept = arrayEncoder
if (kept != null && !kept.inUse) return kept
val encoder = ArrayDirectEncoder(avro, binaryEncoder)
if (kept == null) arrayEncoder = encoder
return encoder
```

How `endStructure` is called on the encode side, checked in the kotlinx-serialization-core 1.11.0 sources
(`kotlinx-serialization-core-jvm-1.11.0-sources.jar` in the Gradle cache):
- `Encoder.encodeStructure` and both `encodeCollection` overloads (`Encoding.kt:472-507`) call `beginStructure` or
  `beginCollection`, run the block, then `endStructure`, without `try/finally`.
- The collection serializers (`CollectionSerializers.kt:64-71`, `116-126`, `172-177`: lists, maps, primitive arrays)
  go through `encodeCollection`; `AbstractPolymorphicSerializer.serialize` (`:32-38`) through `encodeStructure`;
  `Tuples.kt` (pairs, map entries, triples) and `ObjectSerializer` call begin and end directly. There is no `finally`
  anywhere in kotlinx-serialization-core's common sources.
- Plugin-generated `serialize`: `beginStructure`, `write$Self`, `endStructure`, with no exception table (checked with
  `javap -c -p` on `Branch$$serializer.serialize` from the test classes).

So an encode that throws never ends its structure, and kotlinx never begins two structures on one encoder.

| Serializer | What happens |
|---|---|
| begins a second structure on an encoder before ending the first | the second is encoded on a fresh encoder; the first keeps the slot. Tested for records (exact, and skipping with their elements written in turn), lists, maps and polymorphic structures. |
| never calls `endStructure` | the slot stays busy for the rest of the call: every later structure of that kind at that level gets a fresh encoder (allocating as before) |
| catches an error inside a structure and goes on with it | it keeps using its own encoder, still marked busy |
| abandons a structure on an error, unended, and encodes the value again on the parent | the abandoned encoder is busy: the new attempt gets a fresh one |
| calls `endStructure` twice | harmless (records and polymorphic); for a collection the end marker is written twice, as before |
| a polymorphic value's serializer encodes on its own polymorphic structure again from inside its value (re-entrant) | that inner value gets a fresh value encoder: `encodingValue` is set while the kept value encoder runs. A value that throws leaves it set, so every later value of that polymorphic encoder gets a fresh value encoder (correct, allocating as before). |

**Limit**, as for decoders: a serializer that keeps using a composite encoder **after** calling `endStructure` on it,
while its parent begins another structure of the same kind, would share that encoder. That breaks the kotlinx
contract; no kotlinx or plugin serializer does it.

**Why `encodingValue` and not the value encoder's own `inUse`.** The value encoder is not a structure: nothing calls
its `endStructure`, and the polymorphic encoder is not a subclass, so it cannot read the `protected` flag. A second
`Boolean` on the polymorphic encoder costs nothing (see the layouts: it fills padding).

Notes:
- **Ordering.** Each reset assigns its own fields first, writes the collection start if any, and calls `beginReuse()`
  last. A reset that throws (only the codec's start can, under validation) leaves the encoder free.
- **The union index reset is an equivalent mutant on record and collection encoders.** After a reset the field or
  item schema is unset, and `encodeUnionIndex` reads it (for the branch, or for its "already selected" message), so a
  stale index can only surface as the same `IllegalStateException` a new encoder throws; after `encodeElement` the index
  is -1 again. It is observable on the value encoder of a polymorphic structure, which encodes without `encodeElement`:
  a reused value encoder whose previous value selected branch 1 failed with "Already selected union index" on the next
  value. The reset is kept on every encoder so that the reset stays complete.
- **The throwing getters.** A new encoder failed with `UninitializedPropertyAccessException` when asked for its writer
  schema (or to encode) before an element was begun. A reused one would otherwise answer with the previous record's last
  field schema. The getters keep the failure, as `IllegalStateException` (the decoder unit's deviation, for the same
  Kotlin/Native reason), and compile to the same null check (`getCurrentAvroSchema` 16 → 13 bytes).
- `encodeElement` writes the backing field directly instead of through the virtual setter.

## Tests added (16, `commonTest`, run on JVM, JS, native)

`core/src/commonTest/kotlin/com/github/avrokotlin/avro4k/encoding/EncoderReuseTest.kt` (new). Expected bytes are written
with `ByteArrayEncoder` in the order of calls a new encoder per structure makes; round trips decode with `Avro` and
`Avro { validateSerialization = true }`. Protocol-breaking serializers encode with `Avro` only.

1. `sibling records lists and maps encode at several depths`: a tree of branches of leaves, nullable records, lists and
   maps of records, lists of `Int` then `String`, maps of `Int` then `Boolean`, lists of lists, maps of maps, maps of
   lists; alone and as a list of three.
2. `a recursive type encodes six levels deep`.
3. `two record types alternating as fields of one parent encode`.
4. `records of one type written with several writer schemas in turn encode`: one descriptor (with aliases) written with
   an exact, a skipping, a reordered and a second skipping schema, as siblings twice, then a list. Exercises the schema
   half of both memos, and exact/skipping/reordering siblings.
5. `one writer schema written from several types in turn encodes`: one writer schema instance written from an exact type
   and two skipping types that skip other elements, after another schema on the exact slot. Exercises the descriptor
   half of both memos and the key assignments.
6. `exact skipping and reordered records encode as siblings and in one list`: as fields, and as one polymorphic list
   switching between the three on the value encoder's slots.
7. `a list of records whose writer type alternates through a union encodes`: polymorphic values in a field, a nullable
   field (other union), lists, nullable lists, lists of lists; bytes and round trip.
8. `a polymorphic value selecting a union branch after a sibling selected another encodes`: branch 1 then 0 on a reused
   value encoder.
9. `maps of lists of records encode`.
10. `a serializer beginning a second structure before ending the first encodes both`: records at the root, as a field,
    as list items; skipping records whose elements are written in turn.
11. `a serializer beginning a second list map or polymorphic value before ending the first encodes both`.
12. `a serializer that never ends its structures encodes`: fields, list items, map-of-list items, siblings after.
13. `a serializer catching an encoding error inside a structure goes on encoding`: one goes on in its record, one
    abandons it and encodes again on the parent; as fields and list items.
14. `successive structures of one kind are encoded by one encoder`: identity (`===`) of the record, list, map,
    polymorphic and value encoders of successive values; when never ended, each is a new one.
15. `a reused encoder knows no field or item before one is begun`: a record (exact and skipping), a list and a map asked
    for `currentWriterSchema` and to select a union branch before any element, after a sibling whose last element
    selected a branch; and at the root.
16. `a polymorphic value encoding again on its structure from inside its value gets its own encoder`.

| Class | Before | After | Fields after |
|---|---:|---:|---|
| `AvroValueDirectEncoder` (root, and per polymorphic structure) | 32 | **56** | base 36 B (`selectedUnionIndex`, `inUse` + 3 B padding, `avro`, `binaryEncoder`, 5 slots) + `currentAvroSchema`: 52 |
| `RecordContiguousExactEncoder` | 32 | **64** | base + `schema`, `resolvedDescriptor`, `fieldSchema`: 60 |
| `RecordContiguousSkippingEncoder` | 40 | **72** | base + `nextWriterFieldIndex`, `schema`, `resolvedDescriptor`, `skippedElements`, `fieldSchema`: 68 |

| `MapDirectEncoder` | 32 | **56** | base + `valueType`, `entrySchema`: 56 |

The base grows by 24 B: 5 slot references and `inUse` with its padding. The added fields are the minimum for the
design: one slot per kind, one memo key per record encoder (the descriptor; the schema was already there), one busy
flag. With the busy state packed into another field instead of `inUse`, the value, exact, skipping and reordering
encoders would be 8 B smaller (48 / 56 / 64 / 56); array and map would not change. As for the decoders, the `Boolean`
was kept for clarity, since these encoders are now allocated per call rather than per value.

Native and JS, estimated: Kotlin/Native (8 B header, 8 B references): the exact record encoder from ≈40 to ≈88 B, array
and map from ≈40 to ≈80, value from ≈40 to ≈80, polymorphic ≈32 to ≈48. JS (≈24 B + 8 B per property): the base gains 6
properties. Neither has escape analysis, so each object no longer allocated is saved in full.

the slots the design accepted (§3: "about 5–10 small objects").

**Should not move:** every read row; every row of another library (Apache, Jackson); generic-data rows
(`apache-interop`'s generic encoder is untouched); schema inference; the identity-lookup micros.

**Throughput** (EA on, JVM): probably within noise; with escape analysis on, most per-record encoders were likely

memo check (two loads and two identity compares) and a reset (three to five field stores) instead of a resolver call
(16-entry identity scan) and an allocation with its constructor chain. The risk is JIT shape: `getRecordEncoder` grew
from 22 to 105 bytes inside `beginStructure`'s record branch, which matters for the `simple` write rows that were
JIT-sensitive before (`benchmark/README.md`, M3 notes). On JS and native the objects disappear at the sizes estimated
above.

## Deviations and things to review

- **Misuse fails with `IllegalStateException`, not `UninitializedPropertyAccessException`**, as in the decoder unit
  and for the same reason (the class is internal on Kotlin/Native). Only a serializer asking a record or collection
  encoder for its schema, or encoding on it, before any element sees it; it failed before too.
- **Record encoders take their memo keys in the constructor** (and again in `reset`), so their schema is a non-null
  field and `encodeElement` stays the same size; array and map encoders take nothing and keep nullable types
  (`elementType`/`valueType`), which their hot methods only copy, never dereference.
- **The polymorphic value encoder's guard is `encodingValue` on the polymorphic encoder**, not the value encoder's own
