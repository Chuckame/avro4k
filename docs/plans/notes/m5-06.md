# M5-06 — Union branch tables and small per-value encode methods

**Outcome:** implemented, tests green on JVM, JS (Node) and macosArm64. Not measured: the orchestrator measures it in
the write A/B. Internal code only: no API change (`core/api` and `apache-interop/api` are clean).

**Branch** `v3/union-tables-small-encode`, base `5504c87b`, one commit (code, tests, this note, backlog entry 16).

## What changed and why

### 1. `UnionSchema.firstIndexByType`

`AvroSchema.UnionSchema` (`C/AvroSchema.kt`) gains `internal val firstIndexByType: IntArray`, one slot per
`AvroSchema.Type` (indexed by `ordinal`, 14 slots), −1 when the union has no branch of that type, otherwise the index of
the **first** branch of that type. Built once by the property initializer, after `types` (a forward loop that writes a
slot only while it is still −1).

- Not a constructor property: no part in `equals`/`hashCode`/`copy`/`toString` (`equals`, `hashCode` and `toString` are
  overridden anyway and read `types` only). Same precedent as `EnumSchema.symbolIndex`.
- `internal`: on the JVM its getter is `getFirstIndexByType$com_github_avro_kotlin_avro4k_core`, absent from the `.api`
  and klib dumps (`apiCheck` green, `git diff core/api apache-interop/api` empty).
- Cost: one `int[14]` per union schema (16 + 56 = 72 B) plus a reference field, at construction, never per value.

`getIndexTyped` (`C/internal/schema/AvroSchemaHelpers.kt`) is now
`(this as? UnionSchema ?: throw wrongKind("Not a union")).firstIndexByType[expectedType.ordinal]`: same answer as the
loop (first branch of that type, −1 when none), same `Not a union` error on a non-union. Only named types can appear
twice in a union (the model rejects two branches with the same full name, and an unnamed type's full name is its type
name), so "first" only matters for record/enum/fixed; no encoder call site asks for a named type.
`trySelectTypeNameFromUnion`'s KDoc now says "one array read".

### 2. Small `encodeX` methods in `AbstractAvroEncoder`

Every value method keeps only the case of a value written to its own Avro type:

```kotlin
override fun encodeString(value: String) {
    if (currentAvroSchema.isUnion) selectUnionBranchForString(value)
    if (currentAvroSchema.type === AvroSchema.Type.STRING) encodeStringUnchecked(value) else encodeStringConverted(value)
}
```

and two private, non-inline members per type: `selectUnionBranchForX` (the `trySelect…` chain and its
`unsupportedWriterTypeError` array, unchanged and in the same order) and `encodeXConverted` (the other branches of the
old `when`, the `convertForEncoding` `try`s, and the `else` error). Private members, not top-level functions, so no
synthetic accessor; `apache-interop`'s generic encoder inherits them without seeing them.

| Method | Natural case (inline) | Out of line |
|---|---|---|
| `encodeBytes` | `BYTES` → `encodeBytesUnchecked` | union chain; `STRING`, `FIXED` (+ size check), error |
| `encodeFixed` | `FIXED` → `encodeFixedUnchecked(ensureFixedSize(value))` | union chain; `BYTES`, `STRING`, error |
| `encodeEnum` | `ENUM` with a matching name → `encodeEnumUnchecked` | union chain (returns whether the branch was selected by name); `ENUM` with a mismatched name (throws), `STRING`, error |
| `encodeBoolean` | `BOOLEAN` | union chain; `STRING`, error |
| `encodeInt` (and `encodeByte`/`encodeShort`, which call it) | `INT` | union chain; `LONG`, `STRING`, error |
| `encodeLong` | `LONG` | union chain; `INT` (`toIntExact`), `STRING`, error |
| `encodeFloat` | `FLOAT` | union chain; `DOUBLE`, `STRING`, error |
| `encodeDouble` | `DOUBLE` | union chain; `FLOAT` (`toFloatExact`), `STRING`, error |
| `encodeChar` | `INT` (`value.code`) | union chain; `STRING`, error |
| `encodeString` | `STRING` | union chain; `BOOLEAN`/`INT`/`LONG`/`FLOAT`/`DOUBLE` (`convertForEncoding`), `BYTES`, `FIXED`, `ENUM`, error |

- The natural test is `type === X` (one reference compare) instead of the `when`'s `$EnumSwitchMapping$` lookup and
  `tableswitch`.
- `encodeString`'s two 9-type error lists were identical, so they are one private `stringUnsupportedWriterTypeError()`.
  Every other list stays where it was, because the union-chain and the `else` lists differ for bytes, long and double
  (e.g. long: `LONG, INT, STRING` vs `INT, LONG, STRING`). **Every message is byte for byte the same**: same helper,
  same arguments, same order.
- `encodeEnum`: the order of evaluation is unchanged (union selection, then `getElementName(index)`, then the name check
  only for an `ENUM` branch not selected by name).
- `encodeNull` (80 B) is untouched: already small, and its two errors are its only other content.
- The fixed-size and enum-symbol scans (`trySelectFixedSchemaForSize`, `trySelectEnumSchemaForSymbol`) are unchanged.
  They are only reached when the union has no branch of the value's own type.
- `beginStructure`/`beginCollection` and the decode side are out of scope (brief).

## Tests added (13, `commonTest`, run on JVM, JS, native)

`core/src/commonTest/kotlin/com/github/avrokotlin/avro4k/encoding/UnionBranchSelectionTest.kt`. Each case encodes with
`Avro` and with `Avro { validateSerialization = true }` and compares with bytes written by the codec (union index, then
the value as the selected branch's type); each error case checks both instances throw the same
`AvroSchemaMismatchException` message.

1. `a boolean selects its own branch first then a string` — `boolean`, `[null,boolean]`, `[string,boolean]` (own branch
   at 1), `[null,string]`, `string`; errors `[null,int]`, `int`.
2. `an int a short and a byte select int first then long then string` — for `Int`, `Short`, `Byte`: `int`,
   `[null,int]`, `[string,long,int]` (own at 2), `[null,long]`, `[string,long]` (long before string), `[null,string]`,
   `long`, `string`; errors `[null,double]`, `double`.
3. `a long selects long first then int then string` — same shapes; `Long.MAX_VALUE` into `[null,int]` fails.
4. `a float selects float first then double then string`.
5. `a double selects double first then float then string` — `2.5` (exact as a float) into float branches; errors
   `[null,long]`, `long`. No inexact double into a float: see the JS finding below.
6. `a char selects int first then string`.
7. `a string selects string then bytes then fixed then enum then boolean int long float and double` — each step of the
   chain beaten by the one before it (`[double,bytes,fixed,string]` → string at 3, `[double,fixed,bytes]` → bytes,
   `[int,enum,fixed]` → fixed, `[boolean,enum]` → enum, `[double,long,int]` → int, `[double,float,long]` → long,
   `[null,double,float]` → float), every conversion outside a union, and errors (`[null,record]`, `record`, `"abc"` into
   `[null,int]`, `"abc"` into a 2-byte fixed).
8. `a string selects the first of two fixed of its size and the first of two enums with its symbol` — first-branch
   semantics for the two scans, both orders, and an enum skipped because it lacks the symbol.
9. `bytes select bytes first then string then a fixed of their size` — including two fixed of one size (first wins) and
   a fixed of another size skipped.
10. `a fixed selects a fixed of its size first then bytes then string` — through a test serializer calling
    `AvroEncoder.encodeFixed`.
11. `an enum selects its named branch first then a string` — named branch at 2 after a string and another enum,
    string fallback, errors (`[null,int]`, an enum of another name, `int`).
12. `no compatible branch in a union names the type and its fallbacks in the order tried` — pinned verbatim:
    - int into `["null","boolean"]`: `Unsupported schema 'union[null, boolean]' for encoded type of int, and also not
      matching to any compatible type (one of LONG, STRING).. Actual schema: ["null","boolean"]`;
    - long into the same: `… for encoded type of long, … (one of INT, STRING).. …`;
    - string into `["null",record R]`: `… 'union[null, R]' for encoded type of boolean, … (one of INT, LONG, FLOAT, DOUBLE,
      STRING, BYTES, FIXED, ENUM).. Actual schema: ["null",{"type":"record","name":"R",…}]`.
13. `an incompatible writer type and a failed conversion keep their messages` — pinned: long into `"boolean"`
    (`… 'boolean' for encoded type of int, … (one of LONG, STRING).. Actual schema: "boolean"`: the `else` list, not the
    union one), the conversion prefix `Cannot convert the String value 'abc' to the writer type int: `, and the enum
    one `Named schema Suit not found in union. Also no compatible type found (one of STRING). Actual schema:
    ["null","int"]`.

**Behaviour unchanged, checked:** the 13 tests were also run against the base code (`5504c87b`'s `core/src/commonMain`
checked out over the change, tests kept): 13/13 green. So every byte and every pinned message is the old one.

Byte identity is still guarded by the Apache oracle (`jvmTest`) and the golden fixtures on the three platforms: no
expected byte edited. `apache-interop` tests pass unchanged.

## Predicted effect (measured in the write A/B)

**B/op: unchanged on every row.** Nothing on the encode path allocates more or less: the selection and conversion code
is the same, only split. The table is per union schema; every benchmark builds its schemas in `@Setup` (the
`FreshWriterSchema` and `SchemaInference` rows build schemas per call, but `SmallRecord` and `Nested8` have no union),
so it never shows per op.

Throughput, JVM:
- **`StringField.writeNullable` should gain more than `writeNonNull`.** Each of its 12 `["null","string"]` fields went
  through a 775-byte `encodeString` (never inlined) whose union path looped over the branches; now a 48-byte
  `encodeString`, a 121-byte selection function (small enough to be inlined at a hot call site) and one array read.
  `writeNonNull` is the control for the union part: it may still move a little, since its `encodeString` call can now
  be inlined too, but the gap between the two rows should shrink.
- **`simple` write @1/@25 (9 forks)**: up. Each record writes a boolean, byte, short, long, float, double and bytes on
  their natural path (each method 40–48 B instead of 142–195) and an `int?` and a `string?` through a union.
- **`complex` write**: up, likely the most of the end-to-end rows. Its `Client` has many nullable fields reaching the
  union path of `encodeString` (`name`, `company`, `address`, `about`, `balance` stringable), `encodeBytes`
  (`picture`), `encodeEnum` (`eyeColor`, 292 → 169 B), `encodeChar` (`gender`), and a `List<String?>`.
- **`Polymorphic.writeConcrete` / `writePolymorphic`**: at most a small gain, equal on both. The polymorphic branch is
  selected in `beginStructure` (unchanged); the shapes' `double`s now go through a 40-byte `encodeDouble`.
- **Controls, should not move**: every read row, `FieldOrder.write` (records of ints and strings, exact or reordered,
  no union), the schema rows. `NestedRecord.write` and `Collection.writeLongs` write longs on the natural path only and
  may move a little from the smaller `encodeLong`, not from the table.
- JS and native: not benchmarked; the code is common and the split is neutral there.

## Finding: a double that is not exact as a float is accepted on JS

The first acceptance run failed on JS only: `0.1` written to `["null","float"]` threw on the JVM (`Value 0.1 is not a
valid Float`) but encoded on Node. On Kotlin/JS a `Float` is a JS number and `Double.toFloat()` does not round, so
`toFloatExact` (`C/internal/NumberUtils.kt`) never fails there. Not caused by this unit (the conversion code is the same,
only moved) and not a pre-existing `main` bug (JS is new), so it is a cross-platform divergence for the migration, left
to the coordinator. The case was removed from the common test rather than fixed here. Native (real 32-bit floats)
behaves as the JVM. Possible fix: compare against a rounding that JS honours (`Math.fround` through an `expect`/`actual`,
or the float's raw bits), with a common test on the three platforms.
