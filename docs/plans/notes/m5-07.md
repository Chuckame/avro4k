# M5-07 — Strings written without an intermediate array

**Outcome:** implemented, tests green on JVM, JS (Node) and macosArm64, the ten other native test binaries link; not
measured (the orchestrator measures it in the write A/B). Internal code only: no API change (`core/api`,
`apache-interop/api` clean).

**Branches:** `v3/string-write-in-place` (base `c12fde49`, one commit: code, tests, this note) and the candidate
`v3/string-write-jvm-threshold` (one commit on top, see the last section).

## Problem

`ByteArrayEncoder.writeString(String)` (the only string writer since kotlinx-io left core: `encodeToByteArray`, and on
the JVM `encodeToStream`, which is the same class with a `writeFullChunk` callback) did
`writeBytes(value.encodeToUtf8())`: one `ByteArray` per non-empty string, its length written, then the array copied
into the chunk. On JS and native `encodeToUtf8` also ran a counting pass first (to detect unpaired surrogates) before
Kotlin's `encodeToByteArray()`.

## What changed

- **`internal/codec/Utf8.kt`** (common), next to `decodeUtf8`:
  - `String.utf8Length(): Int`: the counting loop formerly inside `Platform.nonJvm.kt`, an unpaired surrogate counted
    as 1 byte (`?`), the contract of `encodeToUtf8` in `Platform.kt`. A string of more than `Int.MAX_VALUE / 3 - 1`
    chars (≈715 M) is counted by slices into a `Long`, out of line, and throws `IllegalStateException` past
    `MAX_BINARY_LENGTH` bytes, so that the count can never wrap into a wrong length prefix. Not testable here (it takes a
    1.4 GB string); the JVM's `getBytes` failed on such a string before too.
  - `String.encodeUtf8Into(bytes, offset, startIndex, endIndex): Int`: the one UTF-8 encoding loop of avro4k, writing
    in place and returning the offset after the last byte. ASCII is a loop of its own (71 bytes of bytecode, inlinable);
    the first other char hands over, out of line, to the general loop (`encodeUtf8From`, the former non-JVM loop, `?`
    for an unpaired surrogate). A surrogate pair must not be split between two calls (the caller's job).
- **`Platform.nonJvm.kt`**: `encodeToUtf8()` = `ByteArray(utf8Length())` filled by `encodeUtf8Into`: one encoding loop
  in common code. It is now only used off the string path (a string written to BYTES/FIXED, JSON defaults). The JVM's
  `encodeToUtf8` stays `getBytes(UTF_8)`, the reference the tests compare to.
- **`ByteArrayEncoder.writeString(String)`**:
  - **Short strings in one pass**: when `length <= 21` and the chunk has more than `3 × length` bytes left, the length
    byte is reserved, the chars are encoded after it, and the length is written back into it as `(n shl 1)` (the
    zig-zag varint of `0 <= n <= 63`). The empty string goes through the same path and writes `0`. This is all the
    method writes itself (79 bytes of bytecode).
  - **Otherwise, `writeCountedString`** (out of line): `utf8Length()`, `writeInt(count)`, then the bytes. If they fit
    in the room left, one `encodeUtf8Into`. If not, see below.
  - The TODO is resolved and removed; `ByteArrayEncoder` no longer imports `encodeToUtf8`.

### Why 21 chars always have a one-byte length

One UTF-16 char gives at most 3 UTF-8 bytes:
- below U+0080: 1 byte; below U+0800: 2; the rest of the basic plane (non-surrogate): 3;
- a surrogate pair: 2 chars → 4 bytes, so 2 per char;
- an unpaired surrogate: 1 byte (`?`).

So `n` chars take at most `3n` bytes: 21 chars → at most 63 bytes, whose zig-zag value 126 is below 128: one varint
byte. 22 chars can take 66 bytes (zig-zag 132, two bytes), so 21 is the largest count for which the prefix width is
known before encoding. The room check `bytes.size - p > 3 * length` is exactly one length byte plus `3 × length`.

### Chunk boundaries

The encoder's rules (`m4-bytearray-encoder.md`, `m4-jvm-streams.md` §7) are kept as `writeFixed` applies them:
- a varint needs contiguous room (`reserveUpTo`), so `writeInt(count)` may start a new chunk, leaving a few bytes of the
  old one unused, as before;
- the bytes fill the current chunk, then **the rest goes at the start of the next one, sized for that rest if it is
  larger than the doubled chunk** (`nextChunk(remaining)`, as `writeAcrossChunks` does). In the stream mode the full
  chunk is handed to the stream and, from 64 KiB, its array reused, as for any other value.
- The difference with `writeFixed`: chars, not bytes, are cut. The chars are encoded by runs of `room / 3` chars, which
  surely fit; a run never ends on a high surrogate (the pair stays whole for the next run); when no char surely fits
  (`room < 3`, or `room < 6` before a pair), the next chunk starts. So a chunk can end with up to 2 unused bytes (5
  before a pair), like the up to 9 before a varint. `toByteArray` and `writeChunksTo` already copy only the used length
  of each chunk.
- The runs shrink the room by at least a third each time, so a crossing takes at most about 27 runs for a 64 KiB chunk,
  once per chunk crossed; after `nextChunk(remaining)` the rest always fits in one run.
- A short string that does not fit the `3 × length` room goes to the counted path, which fills the chunk as above: no
  more unused bytes than a counted string.

## Tests added (9; jvm 1078 → 1087, jsNode 237 → 244, macosArm64 240 → 247)

`core/src/commonTest/.../internal/codec/StringWriteTest.kt` (new, 7 tests, JVM, JS, native). Every expected byte comes
from a UTF-8 encoder written in the test from the code points (`?` for an unpaired surrogate) and a zig-zag varint
written bit by bit, so the oracle shares no code with the encoder; on the JVM it is also checked against `getBytes`.
The case list (`STRING_CASES`, 44 strings): empty, ASCII, Latin-1, U+0080/U+07FF/U+0800 edges, CJK, U+FFFF/U+E000/U+D7FF,
4-byte characters (U+10FFFF included); unpaired high and low surrogates at the start, middle and end, a reversed pair,
a high surrogate before a pair; a pair at the 21-char boundary (19+pair, 20+pair, 20 + lone high, 21 + lone low,
20 × `€` + pair); exactly 20/21/22 chars of 3-byte and of 4-byte content, 21 lone surrogates; lengths at the varint
boundaries 63/64 and 8191/8192 bytes in ASCII, 2-byte, 3-byte and 4-byte content; longer than the first chunk.
1. `every string case is written as its length then its UTF-8 bytes`: also `encodeToUtf8()`, `utf8Length()`, and the
   previous encoder's bytes (`writeBytes(encodeToUtf8())`).
2. `a string of up to 21 chars has a one-byte length whatever its content and 22 chars can need two`: the prefix bytes
   pinned.
3. `every string case is written whole wherever it starts against the end of a chunk`: after 180 to 256 bytes (the
   first chunk is 256), in both modes (`toByteArray` and the chunk-handing mode the JVM streams use); the cases over 100
   chars from every 8th offset and 253–256.
4. `strings of every length up to 300 chars are written whatever their content`: 7 contents × 301 lengths.
5. `strings of several hundred kilobytes are written across every chunk size`: 50 K chars of mixed content, 200 K
   ASCII, 70 K pairs, in both modes; then 10,000 strings in a row, crossing chunk ends at every offset past 64 KiB.
6. `the rest of a string crossing the end of a chunk goes to a next chunk sized for that rest`: chunk sizes pinned.
7. `strings are written by encodeToByteArray as their length then their UTF-8 bytes`: every case through
   `Avro.encodeToByteArray`, and all of them in one record (`List<String>` between an int and a string).

`core/src/jvmTest/.../StringWriteJvmTest.kt` (new, 2 tests):
1. `every string case is written as Apache's BinaryEncoder writes it`.
2. `every string case is written by encodeToStream as by encodeToByteArray and Apache wherever it starts against the end
   of a chunk`: a record `(bytes prefix, string)` with prefixes of 0 to 70,000 bytes, through `encodeToStream`,
   `encodeToByteArray` and Apache's `BinaryEncoder`.

The Apache oracle and the golden fixtures pass unchanged; no expected byte was edited.

JS: the chunk-end test first timed out (Mocha's 2 s) when it recomputed the expected bytes per offset; it now computes

| method | before | after |
|---|---:|---:|
| `ByteArrayEncoder.writeString(String)` | 39 | 79 |
| `ByteArrayEncoder.writeCountedString` (new, out of line) | — | 141 |
| `Utf8Kt.encodeUtf8Into` (new, ASCII loop) | — | 71 |
| `Utf8Kt.encodeUtf8From` (new, non-ASCII, out of line) | — | 326 |
| `Utf8Kt.utf8Length()` (new) | — | 31 |
| `Utf8Kt.utf8Length(start, end)` (new, private) | — | 127 |
| `Utf8Kt.utf8LengthOfHugeString` (new, never on a realistic path) | — | 99 |
| `ByteArrayEncoder.writeBytes` / `writeFixed` / `writeInt` | 35 / 54 / 53 | unchanged |
| `Platform_jvmKt.encodeToUtf8` | 10 | 10 |

Before, a string went `writeString` (39) → `encodeToUtf8` (10) → `getBytes` → `writeBytes` (35) → `writeInt` (53) +
`writeFixed` (54). Now a short ASCII string is `writeString` (79) → `encodeUtf8Into` (71), both under `FreqInlineSize`
(325); `writeString` is above `MaxInlineSize` (35), as `writeInt` already is. The non-ASCII loop (326) is just over
`FreqInlineSize` on purpose: it stays a call, only taken for non-ASCII content.

## Predictions (measured in the write A/B, not here)

Allocation, escape analysis off, `writeToByteArray` and `writeToStream` alike: one UTF-8 array less per non-empty
string, `16 + n` bytes rounded up to 8. Exact per call, from the seeded generators (counted with a throwaway program over
`ClientsGenerator`/`SimpleDatasClass` on the benchmark classpath; every string is ASCII):

| row | arrays gone | B/op delta |
|---|---:|---:|
| `simple` @1 / @25 / @500 | 1 / 25 / 500 (one 25-char string per record, 48 B) | −48 / −1,200 / −24,000 |
| `complex` @1 / @15 / @200 | 35 / 553 / 7,556 (≈37.8 per client: names, about, emails, tags, map keys and values, partner name, the `@AvroStringable` balance) | −1,128 / −18,072 / −246,672 |
| `lists` @100 / @10000 | 0 (no string) | 0 |
| `StringField.writeNonNull` / `writeNullable` | 12 × 16 chars | −384 each |

Caveat: a string crossing a chunk end can leave up to 2 bytes of that chunk unused where `writeFixed` filled it; the
number of chunks only changes if a value's size lands within those few bytes past a chunk total. Not expected on these
rows.

Throughput:
- `simple` write: its 25-char string takes the counted path (two passes over 25 chars, no allocation); expected a small
  gain on the JVM (the JDK's `getBytes` on a 25-byte Latin-1 string is an intrinsic, the gain is the allocation and the
  copy), more on JS/native (no escape analysis, and the non-JVM path also lost a counting pass).
- `complex` write: most strings are 10–20 chars, the one-pass path; expected the clearest gain of the three.
- `StringField.write*`: 16-char strings, one pass; the gain should show there first.
- Not expected to move: every read row, `lists` write (no string), the Apache and Jackson controls, the non-string
  micros (`FieldOrder.write`, collections, polymorphic).

On the JVM a long ASCII string (well over 21 chars) is the case at risk: `getBytes` checks and copies a Latin-1 string
with vectorized intrinsics, the common loop reads one char at a time, twice. No benchmark row has a string over 30
chars, so the A/B cannot see that case unless a long-string row is added; the candidate below is built for it.
