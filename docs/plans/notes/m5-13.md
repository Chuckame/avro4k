**Outcome:** both steps implemented, one commit each, each passing `ACC` alone. Tests green on JVM, JS (Node) and
macosArm64. Not measured: the orchestrator measures each commit as its own side of the read A/B (step 1 against the
base, step 2 against step 1). Internal code only: no API change (`core/api`, klib included, and `apache-interop/api`
are clean).

**Branch** `v3/schema-field-nullable-path`, base `4254a4d0`: step 1 `5e174c72`, step 2 the commit after it.

## Step 1 — the current schema as a plain field

### What changed and why

The CPU profile of a `complex` read (`m5-read-profile.md`) charged ≈ 7.7% of a `complex` @15 read to the per-value
schema access: `currentAvroSchema` was an abstract property of `AbstractAvroDirectDecoder`, overridden by six decoders
(five with a getter that threw when no field was begun), so every read was a virtual call, made through a vtable stub
once the decoder kinds mix in one decode call (getters 3.3%, their stubs 1.0%), and `decodeAndResolveUnion`, which runs
first on every `decode*` and `decodeSerializableValue`, read it three times (3.4%).

Now `currentAvroSchema` is a `@JvmField var` of `AbstractAvroDirectDecoder`: one field, assigned by each decoder where it
assigned its own field before, read as a plain field everywhere. No subclass overrides it; the record, exact record,
array block, map block, record-as-map and value decoders each lost their own schema field.

**The "no field begun" check moved to the rare paths** with a marker: `NO_ELEMENT_SCHEMA`, a private union instance
(`["null"]`) that a record or block decoder holds from its reset until its first field or item. It is compared by
identity only, at three places, none of them on a value's path:
- `resolveUnion` (the union path of `decodeAndResolveUnion`, out of line): the marker is a union, so
  `currentWriterSchema`, `decodeNotNullMark` and `decodeSerializableValue` meet it there, before reading any index;
- `unsupportedWriterTypeError`: every other read (`decodeInt`, `decodeNull`, `beginStructure` of a list, map or record…)
  matches none of its types with a union and fails through it;
- `beginStructure` of a polymorphic value, which hands the schema on without a type check (the polymorphic decoder would
  read a union's index itself).

Each place throws `noWriterSchemaError()`, which is `noElementBegunError()` (same `IllegalStateException`, same message as
before), except on the record-as-map decoder: it kept its schema in a `lateinit` property and threw Kotlin's
`UninitializedPropertyAccessException("lateinit property currentAvroSchema has not been initialized")`; it still does,
raised by reading a never-assigned `lateinit` property of that name, since the class is not public on Kotlin/Native.

`decodeAndResolveUnion` is split: the type check (20 bytes, inlined everywhere) and `resolveUnion` (the index read), so
the schema is read once into a local. The general record decoder keeps its decoding-step check (`currentDecodingStep`),
which already threw first on every `decode*` it overrides.

`AnySerializerTest` stubs the decoder's schema on a mock: the field has no getter to stub any more, so the test assigns
it on the mock.

Files: `AbstractAvroDirectDecoder.kt`, `RecordDirectDecoder.kt` (both record decoders), `CollectionsDirectDecoder.kt`,
`RecordAsMapDirectDecoder.kt`, `AvroValueDirectDecoder.kt` (all in `core/.../internal/decoder/direct/`),
`core/.../AvroDecoder.kt` (`unsupportedWriterTypeError`), `core/src/jvmTest/.../AnySerializerTest.kt`.

### Predicted effect of step 1 (measured in the read A/B)

**Allocation, escape analysis off: no change on any row.** Every decoder keeps its size (table above); nothing else
allocates differently (the marker is one shared instance, built once).

**Throughput:**
- `complex` read @1, @15, @200: up. The profile's `getCurrentAvroSchema` frames (3.3%) and their stubs (1.0%) go, and
  `decodeAndResolveUnion` reads one local instead of a virtual call three times (part of its 3.4%): ≈ 4–7% of a
  `complex` read at most, less once the JIT's own inlining of the formerly bimorphic sites is counted.

  slightly up. A JMH fork of one of these sees one or two decoder kinds, so the getter call was mono- or bimorphic and
  already inlined; what remains is the null check the getters made.
- Every write row and every other library's row: unchanged (encoders untouched).

## Step 2 — nullable fields on a short path

### Is step 1 already as short?

No. After step 1, a present value of a `String?` field written `["null","string"]` on the exact record decoder goes:
`decodeNullableSerializableElement` (kotlinx's generated deserializer, base implementation) → `beginElement` →
`descriptor.isNullable` → `decodeNotNullMark` (virtual) → `decodeAndResolveUnion` (type compare) → `resolveUnion`
(marker compare, cast to `UnionSchema`, `readIndex`, `List.size` and `List.get` on the branches, two interface calls) →
the branch's type loaded and compared with `NULL` → `decodeSerializableValue`. The short path drops the `decodeNotNullMark`
call, the cast, both list calls and both type loads: `readIndex`, one `int` compare, one field write. Kept.

### What changed and why

- `RecordResolver.kt`: when a workflow is resolved and its record decodes exactly as written (`exactFieldSchemas`),
  `nullableUnionFields` marks each field whose writer schema is `["null", T]` or `[T, "null"]` with a
  `NullableUnionField(union, nullIndex, nullBranch, valueBranch, valueIndex)` (`@JvmField`s), by element index, in
  `SerializationWorkflow.exactNullableFields` (internal, out of the dumps). The shared empty array when the record has no
  such field (so a writer schema parsed anew per call, `FreshWriterSchema`, allocates nothing more) or is not exact.
- `RecordDirectDecoder.kt`, `ExactRecordDirectDecoder`: keeps that array next to `fieldSchemas` (`reset` takes it) and
  overrides `decodeNullableSerializableElement`: after `beginElement`, if the element has a `NullableUnionField`, its
  current schema is still that union (identity) and the deserializer is of a non-nullable type, it reads the index:
  the null index → current schema = the null branch, `readNull()`, `null`; the value index → current schema = `T`,
  `decodeSerializableValue`; anything else → `unionIndexOutOfRangeError` (same message). Otherwise the generic path,
  out of line (`decodeNullableValue`). The codec sees the same calls in the same order (the validating decoder included).
- `AbstractInterceptingDecoder.kt`: `decodeIfNullable` `private` → `internal`, reused by the fallback.
- `AbstractAvroDirectDecoder.kt`: `beginRecord` passes the array.
- Unchanged: the general record decoder (reordered, skipped or defaulted fields), other unions, `JsonDefaultDecoder`,
  block decoders (`List<String?>` items go through `NullableSerializer`), a non-nullable property read from a nullable
  union (pre-existing bug #1, its message pinned by a test).

**Deviation from the sketch:** the check lives in `decodeNullableSerializableElement`, not `decodeNotNullMark`.
`decodeNotNullMark` does not know which element it is for; finding out would cost every field (nullable or not) a
stored index in `beginElement`. `decodeNullableSerializableElement` is handed the index, and kotlinx's generated code
calls it for every nullable property. Same work otherwise: index read, compared with the null index, current schema set
to `T` directly.

**Guards:** `currentAvroSchema !== field.union` (a serializer that asked `currentWriterSchema` after
`decodeElementIndex` already read the branch); `deserializer.descriptor.isNullable` (a nullable deserializer is handed
its null, e.g. one mapping null to a value).

## Observations, not fixed

- **The validating decoder rejects a collection begun by a non-collection serializer right after another collection on
  the same decoder** (`Invalid call mapNext() … expected the start of a map`): since collections are read in blocks by
  the decoder (M5-01), a decoder that read a collection's last block takes the next `beginStructure` of a collection as
  that collection's next block, and the validator, unlike the plain decoder, tells `mapNext` from `readMapStart`. Only
  serializers that call `beginStructure` for a collection themselves reach it (the plain decoder reads the same varint
  either way); `DecoderReuseTest`'s block peeks run without validation for that reason, and so does test 3. Not
  checked on `main`, and outside this unit's files: recorded here for the orchestrator to place.
